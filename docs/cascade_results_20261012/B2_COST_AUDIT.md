## Подтверждённая бесполезная работа перед review

В 8 строках корректно разобранный предварительный анализ затем отброшен событием `pre_injection_budget`: дополненный запрос больше существующего лимита 60000 сериализованных байт. На эти 8 ответов потрачено 7313 выходных токенов. Ещё один pre-анализ оборван на 3400 токенах и не использован.

`PredictableBudgetHook` заранее собирает минимальный дополненный запрос с пустым объектом анализа, который служит только нижней границей размера и никогда не отправляется модели. Если даже он превышает 60000 байт, любой валидный анализ также превысит лимит. Тогда исходный Hook всё равно отбросил бы его и вернулся к базовому review.

На 6 из 28 строк пропуск доказан этим условием. Локальная проверка подтвердила побайтно неизменный запрос к review и тот же сохранённый ответ. Убираются 23735 входных и 8194 выходных токенов. Это включает строку с оборванным pre-анализом. Пять тестов проверили строгую границу лимита, отсутствие мутации, делегирование остальных профилей и корректность нижней границы при Unicode/экранировании.

Если дополнительно в экспериментальном профиле убрать последующие компоненты, получается 50 вызовов вместо 100, на 28.8% меньше входных и 30.4% меньше выходных токенов. Сохранённая проекция F1 остаётся 0.8889. Это не означает измеренного ускорения в два раза и не доказывает сохранение качества вне valid46.

## Почему включённый prefix cache сам по себе не решает задачу

По точным токенам `/tokenize`, сохранённым в 28 primary receipts: медиана наилучшего префикса с предыдущим review равна 420.5 токена. Даже лучший выбор любой другой review-строки даёт всего 15.7% общих входных токенов суммарно. Это оценка только review/review-пар, а не измерение реальных попаданий кэша. Выравнивание блоков, гибридное состояние, конкуренция и вытеснение могут снизить реальное переиспользование.

Сейчас JSON начинается с `contract`, затем переменной `coverage`, лишь затем с политики и инструментов. Различия в начале запроса могут мешать повторному использованию одинаковой политики дальше по тексту. Перенос общих источников в начало — отдельный профиль промпта, его качество нужно измерить. APC сокращает prefill, но не decode: https://docs.vllm.ai/en/v0.22.1/features/automatic_prefix_caching/

Для гибридных Mamba/GDN-моделей также существует описанная upstream проблема расположения сохранённого checkpoint относительно общего префикса. Обсуждение содержит последующее уточнение автора о частичном исправлении на main. Применимость именно к нашему 0.19.1 не проверена, поэтому это не установленная причина: https://github.com/vllm-project/vllm/issues/45238

## Почему F1 0.32 пока не объяснён

1. F1 0.8889 получен на полном прохождении 46 разработочных строк. В большом тесте второй этап может пройти только часть кандидатов. Сохранённая кривая по приоритету Granite достигает всех четырёх исправлений после 17 из 28 кандидатов; это качество при заданной частичной обработке, не измеренный дедлайн или реальный порядок завершения конкурентных запросов.
2. Пропуск только Qwen на этом valid дал бы Granite 0.7805. Поэтому старый балл нельзя объяснить одним утверждением «Qwen не успел», перенеся этот вывод на неизвестный тест.
3. OR не может убрать ложные положительные Granite. Его две ложные тревоги исчезали при большем контексте, но большой контекст добавлял другие ошибки. Уверенность модели не доказывает наличие достаточных источников.
4. Статус 0 не гарантирует полного участия всех этапов: при сбое Qwen остаётся Granite, а при частично выполненном Granite непосчитанные строки получают 0. Без старого журнала, выходных меток и размера входа вклад этих путей не установлен.
5. Precision 0.26316 не является измерением доли положительного класса. Дубликаты id в том платформенном входе также не доказаны.

## Следующие эксперименты на A100

Порядок фиксируется до новых прогонов, изменения сравниваются отдельно:

1. Сокращённый B2: primary + blind с доказуемым preflight выше, без последующих компонентов. Сравнить сохранение меток, input/output tokens и время целиком на уникальных строках. Отдельно проверить случаи, где раньше срабатывали DF/Ems/F/S/P, чтобы не выдавать нулевой вклад на valid за универсальную ненужность.
2. Один совместный разбор Qwen с коротким обоснованием и адресами источников: сохранить проверку условий политики, исключений, сущности и подтверждения инструментом, но не генерировать отдельный blind JSON и повторный длинный review. Это меняет метод: модель видит текущий ответ с начала, независимость blind-прохода теряется. Улучшение качества/скорости не обещается. Профиль пока не реализован и не измерен.
3. Общую политику и определения инструментов размещать перед переменными данными; замерить настоящие APC hits. Для гибридного кэша отдельно проверить наличие checkpoint в общей части. Одного включённого `--enable-prefix-caching` недостаточно для обещания ускорения.
4. Отдельный запуск с `--language-model-only`: в 0.19.1 флаг официально отключает мультимодальные входы (лимиты всех модальностей 0). В текущей команде каскада этого флага нет. Проверить, исчезает ли лишний vision warmup, и измерить старт; размер ускорения не установлен. Отдельно сравнить `--max-num-batched-tokens 4096/8192` с исходным режимом, сохраняя входы и учитывая VRAM. Документация: https://docs.vllm.ai/en/v0.19.1/configuration/engine_args/

Требуемый результат — сокращение полного времени при сохранении качества на независимых размеченных данных, а не только лучший F1 на многократно использованном valid46. Для цели около ×5 одних 30% экономии токенов недостаточно.
