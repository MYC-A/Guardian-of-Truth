# Следующий метод: повторное использование политики и проверка действий

Это проект эксперимента, не новая сборка и не измеренный прирост качества. Боевой ZIP не изменён. Разбор выполнен с независимым участием Astra.

## Что известно

- Каскад получил на платформе F1 0.32448, P 0.26316, R 0.42308. После исправления сопоставления повторяющихся id пользователь сообщил тот же результат. Это не подтверждает id как объяснение провала.
- Новый запуск Qwen B2, по сообщению пользователя, снова не прошёл. Пока неизвестно, речь об ошибке выполнения или низкой оценке. В A:/GIS_Загрузки нет свежего лога этого запуска.
- В standalone entrypoint внутренний duration=1800 не резервирует время для pip install и внешних операций. Это проверенное ограничение, но без лога не установленная причина остановки.
- Сохранённый каскад valid46: TP20/FP2/FN3/TN21. Разбивка по доменам: airline 6/0/0/6; banking 5/1/1/4; retail 4/1/1/5; telecom 5/0/1/6. Простое изменение весов этих четырёх сохранённых профилей не даёт F1 0.324. Изменение состава внутри домена, трудности примеров и технического покрытия этим не исключается.
- Precision не измеряет долю положительных примеров. Изменение только доли классов при неизменных условных ошибках не объясняет падение recall с 20/23 до 0.42308.
- valid46 многократно использован при разработке. Новые рассуждения по его ошибкам не являются независимой валидацией.

## Новое наблюдение

В valid46 ровно четыре различных полных блока <policy>, проверено SHA256 точного содержимого. Они повторяются 12/11/11/12 раз. Поэтому статическую структуру правил можно извлекать один раз на точный текст политики. Политика и каталог инструментов кэшируются по отдельным точным хэшам; различающиеся каталоги нельзя объединять по имени домена.

Три FN полного каскада по эталонным объяснениям:

1. banking task_003: преждевременная эскалация при ещё доступных поисковых действиях; также противоречие в сводке.
2. retail 29: заявление о невозможности обмена, хотя найден доступный вариант того же product_id и соответствующий инструмент.
3. telecom contract_end: resume_line запрещён истёкшим сроком контракта при заданной в policy текущей дате.

Это мотивирует отдельную проверку допустимости действия и обоснованности отказа. Три примера не доказывают её вклад на платформе.

## Экспериментальный вариант

Один локальный Qwen3.8-сервер используется для всех стадий. Astra помогает проектированию; онлайн-вызов Astra в офлайн-сабмите не предполагается.

1. Один раз для новой политики извлечь индекс: действие, обязательные условия, запреты, исключения, точные адреса исходных абзацев. Код проверяет адреса и цитаты. Индекс служит для поиска; он не доказывает правильную интерпретацию и не заменяет оригинал.
2. Код выделяет текущие вызовы, аргументы и результаты инструментов, роли, порядок событий и связи id. Смысловые утверждения и применимость правил оценивает модель. Неразобранные фрагменты явно сохраняются как неполнота.
3. Для строки собрать оригинальные правила и связанные доказательства. Один компактный вызов проверяет вместе факты, действие и отказ. Для отказа вопрос конструктивный: существует ли конкретное разрешённое действие с выполненными предпосылками? Для операции: выполнены ли необходимые условия с учётом исключений и состояния на текущий ход?
4. Выход содержит короткое решение, тип нарушения и адреса источников. Не найденная цитата или неполное покрытие не превращаются автоматически в метку 0/1. Ограниченный второй разбор применяется к неоднозначным/неполным строкам обоих предварительных классов. Предварительный ответ сохраняется отдельно от технического статуса.

Отличие от B2 — повторное использование статической политики и один совместный разбор строки вместо blind/review/веток с повторным чтением большого пакета. Вызовы по одному на каждое утверждение запрещены в этом эксперименте: иначе снова растёт число запросов. Длинный либо усечённый ответ не считается полностью проверенным.

В B2 уже есть проверка требований, условий, исключений и ожидаемых действий. Само добавление таких слов в промпт ничего нового не даёт. Эксперимент меняет распределение работы и представление входа. В ключ переиспользования включаются все инструкции и каталоги, влияющие на интерпретацию; общий индекс ссылается на исходные разделы вместе с родительскими условиями. Совместные действия одного хода проверяются вместе, а выводы предыдущих классифицированных строк не превращаются в состояние диалога.

## Порядок проверки

1. Зафиксировать смысл новой платформенной неудачи: ошибка выполнения или оценённый результат. При наличии лога сверить весь запуск и число реально обработанных строк; не объяснять техническую остановку качеством модели.
2. Контрольный вариант — сокращённый B2 с прежним представлением входа. Новый вариант — индекс политики плюс совместная проверка. Сначала одинаковые модель и веса, чтобы отделить эффект метода от замены модели.
   Перед итоговым сравнением провести две отдельные абляции: одинаковый короткий judge на исходном пакете и адресной карточке; затем одинаковые карточки с индексом политики и без него. Это отличает эффект вопроса/представления от экономии повторяемого разбора.
3. До инференса зафиксировать набор контрпримеров: допустимое и запрещённое действие различаются одним условием/датой/согласием; отказ с существующим решением и без него; повтор старой ошибки и новая ошибка; одинаковый факт для разных сущностей. Примеры проходят настоящий парсер. Отдельно преобразования без изменения смысла: порядок строк, id, CSV/Parquet, размер пакета. Синтетические примеры — диагностика, а не оценка реального F1.
4. На неизменном valid46 сравнить конкретные исправленные и новые ошибки, фактические входные/выходные токены, незавершённые строки и полное время. Затем нужна отложенная разметка, не использованная для конструкции промпта; разбиение по диалогам, а не соседним ходам.
5. Проверить массовый прогон на уникальных входах с холодным стартом. Копии строк с одинаковыми префиксами не подтверждают скорость. Цель пользователя — примерно пятикратное ускорение; необходимая скорость рассчитывается как N / (доступные минуты минус старт и резерв). Для условных 500 строк и 20 минут инференса это 25 строк/мин, но 500 не является установленным размером теста.
6. Если основной вклад времени остаётся в prefill и требуемой скорости нет, прекратить усложнение Qwen3.8 и проверить тот же протокол на Qwen3.5-35B-A3B. Рост качества меньшей модели пока гипотеза. Следующая более дорогая линия — дистилляция специализированного судьи на независимых данных, а не дообучение на этих 46 строках.

Новый ZIP выпускать после проверки метода и рантайма, не по одному улучшению F1 на уже просмотренном valid46.
