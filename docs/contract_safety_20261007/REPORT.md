## 1. Что именно подтверждено

Исполняемые входы и наблюдаемые результаты находятся в [baseline_probes_v3.json](baseline_probes_v3.json). [probes.py](probes.py) блокирует сеть, проверяет результаты assertions и отказывается перезаписывать output. В нём 15 групп, включая четыре отдельных дефекта evaluator в одной группе. Это counterexamples, а не оценка частоты отказов модели на valid46.

### P: правило о происхождении аргумента становится обвинением без проверки смысла

**1. Условие «для возврата» переносится на lookup.**

Политика требует получать ID от пользователя при возврате, но отдельно разрешает lookup с ID, полученным добавлением `-A` к пользовательскому префиксу. Пользователь сообщает `ORD`, ассистент вызывает lookup с `ORD-A`. P выдаёт `MECHANICAL UNSOURCED_REFERENCE`, итог ERROR. Проверка `recheck` возвращает true.

Причина: `contracts()` находит предложение; `applies()` проверяет только связь с именем поля. Regulated action, условия и исключения этому сопоставлению не передаются. Это уже известная ошибка, повторно воспроизведённая в новом worktree.

**2. Внешнее отрицание требования теряется.**

`It is not true that order_id must come from the user.` становится положительным требованием. Явно разрешённое вычисление ID снова даёт ERROR. Совпадение подстроки `must come from the user` недостаточно для установления polarity всего предложения. Это также повторная проверка ранее найденного дефекта.

**3. Требование к другому полю переносится на ID через сокращённое имя.**

`The order total must come directly from the user.` применяется к `order_id`: `_names('order_id')` содержит не только `order_id` и `order id`, но и `order`. При явном разрешении вычислить ID для lookup всё равно получается ERROR. Требование к сумме заказа не является требованием к его идентификатору.

**4. Разрешённая альтернатива источника теряется из-за запятой.**

`The order_id must come from the user, or from a verified tool result.` Пользователь сообщает email, корректный парный вызов find_orders возвращает успешный verified result с `order_id=O-9`, затем выполняется lookup с этим ID. P сам записывает `FOUND/tool_result`, но одновременно выдаёт ERROR «не получено от пользователя».

`FROM_USER` исключает только непосредственно следующую последовательность ` or`; запятая ломает эту защиту. Исправление только для запятой оставит ту же проблему для других конструкций AND/OR, оговорок и ограничений источника.

**5. Равноценная переформулировка schema description выключает проверку.**

`The existing order identifier.` → `The identifier of any existing order.` При одинаковом запрете придумывать ID и одинаковом неизвестном значении изолированный результат P меняется ERROR → 0. Слово `any` попадает в `GENERATED`, и поле ошибочно становится `MAY_BE_NEW`.

Это подтверждённый пропуск слоя P; итог всей системы при живом базовом reviewer здесь не измерялся. P также документированно оставляет entity binding непроверенным — наличие строки в источнике само по себе не доказывает правильность её использования.

Код: [provenance.py](../../src/guardian_truth/v6fix/provenance.py), особенно строки 27, 32, 109–111, 125–132, 164–177.

### S: список разобран полностью, но это не означает запрет других инструментов

**6. Открытая вселенная инструментов ошибочно становится закрытой.**

Политика явно говорит: каталог перечисляет только read operations, динамические write tools разрешены; текущий apply_credit доступен и разрешён. Каталог синтаксически полностью разобран. S объявляет текущий инструмент недоступным и выдаёт `MECHANICAL ERROR`.

Для **того же исходного row** уже существующий `integrated.declarations.check(tool_universe_closed=False)` корректно возвращает gap без обвинения. Новая ветка S обходит это различие и строит собственный `CONTRACT_TEXT` из полноты разбора каталога. Это реальное несогласование двух слоёв, а не отсутствие нужной идеи в проекте.

Код: [structural.py](../../src/guardian_truth/v6fix/structural.py):23–30; [packer.py](../../src/guardian_truth/evidence_packer/packer.py):375–384; сравнить [declarations.py](../../src/guardian_truth/integrated/declarations.py):129–137, 211–220.

### F: проверка количества вызовов точная, связь с полной нормой неполная

**7. Исключение следующей строкой вообще не попадает в extraction input.**

```text
You may make at most one tool call per turn.
This limit does not apply to authenticated users.
```

В истории успешный authenticate receipt подтверждает authentication, текущий ход делает два lookup. Отдельная строка с исключением не содержит ключевых слов отбора F и не передаётся extractor. Два одинаковых предложения `MAX_TOOL_CALLS_PER_TURN=1` принимаются как MECHANICAL, итог ERROR.

Здесь **модельные предложения заданы тестом**. Это не утверждение, что живая модель обязательно ошибётся. Однако обрезание исключения до model call подтверждено непосредственно по `extraction_lines`; downstream admission не восстанавливает потерянную применимость.

**8. Вложенная область действия теряется за промежуточным заголовком.**

```text
If user unauthenticated:
General interaction rules:
You may make at most one tool call per turn.
For authenticated users, no call limit.
```

При подтверждённой authentication одинаковые предложения ограничения снова дают ERROR. Проверяется только ближайшая предыдущая строка, а не цепочка scope/heading.

**9. Совпадение двух extraction replies не проверяет регулируемую операцию.**

`You should not report more than one failed tool call per turn.` ошибочно интерпретируется тестовыми proposals как запрет двух вызовов. F принимает точную цитату и число, но не различает **сообщать о неудачных вызовах** и **выполнять вызовы**. Это повторно воспроизведённая ранее найденная admission boundary.

**10. Предел ноль отбрасывается.**

`You may make at most 0 tool calls per turn.` + корректное предложение `n=0` + два текущих вызова. F отбрасывает правило с `n missing`, потому что требует `n >= 1`. Ноль является допустимым максимумом; такое правило выражает полный запрет вызовов.

**11. Невалидный extraction reply вызывает необработанный KeyError.**

Ответ `{"rules":[{"type":"MAX_TOOL_CALLS_PER_TURN","n":1}]}` не содержит обязательных полей. Он декодируется без локальной проверки schema; `bind()` падает на `_key()`. Запрос provider strict schema не заменяет валидацию полученного ответа.

Код: [turnrules.py](../../src/guardian_truth/v6fix/turnrules.py):53–62, 79–80, 91–97, 118–159.

### Verifier и candidate pool: ошибки обработки сохраняются после «полного» объединения

**12. SUPPORTED принимается из ответа без обязательного поля.**

Реальный parser/packet, точные policy/evidence quotes, boundary reply содержит `verdict=SUPPORTED`, но не содержит обязательного `analysis`. `v5.verify()` возвращает `ADMITTED/SUPPORTED`. В тесте также `finish_reason=length`, но **самостоятельное доказательство schema bug — отсутствие обязательного поля**. Политику допуска полностью валидного JSON при таком finish_reason нужно определить отдельно; нельзя смешивать эти два вопроса.

Код: [common.py](../../src/guardian_truth/verification/common.py):20–24; [v5.py](../../src/guardian_truth/repair/v5.py):83–85; обязательная схема в [verifier.py](../../src/guardian_truth/verification/verifier.py).

**13. Пропуск второго действия в AT удаляет отдельный поддержанный candidate первого.**

В исходном ходе два вызова. Policy явно запрещает ID первого. Boundary reply вернул только первый target с точными policy/evidence. Код записывает `admitted=true`, но `candidates=[]`, потому что второй target отсутствует.

Неполное покрытие запрещает утверждать, что весь ход проверен и чист. Оно не должно удалять отдельно поддержанное обвинение: его нужно сохранить для verifier, а пропущенное действие пометить UNCHECKED. Candidate с точными цитатами ещё не становится автоматически истинным обвинением.

Код: [v5.py](../../src/guardian_truth/repair/v5.py):257. Это сохраняется и с флагом `pool`.

**14. Режим pool схлопывает разные причины одной нормы.**

Два кандидата Ems для одного target и requirement содержат разные причины и разные evidence IDs. Первый будет REFUTED, второй SUPPORTED. Дедупликация оставляет только первый; проверяется только он; итог 0. Пул использует ключ `(target, origin, requirement[:200], kind)` без evidence, reason и proof.

В probe синтетические ответы задают границы A/Ems/verifier; parser, построение очереди, дедупликация и итоговая агрегация настоящие. Это доказательство потери кандидата, а не новая оценка качества verifier. Оно отличается от обычного выключенного pool и от явного лимита очереди K.

Код: [v5.py](../../src/guardian_truth/repair/v5.py):343–350.

### Evaluator: четыре чистые вычислительные ошибки

**15. Замены операторов меняют содержимое строк.**

`value == 'NOT ALLOWED'` при `value='NOT ALLOWED'` даёт `OK False`; аналогично для `'A=B'`. Замены `NOT` и `=` выполняются внутри quoted literals. CBTE может объявить ложный CONTRADICTION и понизить правильную applicability.

**16. Decimal получает уже округлённый float.**

`9007199254740993.0 == 9007199254740992.0` даёт `OK True`. `ast.parse()` превратил литералы во float до создания Decimal. Этот пример проверяет точность; частота подобных значений в реальном наборе не измерялась.

**17. NaN вызывает аварийное исключение.**

NUMBER binding со строкой `NaN` проходит создание Decimal, затем сравнение вызывает необработанный `decimal.InvalidOperation`. Нужен typed failure для конкретной проверки, а не исключение всей строки.

Код: [evaluator.py](../../experiments/guardian_addons/evaluator.py):47, 94, 113–114, 129–145. Пункт 15 содержит два отдельных literal probes; 16 и 17 — ещё два. Evaluator по-прежнему проверяет собственное выражение модели, а не истину policy binding.

## 2. Что повторно проверено вне этих probes

[archive_recheck.json](archive_recheck.json) заново воспроизводит предыдущий архивный пересчёт: 14 semantic run files, 20 add-ons run files; CBTE/CBT не различаются по binary на общих rep1 строках трёх наборов. Исторические outputs не перезаписывались.

**CB всё ещё зависит от скрытого текущего действия на длинном входе.** На двух исходных valid46 inputs при одинаковой истории, замене current tool на другой объявленный инструмент и равной длине response меняются четыре видимых поля prepass: coverage, policy, declarations и history. Причина прежняя: сначала action-dependent packer выбирает источники, затем CB скрывает action. Это исправляется до packer, а не удалением ещё одного JSON metadata field.

Новые scorers по-прежнему допускают last-record-wins и missing-ID denominator. Это уже подтверждено предыдущим аудитом; в этой фазе **не заявляется новый найденный случай нечестного выбора успешного ответа**. Отдельный фальсифицирующий retry/scoring эксперимент не добавлялся.

Выбранные прежние тесты повторены: **97 passed**. Это показывает пробелы test coverage, а не отсутствие перечисленных ошибок. Весь исторический test suite этой фазой не объявляется зелёным; прежнее Windows ограничение `fcntl` для двух research модулей не исправлялось.

## 3. Что это означает для системы

- Regex полезен для поиска кандидатов. Ошибка возникает, когда lexical match выдаётся за установленные scope, polarity или разрешённый источник и получает право менять binary result.
- `recheck=true` на ложных P/S/F обвинениях означает повторение одного алгоритма. Это не независимая проверка семантики.
- Чистые arithmetic/schema/pool ошибки можно исправить детерминированно. Применимость произвольной NL нормы нельзя гарантировать добавлением списка новых специальных фраз.
- Нельзя лечить всё переводом в UNKNOWN→0 и объявлять улучшение: это может убрать FP ценой новых FN. Нужны отдельные метрики покрытия и полный парный replay.
- Ни новые TP, ни новый F1 здесь не заявляются: runtime пока тот же. Исправления и их эффект — следующая отдельная фаза.

## 4. Порядок исправлений

1. Общий контракт authority: observation/search candidate, semantic hypothesis, source-bound applicable violation. Прекратить выдавать одно слово MECHANICAL за все три уровня. Переходы в ERROR сделать явными и versioned.
2. Локально валидировать каждый reply по отправленной схеме, фиксировать failure reason, безопасно сохранять кандидатов после technical failure. Проверять F, verifier и prepass, а не только основной reviewer.
3. Исправить evaluator tokenization/Decimal/nonfinite, `n=0`, identity/dedup candidates и локальную AT coverage. Эти изменения отдельно проверить на сохранённых raw outputs.
4. S должен пользоваться общим explicit closure contract, уже существующим в integrated guard. Не выводить closure из header или полного разбора.
5. P должен сохранять целевое поле, action scope, source alternatives, conditions/exceptions и их authority. Stem/word match — только retrieval. Для неподдержанного binding сохранять hypothesis с видимым gap; подтверждать его отдельным source-based механизмом и измерять возникающие FN.
6. F должен получать связный policy context и scope/exception provenance. Совпадение двух model replies оставить модельным свидетельством. Для ограниченного формального grammar допускается проверяемый compiler с явными границами; произвольный английский нельзя автоматически считать этим grammar.
7. CB prepass строить из prompt/history независимо от current response; новый wire/request hash требует новых ответов. Старый prepass cache нельзя объявлять совместимым после смены входа.
8. Полные valid46 и доступные long archives: fixes-only, semantic-gates, neutral-CB и matched open control отдельно. Только после offline checks — новые модельные фазы и новый независимый holdout. Старый gold, receipts и frozen decisions сохранять.
