# Этап 2: происхождение аргументов без LLM

Реализован структурный граф, а не полноценная модель мира. Он показывает, откуда могло прийти значение,
к каким явно указанным идентификаторам оно относится и какие наблюдения той же структуры были раньше.
Правила допустимости операций — следующий слой. Подключение LLM не требуется для работы текущего решения.

## Поток данных

```text
prompt / response
        │
        ▼
разбор ролей, вызовов и результатов
        ├── каталог → точные проверки инструментов и схемы
        ├── результаты → узлы наблюдений → связи предыдущих версий
        └── аргументы ответа → поиск совпадений и несовпадений в графе
                                      │
                                      ▼
                            AnalysisContext
                                      │
                       SemanticAnalyzer.analyze(context)
                       сейчас: NoSemanticAnalyzer
                       позже: отдельный локальный адаптер
                                      │
                                      ▼
                   проверка формата вывода и ссылок
                                      │
                                      ▼
                 отчёт: точные нарушения + предположения
```

## Что хранит граф

- `FactNode`: значение одного поля результата инструмента, путь внутри JSON, событие, роль, имя инструмента,
  структурные идентификаторы, ссылки на исходный результат и связанный запрос, если связь однозначна.
- `previous`: ссылки на предыдущие наблюдения с той же структурной областью. Старые узлы не удаляются.
- `ArgumentTrace`: значение аргумента проверяемого вызова и ссылки `supporting` / `alternatives` на узлы истории.
- `issues`: неоднозначные связи вызова и результата, конфликт идентификаторов запроса/ответа,
  результаты, не разобранные как JSON. Текст этих результатов остаётся в истории и доступен смысловому модулю.

Идентификаторы распознаются по именам полей с окончаниями `_id` и `_number`.
Это структурная эвристика, не автоматическое доказательство владения или уникальности сущности.
Дополнительно сохраняются явные `date`, `start_date`, `end_date`, `as_of`, в том числе из запроса:
один номер рейса в разные даты не должен превращаться в одну версию рейса.
Дата без идентификатора не образует сущность.

Поля сравниваются по точному имени и типу значения. Строка `"001"` не превращается в число `1`;
`true` не приравнивается к `1`. Даже числовые `1` и `1.0` здесь остаются разными представлениями — это ограничение
структурного поиска, а не вывод о математическом неравенстве. `id` не превращается автоматически в `payment_id`.

## Значение статусов аргумента

| Статус | Что установлено | Чего он не доказывает |
|---|---|---|
| `observed_match` | Найдено то же поле и значение с пересечением идентификаторов без явного конфликта | Корректность операции, владение и актуальность в реальном мире |
| `older_observation_match` | Значение совпало со старым наблюдением, а более позднее в той же структурной истории отличается | Что аргумент обязан повторять последнее значение |
| `ambiguous_history` | Подходящие истории или одновременные записи дают разные значения | Какой источник истинный |
| `scope_conflict` | Значение встретилось, но структурные идентификаторы расходятся | Запрет использовать сведения другой сущности |
| `different_observed_value` | В области с пересекающимися идентификаторами найдены другие значения поля | Что новое значение ошибочно: оно может быть целью изменения |
| `unscoped_match` | Поле и значение встретились, но идентификаторов для привязки недостаточно | Что это сведения нужного человека или объекта |
| `not_observed` | В структурированном индексе такого совпадения нет | Отсутствие в свободном тексте, невозможность вычисления или выдумку |

Ни один из этих статусов сам по себе не выставляет метку `1`.

## Защита от ложного объединения

1. Версии связываются только внутри одного инструмента, роли, пути к полю и набора идентификаторов.
   Между разными инструментами обновления автоматически не переносятся.
2. Порядок — порядок наблюдений в журнале, не гарантированное время изменения мира. Временные отметки
   свободного текста и метаданные актуальности пока не интерпретируются.
3. Перестановка явно идентифицированных объектов в массиве не меняет их структурные связи.
   Элементы без собственного идентификатора в общую цепочку версий не сливаются.
4. Повтор одного идентификатора внутри одного результата даёт одновременные альтернативы, не две последовательные версии.
5. Пропавшее в следующем результате поле не считается удалённым: результат может быть частичным.
6. Если ожидаются несколько ответов на один и тот же инструмент без идентификатора вызова, порядок соответствия не угадывается.
   Самодостаточные идентификаторы из результатов сохраняются и без такой связи.
7. Результаты внутри проверяемого `response` не служат независимым доказательством самого этого ответа.
8. Дубли ключей JSON, `NaN`, `Infinity` и числа вне поддерживаемого конечного диапазона не индексируются как однозначные данные.

Ссылки ведут на целое исходное событие, а путь указывает поле внутри его JSON. Смещения — символы, не токены и не байты.
У каждого аргумента экспортируется не более 32 ссылок каждого вида, начиная с недавних; обрезка отмечается `truncated`.
Сам граф наблюдений этим пределом не обрезается. Предел общего контекста и времени работы будущей модели — ответственность её адаптера.

## Подключение будущей модели

Файл интерфейса: `src/guardian_truth/semantic.py`. Основной поток не импортирует библиотеку модели.

```python
from guardian_truth import Detector
from guardian_truth.semantic import AnalysisContext, SemanticResult

class LocalAnalyzer:
    name = "local-v1"

    def __init__(self, model_client):
        self.model_client = model_client

    def analyze(self, context: AnalysisContext) -> SemanticResult:
        # Здесь адаптер выбирает контекст, вызывает модель и переводит её ответ
        # в Finding с проверяемыми ссылками Source. Пока только пример границы:
        return SemanticResult(unresolved=["local_model_not_implemented"])

# Будущее подключение: Detector(semantic=LocalAnalyzer(model_client)).
# Текущий рабочий режим без модели:
detector = Detector()
```

`AnalysisContext` содержит `prompt`, `response`, `history`, `candidate`, `catalog`, `obligations`, `graph`, `evidence`.
Идентификатор строки, эталонная метка и объяснение из датасета в него не передаются.
Фрагменты истории — данные для анализа, а не команды исполнителю. Адаптер не должен исполнять код из контекста или модели.

Возвращаемые `Finding` принудительно становятся `hypothesis`; границы ссылок проверяются.
Это проверка существования фрагмента, а не подтверждение, что он действительно обосновывает вывод.
Исключение адаптера даёт `semantic_backend_error`, сохраняя результаты точных проверок.
Это не изоляция недоверенного Python-кода и не ограничитель времени: их нужно реализовывать в адаптере при необходимости.
Старое подключение `Detector(checker=...)` поддерживается через `LegacyCheckerAdapter`.

Чтобы выводы модели начали влиять на CSV, позже нужна отдельная проверенная политика принятия решения.
Простое подключение адаптера намеренно не превращает произвольное мнение модели в доказанную ошибку.

## Проверка на рабочем файле

На 46 примерах `valid.parquet`:

- 5 753 скалярных наблюдения; 78 связей с предыдущими наблюдениями.
- 191 значение аргументов в 19 примерах. Пустые вызовы не содержат значений для этого этапа.
- 133 `observed_match`, 48 `not_observed`, 4 `scope_conflict`, 6 `different_observed_value`.
- Итоговые метки не изменились: TP=6, FP=0, FN=17, TN=23; F1 ≈ 0,414.

Это покрытие структурного поиска, не доля доказанно правильных аргументов. Никакого измеренного прироста F1 этот этап пока не дал.
Выборка уже использована для разработки и не является независимым тестом.

```powershell
python -m unittest discover -s tests -v
python scripts/predict.py --input valid.parquet --output outputs/stage2_predictions.csv --audit outputs/stage2_audit.jsonl
python scripts/evaluate.py --input valid.parquet --output outputs/stage2_metrics.json
```

## Следующий содержательный этап

Явные предварительные условия операций. Каждое правило должно определять, откуда взято условие,
какие поля и сущности нужны, как учитывать неизвестность и почему нарушение существенно.
Тогда граф станет источником данных для проверок вроде «договор уже истёк» или «заказ не находится в разрешённом статусе».
Перевод произвольного текста политики в такие правила пока не реализован; его можно вынести в тот же подключаемый смысловой слой,
не приравнивая автоматически сгенерированное правило к проверенному.
