## Что было неправильно

1. `idcheck` определяет read/create по префиксу имени инструмента, принимает
   отсутствие строки за нарушение, выбирает первый ID объекта и смешивает
   старые и новые пользовательские намерения/результаты. Законное изменение
   телефона становится конфликтом. JSON key order меняет обнаружение.
2. Regex «must not ... both» не связывает запрет с регулируемыми действиями:
   запрет одновременно delete/archive превращается в запрет call+prose.
3. H3 объявляет mismatch доказанным по наличию двух строк. Значение customer_id
   может подставляться как правильный invoice_id; даже несуществующий аргумент
   проходил. Exact quotes не доказывают правильность роли, entity и нормы.
4. Настоящий TOOL_RESPONSE внутри assistant-turn отвергался по actor. Это
   отдельный технический дефект. В сохранённой H3-фазе его исправление само
   по себе **не возвращает TP**: единственный MISMATCH имеет и другую ошибку.
5. Технические отказы, неполное покрытие и повторные receipts смешивались с
   бинарными решениями. Сохранённые 66 H3 строк не подтверждают заявленные 77
   call rows. Ошибку Qwen и отказ обработки следует измерять раздельно.

Production-parser контрпримеры и независимый code review:
`tests/test_qwen_binding_boundaries.py`, `CODE_REVIEW.md`.

## Исправленная фаза

Отдельная ветка `fix/qwen-binding-contracts-20261008`, от `51160fcd`.
Исторические gold, outputs, отчёты и `src/guardian_truth` не менялись.

- A/B/C сохраняются как `HYPOTHESIS`, без права менять итог. Старый OR можно
  воспроизвести только через явно названный `--historical-unsafe-or`.
- H3 проверяет точный current argument/path, case-sensitive значение, точные
  цитаты, локальную схему и source kind. Успех называется
  `SOURCE_SUPPORTED_MISMATCH`; binding/applicability остаются unresolved.
- Невалидные/незавершённые ответы не становятся binary 0. Missing IDs и
  conditional F1 видны; дополнительно считаются неизвестные positives/negatives,
  UNKNOWN→0 projection и границы полного результата.
- Conflicting duplicate receipts не выбираются молча. Нормальный duplicate
  cache receipt не считается независимым модельным повтором.
- Новый runner пишет в `guardian_binding_contract_v2`, фиксирует входы/config,
  сохраняет per-row технические отказы и проверяет полный expected inventory.
  Общий process lock и fsync reservation до dispatch ограничивают попытки,
  включая abandoned/cache calls. Старые фазы не возобновляются как новые.

**Это исправление достоверности обработки, не прирост F1.** Относительно
unsafe ABC OR шесть добавленных TP больше не являются решающими. Они сохранены
как кандидаты, ожидающие настоящего semantic binding checker. Относительно
базового Qwen решения не меняются. Числовые/сложные argument values пока
не поддержаны H3 admission; отсутствие проверки не объявляется корректностью.

## Куда направить улучшение Qwen

Цель следующей фазы — повысить качество, а не остановиться на quarantine.
Проверить extraction без знания использованного значения: модель получает
политику, историю, декларацию операции и названия её аргументов, но не их
текущие значения. Она независимо выбирает запрошенную сущность и адресованные
значения. Код сравнивает точные leaves с текущим вызовом; отдельная проверка
семантики устанавливает применимость, допустимые альтернативы, изменения
атрибутов, chronology и exceptions. Так можно проверить anchoring, из-за
которого прежний H3 объявлял чужую линию MATCH.

Контроль — равный бюджет прежнего visible-arguments H3/повторного reviewer.
Сначала oracle relation ceiling и короткий диагностический пилот с lawful
contrasts, затем полный valid46 и доступные наборы, новое task-separated
испытание и несколько повторов. Один telecom gain не достаточен.

Планы и результаты дальнейшего улучшения сохраняются отдельными фазами.
Default/production меняется только после сопоставимого измерения.
