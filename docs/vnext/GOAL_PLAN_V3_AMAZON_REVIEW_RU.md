# Goal/Plan v3: что переносим из Amazon

Статус: обзор и проектирование. Goal v2 завершён: **22/22 UNRESOLVED**.
Его код, замороженные входы и результаты не изменяются. Реализация v3 — только
после завершения текущего Policy-прогона и его полного аудита.

## Разделение источников

[SOP-Bench](https://github.com/amazon-science/SOP-Bench) — набор процедурных задач
с исполняемыми mock-инструментами и эталонными результатами. Полезна идея
независимого исполняемого эталона, а не переноса одной последовательности действий
на произвольную пользовательскую цель. У репозитория указана лицензия CC-BY-NC-4.0:
перед заимствованием данных или кода отдельно проверяем условия использования.

[Behavioral Contract Evaluations](https://github.com/aws-samples/sample-agentcore-behavioral-contract-evaluations)
— демонстрационный детерминированный проверяющий код для заданных контрактов.
Берём условные ограничения, независимый проверяющий модуль и версионированный
пакет доказательств. AWS-развёртывание для этого не требуется.

Важное предостережение: генератор из golden session превращает увиденные шаги
и порядок в требования. Для Guardian это только предложения, не авторитетный
контракт. Несколько совпавших трасс тоже не доказывают обязательность процедуры.

## Основная проверка v3

Проверяем соответствие **текущего действия** цели и разрешённым изменениям,
а не совпадение с предполагаемым планом. Один смысл цели допускает несколько
инструментов и путей. Отдельно храним четыре класса:

- действие непосредственно соответствует цели;
- допустимое вспомогательное действие;
- соответствие неоднозначно;
- доказанное нарушение области задачи или ограничений.

Обязательный порядок появляется только из USER/SYSTEM/POLICY с подтверждённой
обязательностью. Вызов, успешное получение данных, завершение операции и её
эффект — разные предикаты. Название инструмента не доказывает его семантику.

## Защита условных правил

Guard должен иметь источник, сущность, допустимую версию и временную область.
Нельзя выбрать удобный старый ответ или другую сущность. Факт USER означает
содержание запроса/утверждения, но не автоматически истинное внешнее состояние.

TRUE активирует правило; FALSE отключает только его; UNKNOWN сохраняет варианты;
BOTH фиксирует конфликт. Пропущенная проверка не даёт FALSE. Безусловное
предусловие защищает от обхода только когда оно действительно задано источником.

Допустим trigger «при попытке изменения нужна проверенная личность»: действие
определяет применимость запрета, но не даёт агенту самостоятельно выбрать исключение.

## Доказательства и границы

Один независимый доказанный запрет достаточен для ERROR, даже при посторонних
UNKNOWN. Но неизвестная применимость или исключение именно этого запрета
блокирует доказательство. Нарушение должно сохраняться во всех существенных
трактовках; «хоть одна трактовка дала ERROR» недостаточно.

Для NO_ERROR требуется полнота существенных проверок. PASS отдельного контракта
не доказывает правдивость ответа и общую безопасность. На префиксе нельзя
объявить отсутствующим шаг, срок которого наступает только в будущем.

Пакет доказательств включает требование и исходный span, версию/хеш контракта,
цель и действие, все существенные привязки, guard/исключение, найденное и отсутствующее
с границами полноты, свидетельство нарушения и оставшиеся неизвестности.
