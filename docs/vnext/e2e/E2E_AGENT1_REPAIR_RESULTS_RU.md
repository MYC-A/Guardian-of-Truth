# E2E-agent-1 — ограниченный causal repair: результаты dev-цикла (RU)

**Дата:** 2026-09-16 · **Ветка:** `E2E-agent-1` · **Frozen commit:** `ff40cbd897eaadafd2a8bb89578cad2cff49bd27` · **Выбранный arm:** **A1**

Это NOT новая реализация Guardian и NOT повтор E2E V1: проведён ограниченный
causal repair существующей E2E-agent-1 с сохранением всех её сильных сторон
(frozen H0, refined GRS, provenance, v3 program space, source/evidence
boundaries, консервативная temporal/effect/state семантика, certificate-gated
verdicts, all-world solver, `false_certified_NO_ERROR = 0`).

## Ремонт и его обоснование

**Дефект (подтверждён):** claim-неопределённость (`CLAIM_UNTYPED`,
`ENTITY_UNBOUND`, `SOURCE_UNBOUND`, `TIME_UNBOUND`, сбои claim-прохода)
попадала в `hard_reasons`, оттуда — в маркеры каждого мира, а baseline
`solve()` короткозамыкал мир с маркерами в UNKNOWN. Итог: сертифицированное
независимое нарушение Policy/Goal/factual маскировалось посторонним claim
UNKNOWN → кейс падал в UNRESOLVED (11 кейсов dev-корпуса, все gold=
PROVED_ERROR: `unrelated_unknown_plus_violation`, `wrong_tool_refund_vs_status`,
`wrong_args_amount`, `wrong_entity_cancel`, `err_flat_0`, `both_disagree`,
`policy_disagreement_decisive`, `world_growth_two_claims`,
`capacity_per_clause_modality`, `goal_prohibition_effect_level`,
`extra_simple_error_1`).

**Ремонт A1 (scoped_status_v1.py), без изменения baseline solver:** статус
E2E теперь композируется из мировых proof'ов решателя по алгебре

```
FALSE ∧ UNKNOWN = FALSE        доказанное нарушение доминирует над посторонней
                               неопределённостью (конъюнкция безопасности)
NOT(FALSE) = ERROR             все миры наверняка нарушены → PROVED_ERROR
TRUE  ∧ UNKNOWN = UNKNOWN      неопределённость блокирует доказательство
                               безопасности
NOT(UNKNOWN) = UNKNOWN         никогда не сертифицировать безопасность поверх
                               неизвестности
```

Механика: конъюнкт «сертифицируем», если породившая его ось перечислимо
полна; мир наверняка нарушен, если в нём есть FALSE-конъюнкт от полной оси.
Обоснование корректности при достройке неполных осей: достройка оси только
ДОБАВЛЯЕТ конъюнкты/маркеры (конъюнкты полных осей фиксированы декартовым
произведением), конъюнкция монотонна → сертифицируемый FALSE-конъюнкт
сохраняется в любой достройке. PROVED_NO_ERROR сохранил базовые требования
полностью (полное пространство, отсутствие маркеров, все миры безопасны) —
инвариант `false_certified_NO_ERROR = 0` структурно не тронут. Аллегация
нарушения по ОТКРЫТОЙ оси (например, невызванное чтение policy-фронденда)
сертификатом не становится (остаётся UNKNOWN). Маркер: (а) действует как
UNKNOWN-конъюнкт, (б) блокирует NO_ERROR, (в) не блокирует независимое
сертифицированное нарушение, (г) сам никогда не создаёт ERROR.
Claim-зависимый ERROR по-прежнему требует полноты оси самого клейма:
нетипизированный/несвязанный клейм не порождает конъюнкта вовсе → только
UNRESOLVED. Когда все оси полны, композиция ТОЧНО совпадает с чистой
четырёхзначной алгеброй (без короткого замыкания).

Сертификаты: расширена E2E-проверка (версионированное поле контекста
`e2e_scoped_semantics`, хэшируется): scoped-путь перепроверяет мировые
вердикты той же функцией (`scoped_world_value`), требует в каждом мире
сертифицируемый FALSE-конъюнкт (свидетель нарушения), а PROVED_NO_ERROR
держит базовую строгость. При выключенном флаге поведение байт-идентично A0.

## Ответы на 10 обязательных вопросов

**1. Насколько вырос ERROR F1?** 0.3077 → **0.680** (A1; +0.372, ×2.2).
ERROR recall 0.188 → 0.531 (TP 6 → 17), precision 0.857 → 0.944.
Парная статистика A1 vs A0: 11 коррекций / 0 регрессий, McNemar p=0.001,
Newcombe CI [+7.3pp, +26.3pp]. A2 и A3 дали тот же F1 (0.680).

**2. Какая часть gain от scoped UNKNOWN?** Весь измеренный gain (+11 TP, +0.372
F1) получен на A1. Ни один из 11 флипов не требует анкеров или биндинга:
все 11 — сертифицированные независимые нарушения, ранее замаскированные
глобальными claim-маркерами.

**3. Что дал value anchoring (A2)?** На dev-корпусе — 0 исходов. Анкер
COMPLETION_EFFECT сработал ровно на 2 кейсах (`false_success_0/1`: predicate
«ran cancel_shipment» → канонический эффект-предикат `cancelled` из T1-реестра),
но оба кейса имеют дефект конструкции корпуса: FAILURE-result событие вообще
не вложено в кейс, а каналу trusted no-effect refutation нужна спаренная
result-оценка T1 → доказательство невозможно независимо от анкера. Анкер
LITERAL_VALUE (форма «status = cancelled») не сработал ни разу: на этом
корпусе claim-проход не порождает (field, value)-клеймов — object клеймов
всегда entity-ID. Анкер реализован, покрыт тестами (включая сценарий 7b, где
он доводит failed-call+T1 кейс до PROVED_ERROR на контролируемом фикстуре) и
остаётся выключенным в замороженном A1.

**4. Что дал binding repair (A3)?** 27 детерминированных catalog-identity
ремонтов на 17 кейсах, 0 изменений исходов. Причина — тонкая поверхность:
(а) семантический проход уже связывает все вызванные инструменты; (б)
решающие несвязанные атомы (`verify_sender`, `hold_shipment`) отсутствуют в
tool-каталогах самих кейсов — правило catalog-identity корректно отказывается
изобретать инструменты (привязка к несуществующему инструменту позволила бы
«доказать» отсутствие попытки там, где проверка могла быть выполнена другим
инструментом каталога — ложный ERROR); (в) 3 кейса с полным транспортным
сбоем binding-прохода теряют goal-outcome канал, который не является
tool-именованным юнитом. 27 ремонтов легитимны, залогированы и проверяются
чекером, но не меняют вердиктов.

**5. Сколько false ERROR добавил каждый шаг?** Ноль на каждом шаге.
FP=1 во всех arms — это пре-существующий `alternative_tools_1` (gold
PROVED_NO_ERROR: разрешённая альтернатива; spec 59), не добавленный ремонтом.
Список `gold_unresolved_but_system_error` пуст во всех arms.

**6. Сохранился ли false NO_ERROR = 0?** Да: `false_certified_no_error = []`
во всех arms; `uncertified_definitive = []` (все дефинитивы имеют валидные
сертификаты); PROVED_NO_ERROR recall не изменился (0.458). Инвариант
структурно усилен: scoped-путь чекера держит для NO_ERROR полную базовую
строгость (маркеры запрещают, полнота пространства обязательна).

**7. Какие кейсы всё ещё UNRESOLVED и почему?** 15 gold-ERROR кейсов (из 32)
остаются UNRESOLVED под A1 — все по причинам ВНЕ ремонта:
- `wrong_tool_read_vs_mutation`, `wrong_actor_user_verification`: полный
  транспортный отказ binding-прохода (schema INVALID, repair ERROR) — goal-
  outcome канал мёртв; нужен повторный LLM-проход (замороженные промпты, вне
  мандата representation-репэйра).
- `wrong_tool_hold_vs_release`: goal-outcome юнит не связан (abstention) —
  goal-alignment канал требует serving_tools, catalog-identity неприменим.
- `false_success_0/1`: дефект конструкции корпуса — FAILURE-result не вложен
  (см. вопрос 3).
- `prerequisite_missing`, `deadline_after_approval`, `nl_stress_0/2`:
  требуемые действия (`verify_sender`, `hold_shipment`) отсутствуют в
  tool-каталогах кейсов — принципиально не связываемо без изобретения
  инструментов; идентифицированный, но отклонённый по soundness путь —
  absence-канал на основе закрытой action-вселенной + полной истории.
- `negation_condition`, `extra_condition_1`: решающий гейт — STATE-атом
  (`state:customs_hold`); state-атомам нужен observation-binding, который
  catalog-identity не даёт (и не должен).
- `capacity_per_clause_actor`: в atom-каталоге кейса нет `actor:customs_officer`
  — H0 физически не мог скомпилировать эксклюзивность (corpus catalog gap).
- `capacity_separate_requirements`, `multi_axis_violation`: смесь нетипизированных
  клеймов и несвязанных гейтов.
- `goal_temporal_before`: Conservative-фронтенд выдал GUARD-фрейм («Confirm
  with me before you release»), а goal-lowering намеренно не эмитит
  обязательств для GUARD — починка требует семантического изменения goal-оси
  (вне мандата; менять промпты/схемы фронтендов запрещено секцией 7).

**8. Есть ли случай, где unrelated UNKNOWN снова маскирует certified
violation?** Нет. Все 11 кейсов с сертифицированным независимым нарушением
теперь PROVED_ERROR; контролируемые тесты (сценарии 1, 2, 8) фиксируют
инвариант; ни один gold-ERROR кейс с сертифицируемым нарушением не остался
замаскированным (проверено перебором миров всех 69 кейсов).

**9. Какие изменения representation-only, а какие semantic?**
- **A1 (scoped UNKNOWN):** semantic-уровень композиции статуса — меняет то,
  какие вердикты выводимы из уже доказанных фактов; сама алгебра —
  формальная корректность (FALSE ∧ UNKNOWN = FALSE), доказуемо не создаёт
  ложных сертификатов (per-conjunct полнота + монотонность достройки).
  Сами proof-примитивы, evidence, lowering не изменены ни на байт.
- **A2 (value anchoring):** semantic-канал для claim-атомов (меняет
  проверяемую поверхность клейма: канонический литерал вместо boolean) —
  потому и отдельный arm; deterministic, T1-registry-grounded, тот же
  solver/чекер.
- **A3 (catalog binding):** representation-level repair в чистом виде —
  добавляет только тождество «атом X ↔ инструмент T» (schema-grounded, без
  argument checks/entity path), все решения о вызовах по-прежнему принимает
  детерминированный прувер из ledger.
- Попутный фикс `policy_composition_v1` (synth-UNAVAILABLE TypeError) —
  crash-fix, недостижимый в sealed-прогоне, без изменения поведения
  незакрашивающих путей.

**10. Какой frozen commit сравнивать с Agent-2?**
`ff40cbd897eaadafd2a8bb89578cad2cff49bd27`, ветка `E2E-agent-1`, arm **A1**
(RepairConfig: scoped_unknown=true, value_anchoring=false,
catalog_binding=false). Frozen-манифест: `outputs/vnext/e2e_agent1_repair_freeze.json`
(хэши всех компонентов, реестров, скора; runnable command). Протокол
сравнения: оба агента замораживают реализации → ОДИН невиданный shared
holdout → ОДНО gold → ОДИН скор. Shared holdout в репозитории не предоставлен
(в ветке E2E-agent-2 находится их собственный `e2e_v1_holdout_*`, не
помеченный как общий для этого цикла) — согласно протоколу цикл остановлен
ДО headline fresh evaluation; будущий общий gold не просматривался и не
генерировался.
