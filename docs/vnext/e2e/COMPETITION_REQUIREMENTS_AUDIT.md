## 2. Что является входом (дословно, правила PDF, «Формат входных данных»)

> Каждый пример – это один текст из двух блоков, обёрнутых в теги:
> `<prompt> … </prompt>` – полный контекст, который видел агент перед своим ответом: системная инструкция (правила и доступные данные/метаданные), запрос пользователя, а также предыдущие вызовы инструментов и их результаты;
> `<response> … </response>` – ответ агента, который нужно проверить.

Внутри блоков — единый текстовый транскрипт со специальными маркерами в скобках `⟦…⟧`:

| Маркер | Значение |
|---|---|
| `⟦SYSTEM⟧` | системное сообщение агента (правила + контекст/метаданные) |
| `⟦USER⟧` | сообщение пользователя |
| `⟦ASSISTANT⟧` | сообщение агента (рассуждение / текст) |
| `⟦ASSISTANT_TOOL_CALL name="X"⟧` | вызов инструмента X агентом; ниже идут его аргументы (JSON) |
| `⟦USER_TOOL_CALL name="X"⟧` | вызов инструмента X пользователем (при наличии у пользователя собственных инструментов) |
| `⟦TOOL_RESULT name="X" requestor="assistant\|user"⟧` | результат инструмента X; атрибут requestor указывает, кто его вызывал |

> Содержательную часть ответа нужно искать и в тексте `⟦ASSISTANT⟧`, и в самом вызове инструмента (его типе/названии), и в его аргументах.

**Режим черного ящика** (дословно): «ему доступен только текст входного контекста и текст ответа агента – без доступа к весам, внутренним состояниям или скрытым рассуждениям проверяемой модели».

## 3. Что считается галлюцинацией (дословно, правила PDF)

> Галлюцинация – утверждение или действие в ответе, которое не обосновано контекстом. Различаем два механизма:
> — Противоречие (contradiction) – ответ противоречит контексту (данным, инструкции, результатам инструментов) так, что итог становится неверным. Типичные случаи: число / дата / значение / имя в ответе не совпадает с данными из контекста; ссылка на сущность, поле или значение, которых нет в предоставленных данных, либо их искажение; нарушение обязательного правила из инструкции, из-за которого результат искажается.
> — Неподкреплённость (unsupported) – утверждение в ответе не выводится из контекста (выдуманный факт, число, причина, сущность или условие), хотя напрямую ничему не противоречит.
> В рамках задачи рассматриваются оба типа контекстных галлюцинаций… Наличие любого из них означает, что галлюцинация есть (метка `1`).

Что НЕ считается галлюцинацией (дословно, сокращения только в перечислениях):
- корректный пересказ, агрегация, фильтрация и сортировка данных из контекста;
- округление, форматирование, перефразирование без смены смысла;
- неточные формулировки во внутреннем рассуждении агента при верном итоговом результате (оценивается результат действия, а не выбор слов);
- служебные / вторичные поля вывода, которые не доходят до пользователя.

> Критерий-тест для спорного случая: «Изменит ли это итог или данные, которые увидит пользователь?» Если да или потенциально да – галлюцинация. Если очевидно никогда – не галлюцинация.

## 4. Колонки test/valid (дословно)

Каждый пример: `id` (str, идентификатор запроса), `prompt` (str, входной контекст), `response` (str, ответ модели), `label` (int: 0 – галлюцинации нет, 1 – есть). В публичном датасете дополнительно `explanation` (str, текстовое объяснение метки).

Публичный development-файл олимпиады в репозитории: `valid.parquet` (ветка E2E-agent-2). Платформенный запуск передаёт **CSV**: `--input <path_to_test.csv>`. Приватный тестовый датасет колонок `explanation`/`label` для инференса не раскрывает.

## 5. Формат submission (дословно, правила PDF + страница задачи)

> Решение оформляется как Docker-образ – архив со структурой:
> ```
> root/
> ├── README.md            (опционально)
> ├── pyproject.toml
> ├── model/               (веса, конфиги, словари токенизатора и т.д.)
> ├── src/
> │   └── your_module/
> └── scripts/
>     └── predict.py       (точка входа: инференс на тестовом датасете)
> ```
> Запуск решения платформой:
> ```
> pip install.
> python scripts/predict.py --input <path_to_test.csv> --output <path_to_predictions.csv>
> ```
> На выходе – файл с колонками `id`, `label` (предсказанный бинарный флаг по каждому ответу).

## 6. Метрика (дословно)

> Оценка проводится на уровне ответов (response-level) по совпадению предсказанного бинарного флага с эталонной меткой `label`:
> Response F1-score – основная метрика (больше – лучше);
> Response Precision – больше – лучше;
> Response Recall – больше – лучше.
> Итоговое ранжирование строится по Response F1-score.
