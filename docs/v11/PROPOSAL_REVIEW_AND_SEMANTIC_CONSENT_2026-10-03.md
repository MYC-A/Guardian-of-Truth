## 2. Исходный диагноз во вложении нужно исправить

**84 — число проверенных вызовов, а не число независимых сценариев.**
`witness_coverage_before_api.json` измеряет только свидетель подтверждения.
В нашем исправленном свидетеле все 84 дают UNKNOWN, поскольку в естественном
диалоге не найден полный явный сертификат операции и её параметров.

В этом пути нет солвера, доказывающего `RequiredAction(A)`. Код разбирает
последовательность «описание действия → ответ пользователя → текущий вызов».
Ему нужно доказать, **что именно подтвердил пользователь**, а не необходимость
действия. Переход к проверке допустимости аргументов не отвечает на этот вопрос.

Например, проверяемая peer-версия разрешает `amount=999` после согласия на
`amount=2`, если ID совпадает. Вопрос «запись X уже закрыта?» → «нет» она
принимает за отказ от модификации X. Это ошибки смысловой привязки.
Строгий UNKNOWN в этих случаях предотвращает недоказанное решение, но нулевое
покрытие свободной прозы действительно остаётся проблемой.

## 3. Полезные части предложения и границы их применения

| Предложение | Решение | Что проверено / что остаётся |
|---|---|---|
| Восстанавливать цитаты с другими пробелами и переносами | Принято в следующем прототипе | Три сохранённые GPT-цитаты содержат двойное экранирование `\\n`. Они восстановлены до точного исходного span без изменения слов |
| Разделить синтаксис вызова, наблюдение и состояние диалога | Принято как ограничение lowering | Диалоговая обязанность не проходит как `args.id exists`; в OR требуемый тип свидетельства обязателен в каждой альтернативе |
| Разделить tool-call и свободный текст | Поддерживаю | Факт выполнения, обещание, просьба пользователю и отказ требуют разных проверок. Отсутствие tool-call не доказывает правильность текста |
| Сохранять несколько состояний результата | Поддерживаю с иной трактовкой | `NO_VIOLATION_OBSERVED` полезно в трассе, но не должно превращаться в NO_ERROR всего ответа |
| Привести все значения к lowercase-строке | Отклонено | Сливаются строка `"105"` и число `105`, `null` и пустая строка, `"true"` и `true`, разные регистры ID |
| Проверять значения по общему историческому pool | Отклонено | Pool не хранит владельца, родителя, момент времени, роль источника и связь с операцией |
| Отсутствующий в pool внешний ID считать выдуманным | Отклонено без явного контракта источника | Новый допустимый ID может ещё не встречаться; отсутствие наблюдения само по себе не доказывает запрет |
| При чистой схеме и известных параметрах снимать UNKNOWN | Отклонено | Пользователь мог отказать, срок мог истечь, обязательное правило могло не попасть в таблицу |

Нормализатор из вложения также нужно сузить: `IGNORECASE`, снятие кавычек и
выбор первого вхождения уничтожают часть свидетельства. Реализация сохраняет
регистр, пунктуацию и кавычки, отказывает при нескольких вхождениях, включая
перекрывающиеся, возвращает точный исходный текст и записывает вид преобразования.
Исправление орфографии или парафразы не принимаются.

Разделение scope предотвращает конкретный класс подмен. Оно не доказывает,
что модель правильно классифицировала само правило. У старых ответов без
`required_scopes` тип не дорисовывается; текущий frozen prompt его не требует.
Этот gate действует при явно заданном scope и ещё не является проверенной
автоматической типизацией всех политик.

## 4. Контрпример к BOUNDED_ADMISSIBLE

В обеих историях пользователь ранее назвал X и сумму 2. Инструмент `apply_a`
разрешён, схема параметров верна, вызов одинаков:

```text
assistant: Confirm apply_a: {"record_id":"X","amount":2}?
user: Yes   /   No
assistant: TOOL_CALL apply_a {"record_id":"X","amount":2}
```

Предложенные schema/provenance-инварианты одинаково проходят в обеих историях.
Но требование согласия выполнено только в первой. Если это правило осталось
UNSUPPORTED или не попало в таблицу, rescue ошибочно объявит второй вызов
ADMISSIBLE. Поэтому отсутствие нарушения **проверенной части** политики не
доказывает отсутствие нарушения **всей** политики.

Для такого вывода нужен отдельный сертификат полноты применимых правил,
смыслового перевода, всех проверяемых фактов и исключений. Пока его нет.
Даже TRUE по одному условию доказывает только это условие, а не весь ответ.

Другой воспроизведённый контрпример: цель — родитель X и дочерний I,
наблюдение — родитель Y с дочерним I. Peer TARGET выбирает I из Y, получает
FALSE и выдаёт finding; атом проходит admission. Pool значений это не исправит,
поскольку I действительно известен. Нужна совместная привязка X и I к receipt.

## 5. Практический путь к увеличению покрытия

### Следующая версия: механический admission

Нормализатор цитат, безопасный default пустого списка только для явно
NOT_APPLICABLE, scope-gate и regression-контрасты реализованы отдельно от
запущенного frozen опыта. Старые ответы и результаты не переписываются.
Артефакт восстановления трёх цитат:
`outputs/searh_23/v11/proposal_review/citation_repair_replay.json`.
Это восстановление источника, не доказательство полноты ledger или улучшения F1.

### Следующая проверка: смысловая запись подтверждаемого действия

Прототип `semantic_consent.py` просит модель извлекать запись:

```text
(роль исполнителя, операция, параметры, цитата действия,
 источники параметров, позиция описания)
```

Модель рассматривает описание и предшествующие события, декларации инструментов
и текущую цель. Код проверяет роли, порядок, полноту инвентаря описаний, реальные
цитаты и типизированные значения, затем сравнивает запись с текущим вызовом.
Нельзя переносить аргументы текущего вызова назад в предложение агента.
Ответ пользователя проверяется целиком, а не по одному найденному «да».

Прототип остаётся **SHADOW / `code_proof:false`**. Наличие правильных слов и чисел
в цитате не доказывает смысловую связь: две модели всё ещё могут одинаково
перепутать вопрос о факте с разрешением действия. Совпадение разных моделей
проверяется по всей записи, а не только по TRUE/FALSE. На API этот новый
прототип в рамках данной оценки не прогонялся.

Полезные контрасты для отдельного freeze: да/нет на одну операцию; вопрос о
факте; изменённая сумма; другая операция; другой родитель; условное обещание;
цитируемое согласие; противоречивый ответ; промежуточный вызов или новая реплика.
Разметка относится к подтверждению конкретной операции, не ко всему ответу.

### Критерий улучшения детектора

Не требовать UNKNOWN < 5 как самоцель: этого легко достичь недоказанным
NO_ERROR. Считать отдельно правильные TRUE/FALSE, ошибочно решённые случаи,
UNKNOWN и затем TP/FP/FN/TN детектора на прежнем замороженном replay.

Порог F1 > .7556 из вложения недостаточен: текущий baseline
TP15/FP0/FN8/TN23 имеет F1 = .78947 при ERROR как положительном классе.
Сохраняется содержательный критерий V11: минимум два новых найденных пропуска
без новых FP. Результат на известных политиках не объявляется переносом.
Случайный UUID не становится ERROR без доказанного ограничения источника ID;
мутации даты требуют применимого правила и исключений.

## 6. Проверка и состояние реализации

Повторно выполнен набор из 10 связанных test-файлов: **234 passed**.
Это не полный `pytest tests/`, не проверка модельного качества и не public46.
`scripts/predict.py` и сервис не менялись.

```powershell
$env:PYTHONPATH='src'
python -X utf8 -m pytest tests/test_policy_table_v11_semantic_consent.py tests/test_policy_table_v11_proposal.py tests/test_policy_table_v11_obligations.py tests/test_policy_table_v11_rescue.py tests/test_policy_table_v11.py tests/test_policy_table_v11_confirmation.py tests/test_policy_table_v11_measure.py tests/test_policy_table_v11_transport.py tests/test_policy_table_eval.py tests/test_compile_agreement.py -q --tb=short
```

**Решение:** переносить нормализатор, типизацию и запись действия; автоматическое
снятие UNKNOWN через чистую схему и общий pool не переносить. Именно проверка
смысловой привязки и полноты правил остаётся следующим измеряемым шагом.
