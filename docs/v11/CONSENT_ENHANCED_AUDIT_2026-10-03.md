# Проверка свежего consent_enhanced: реального покрытия пока нет

Проверен свежий commit `2087b08849590c114a82834d020a1ea9cfa9fe2c` ветки
`research/v11-universal-rescue-20261003`. Аудит сделан в отдельной рабочей
копии; код автора, predictor и ранее замороженные алгоритмы не изменялись.
Все проверки локальные, **0 новых API-запросов**.

## Что действительно получилось

Автор исправил конкретную ошибку: английское `to X` больше не заполняет
одновременно `record_id`, `account_id` и `item_id`. На коротком примере
`Confirm applying amount 2 to X? → Yes` восстанавливаются нужные аргументы.
Также сохранено согласие перед дословным повтором описания действия. Это
полезные локальные результаты; задачу понимания произвольного предложения
операции они не закрывают.

## Проверка неизменённых реальных входов

Использован прежний frozen inventory, с проверкой source hashes. Применимость
19 вызовов взята из уже существующей ручной source-only аннотации, новая
разметка detector не открывалась.

| Свидетель согласия | TRUE | FALSE | UNKNOWN |
|---|---:|---:|---:|
| Старый strict witness, все84 вызова |0|0|84|
| Новый enhanced, все84 вызова |0|0|84|
| Старый strict witness, применимые19 |0|0|19|
| Новый enhanced, применимые19 |0|0|19|

Во всех случаях причина enhanced — `no_complete_action_certificate`.
Следовательно, свежий regex-парсер не исправил отсутствие покрытия на
реальных диалогах. Это проверено прямым вызовом новой функции, а не только
штатного witness: отсутствие интеграции не объясняет этот нулевой результат.

## Почему считать его универсальным нельзя

В native формате `⟦SYSTEM⟧`, `[AVAILABLE TOOLS]`, `⟦ASSISTANT⟧`,
`⟦USER⟧`, `→ TOOL_CALL` проверены короткие диагностические контрасты.
Код отдельно проверяет, что каталог распознан и в каждой строке есть ровно
один реальный native target. Это исследовательские контрпримеры после
просмотра реализации, а не слепой benchmark; метки относятся к согласию,
не к правильности всего ответа.

Во всех строках ниже пользователь отвечает `Yes`, а целевой вызов —
`apply_a(record_id="X", amount=2)`, кроме первой строки с `amount=999`.
Enhanced во всех семи случаях выдаёт **RESOLVED TRUE**, хотя текст не
устанавливает безусловного согласия на эту полную операцию ассистента.

| Предложение/вопрос агента | Что потеряно |
|---|---|
| `Confirm applying to X?` — вызов с999 | Сумма вообще не предложена |
| `Confirm applying amount 2 to X-7?` | `X-7` обрезан до `X` |
| `In your browser, apply amount 2 to X. Confirm?` | Выполнять должен пользователь |
| `Do not apply amount 2 to X. Confirm?` | Подтверждение запрета стало разрешением |
| `If external approval arrives, apply amount 2 to X. Confirm?` | Условное согласие стало безусловным |
| `Did you already apply amount 2 to X?` | Ответ о факте стал разрешением действия |
| `Confirm executing inspect_b for record_id X and amount 2?` | Согласие на чтение стало согласием на изменение |

Причины в коде:

1. `consent_enhanced.py:297`: для natural_nl достаточно, чтобы **найденная
   часть** arguments совпадала с target. Ненайденные параметры фактически
   объявляются согласованными. Это ослабление доказательства, не устранение
   несущественной ошибки формата.
2. `consent_enhanced.py:65`: `to (\w+)` извлекает только префикс ID до дефиса.
   Этот дефект воспроизводится даже в собственном `joined_ID_right` автора.
3. `consent_enhanced.py:168`: общий глагол `execute/apply/run` подходит к
   **первому инструменту каталога**. Описание эффекта выбранного инструмента
   не сопоставляется с действием. При перестановке двух неизменённых
   деклараций вердикт меняется TRUE → UNKNOWN на одинаковом диалоге.
4. `consent_enhanced.py:183`: знак `?` или слово `confirm` делает текст
   запросом действия без проверки отрицания, исполнителя, условности и роли
   вопроса. Поэтому просьба проверить условие снова смешивается с действием.

## Что означает опубликованное 11/17

`python tests/test_enhanced_integration.py` воспроизвёл **11/17**, exit1.
В собственном `joined_ID_right` исходный UNKNOWN заменён ошибочным
TRUE: обсуждается X-1, вызывается X. В `changed_amount_description_after_yes`
вердикт FALSE отличается от ожидаемого автором UNKNOWN; это расхождение с
консервативным контрактом теста, само по себе не доказательство ложной
конкурсной тревоги.

У трёх из17 строк expected хранится строкой (`TRUE`/`UNRESOLVED`), а скрипт
сравнивает его со списком `[status, value]`. Два совпавших UNKNOWN поэтому
помечаются FAIL. Кроме того, эти три строки пришли из другого witness-опыта.
Нельзя интерпретировать11/17 как универсальную точность согласия.

Файл `test_enhanced_integration.py` не содержит собираемых pytest тестов:
`pytest --collect-only` вернул `no tests collected`. Его `main` запускается
только вручную. Прохождение общего pytest не проверяет новую функцию этим
набором. В runtime `witness.py` по-прежнему импортируется исходный
`consent.explicit_confirmation`; enhanced используется только этими двумя
debug/integration скриптами.

## Что перенести и что доработать

- Повтор описания после согласия разрешать только для той же операции и
  **полного типизированного набора** параметров. Саму идею сохранения
  подтверждения при таком повторе использовать можно.
- Неполный NL-разбор оставлять кандидатом/UNKNOWN. Не заполнять отсутствующие
  поля из будущего вызова и не применять subset-match для TRUE.
- Операцию связывать с effect/actor и полным предложением. Вопрос о факте,
  инструкция пользователю и действие ассистента должны иметь разные роли.
- Scope ответа пользователя проверять для конкретной операции: общий `Yes`
  на сущность не переносить на вторую операцию/новые параметры.
- Проверять одинаковый результат при перестановке деклараций. Полный набор
  контрпримеров выше пригоден для регрессии следующей версии.

Нужен отдельный измеренный model/source рукав либо существенно ограниченная
формальная грамматика. Добавление очередных action-слов не решает неоднозначную
привязку инструмента и параметров. Наша frozen модельная версияV3 уже дала
TRUE3/19, но тоже остаётся shadow: две модели могут одинаково ошибиться, а
дословная поддержка значения ещё не доказывает правильную роль этого значения.
