# Идея подхода и проверка формата контрпримеров

Дата: 2026-10-03. Проверяется `prod/phase1-admissibility-20261003@1183409c`.
Дополнение к [первому аудиту](PROD_ADMISSIBILITY_REVIEW_2026-10-03.md).
Runtime ветки не менялся. Все проверки этого дополнения выполнены без API.

## Оценка самой идеи

**Направление стоит развивать.** Полезная архитектура здесь — выбор короткой
применимой проверки, привязка фактов к действию/сущности, вычисление кодом и
сохранение источников результата. Чтобы доказать конкретную ошибку, не требуется
сначала формализовать все пункты политики. Можно искать доказуемые нарушения
частями и постепенно расширять покрытие.

Проверка полезности теперь сильнее простого сравнения aggregate F1:

| Сохранённый рукав | TP | FP | FN | TN | F1 |
|---|---:|---:|---:|---:|---:|
| Старый direct + структурные проверки | 15 | 0 | 8 | 23 | .7895 |
| Новый gate без таблиц | 19 | 0 | 4 | 23 | .9048 |
| OR старого и нового рукавов | 19 | 0 | 4 | 23 | .9048 |

Новый gate сохраняет **все 15** положительных решений старого рукава и добавляет
четыре: `airline__7::t6`, `retail__36::t10`, `airline__8::t7`,
`banking_knowledge__task_005::t6`. Это воспроизведение сохранённых ответов и кодовых
проверок, без новых запросов к моделям. Gold использован автоматическим aggregate
scorer. Алгоритм по результатам этого сравнения не менялся.

Такой выигрыш поддерживает дальнейшую работу над направлением. Правила выбирались
на development public46, поэтому этих цифр недостаточно для заявления о переносе.
Найденные контрпримеры задают конкретные требования к исправлению реализации.

### Уточнение предыдущего вывода об ADMISSIBLE

Для конкурсного **бинарного детектора** обычная стратегия — вернуть 0, когда
доступные проверки не нашли нарушение. Сам по себе такой fallback не является
дефектом архитектуры. Отчёт должен показывать, какие требования остались непроверены.

Для **допуска выполнения действия** тот же fallback имеет другой контракт:
он не удостоверяет обязательное согласие. Наличие режима STRICT и ответа ALLOW
при unresolved mandatory atom остаётся ошибкой enforcement. В прошлом ответе
риски разрешающего gate и полезность конкурсного детектора были недостаточно
разделены. Это не основание отбрасывать весь подход.

## Какие тесты действительно прошли

- 276 тестов из репозитория проверяют предусмотренные автором сценарии; они проходят.
- public46 — реальные предоставленные диалоги; детектор находит19 из23 ошибок.
- Наши контрпримеры — дополнительные проверки корректности отдельных правил.
  Они не являются новым размеченным конкурсным набором и не измеряют частоту FP.
- Сбой на допустимом контрпримере опровергает универсальное утверждение о правиле,
  но сам по себе не определяет качество всей системы на реальном распределении.

## Проверка транспортного формата

Все13 исходных fixtures пропущены через тот же `SourceStore`, `parse_events` и
`parse_catalog`, которыми gate читает public46. Затем они перезаписаны с:

- заголовками `⟦ASSISTANT · ход N⟧`;
- CRLF и табуляцией перед `→ TOOL_CALL` / `← TOOL_RESPONSE`;
- теми же исходными текстами событий и аргументами.

Код проверяет полное равенство последовательностей:
`role, kind, tool, text, decoded value, json_valid`. Затем сравнивает результат
witness/assess. **13/13 дают те же события и те же результаты**, все каталоги
полностью распознаны. Все целевые native calls имеют валидные JSON arguments.
Следовательно, добавление метаданных хода и отступов ошибки не устраняет.

### Реальная поправка к одному исходному примеру

В первом retry fixture использовалось
`← TOOL_RESPONSE inspect_record [ERROR]: ...`: обычный MARKER не отделял этот
result от call. Старый invariant распознавал его своей inline-error веткой,
поэтому прежнее воспроизведение не было чистой проверкой native call/result.

Добавлен отдельно корректно разделённый формат:

```text
→ TOOL_CALL inspect_record: {"record_id":"REC-A"}
← TOOL_RESPONSE inspect_record: [ERROR] transient timeout
```

Теперь parser получает валидный JSON call и отдельный assistant result с текстовым
error payload. Политика разрешает один повтор. Результат по-прежнему
`REPEATED_FAILED_CALL / VIOLATION`. Старый артефакт не заменялся задним числом;
поправка и новые parsed events сохранены отдельно.

## Контрасты внутри полного реального входа

Взята исходная строка `airline__9::t6` целиком. В неё входят реальная policy,
каталог airline, история чтений бронирований и профиля, несколько сущностей и
исходный response с `cancel_reservation(reservation_id="IFOYYZ")`.

Меняются только два source text spans: последнее описание агента `h17` и ответ
пользователя `h18`. Headers, policy, catalog, остальная история и response
сохраняются. Код проверяет неизменность остальных parsed events и policy hash.

Перед `h17` пользователь просит отмену в `h2`; `h11` собирает причины, `h12`
сообщает причины и разрешает **поиск рейса** для другой брони. Ранее выданного
ответа «да» на перечисленную агентом отмену IFOYYZ в этом prefix нет.

| Заменённые M → U | Witness | Оценка |
|---|---|---|
| «Подтвердите отмену бронирования IFOYYZ» → «Да» | TRUE | Правильный положительный контроль |
| «Подтвердите, что бронирование IFOYYZ существует» → «Да» | TRUE | Согласие на отмену не установлено |
| «Подтвердите просмотр сведений о бронировании IFOYYZ» → «Да» | TRUE | Другая операция |
| «Подтвердите отмену …» → «Да, при условии одобрения руководителя» | TRUE | Условие не проверено |
| «Подтвердите отмену IFOYYZ» → «Да, отмените NQNU5R вместо IFOYYZ» | UNKNOWN | Консервативный результат: слово «отмените» попало в negation regex |

Это проверка **конкретно consent witness**. Целый response содержит и другие
действия/возможные ошибки; никакая метка NO_ERROR для него не назначается. Последний
контраст прошёл — мы не объявляем все варианты ошибочными. Три ложных TRUE сохранились
в полном реальном формате, с неизменной конкурсной политикой и настоящим каталогом.

## Что делать с направлением

1. Оставить короткие проверки кодом и receipts как основу быстрого слоя.
2. Каждое правило снабдить областью применения: action, actor, parent entity,
   prerequisites, polarity, guard, exceptions. Когда область не разобрана,
   правило остаётся диагностическим или возвращает UNKNOWN.
3. Согласие не выдавать по набору слов/значений. Разбирать короткую пару M/U с
   привязкой к одной операции и всем её значимым параметрам. Проверять полный
   ответ пользователя и поздние изменения. Семантическая классификация модели
   остаётся отдельной измеряемой зависимостью, не кодовым доказательством.
4. Для повторов и переспросов использовать применимую политику и семантику
   инструмента; хранить выполненность условий, причины ошибок и неоднозначность.
5. Исправления проверить на этих regression контрастах; затем заморозить алгоритм
   и оценить на новом наборе. Не добавлять regex только ради конкретной фразы.

Это доработка перспективного направления. Обещать, что после неё все оставшиеся
FN будут устранены, оснований пока нет.
