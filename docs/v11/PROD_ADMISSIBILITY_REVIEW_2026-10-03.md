## 1. Свободное согласие: добавленная эвристика небезопасна

В `consent.py:87` поиск перебирает сообщения агента назад. Условие принятия —
request cue и наличие значений аргументов в тексте. **Операция из target в этом
сопоставлении не проверяется.** В `consent.py:102` достаточно положительного начала
ответа без слов из короткого списка отрицаний; остальная семантика ответа не проверена.

Целевой вызов во всех следующих примерах: `apply_a(record_id="REC-A", amount=2)`.
Начальный контекст содержит REC-A; объявлены отдельно изменение и просмотр записи.

| Сообщение агента → ответ пользователя | Ветка выдаёт | Почему нет такого согласия |
|---|---|---|
| “Please confirm whether record REC-A already has amount 2.” → “Yes” | TRUE | Подтверждён факт |
| “Shall I inspect REC-A? The amount shown is 2.” → “Yes” | TRUE | Подтверждён просмотр |
| “Please confirm you will apply amount 2 to REC-A yourself.” → “Yes” | TRUE | Действующий субъект — пользователь |
| “Shall I apply amount 2 to REC-A?” → “Yes, make it 999 instead.” | TRUE | Пользователь изменил сумму |
| То же предложение → “Yes, only if the supervisor approves.” | TRUE | Не установлено выполнение условия |
| То же предложение → “Yes, I refuse to approve.” | TRUE | Пропущен явный отказ |
| Согласие, затем агент отзывает предложение и обещает только просмотр | TRUE | Последующий текст проигнорирован |
| “Shall I inspect REC-A? The amount shown is 2.” → “No” | FALSE | Отказ от просмотра перенесён на изменение |

Положительный контроль с точным предложением `apply amount 2` и ответом `Yes` даёт TRUE.
То есть тесты действительно вызывают работающий bounded witness, а не проверяют
полностью недоступный парсер. Восемь отрицательных контрпримеров воспроизведены root;
субагент независимо подтвердил основные классы ошибок.

Последний пример становится **DECISIVE POLICY_ATOM_VIOLATION / REJECT**, если включить
правильное уже принятое правило о согласии для apply_a. Для воспроизведения таблица
собрана из трёх одинаковых ручных fixture proposals: это тест проводки witness в gate,
**не** три реальных модельных голоса и не статистическое подтверждение компилятора.

Другие дефекты, подтверждённые независимым code audit:

- `consent.py:59`: boolean и длинные значения опускаются; enum-параметры не проверяются.
- `consent.py:119`: enum values собираются из **всех** инструментов, поэтому чужой enum
  может убрать существенный параметр текущего действия из required mentions.
- `consent.py:70`: opaque ID сопоставляется без учёта регистра.
- `consent.py:108`: READ определяется префиксом имени; `get_and_delete` проходит как чтение
  даже при объявлении с эффектом удаления.

Текущий выигрыш TP19 не вызван разрешением этой проблемы: при пустом bundle правила
согласия вообще не участвуют в public46 gate.

## 2. UNKNOWN0 — изменение контракта решения

В `admissibility.py:185` отсутствие найденного нарушения становится ADMISSIBLE,
даже если обязательный policy atom оставлен в `unresolved`. В `admissibility.py:49`
любой ADMISSIBLE сразу становится ALLOW, включая режим STRICT.

Воспроизведение: правило явно требует согласие, принятая таблица содержит DECISIVE
confirmation atom, в истории нет описания операции и подтверждения. Результат:

```json
{"verdict":"ADMISSIBLE","decision":"ALLOW",
 "unresolved":[{"code":"ATOM_UNRESOLVED"}]}
```

Такой bounded score допустимо использовать как отдельный сигнал «проверки не нашли
нарушения», если это явно согласованный контракт. Он не удостоверяет исполнение
обязательного условия и не даёт безопасного STRICT допуска. Падение количества
UNKNOWN нельзя считать улучшением полноты доказательств.

Отдельно: `apply_a({"record_id":null,"amount":null})` проходит required string/number
schema без нарушения и получает ADMISSIBLE. В `admissibility.py:90` условие
`bad and v is not None` пропускает недопустимый null; nullable здесь не объявлен.

## 3. Решающие правила имеют ложные запреты

Четыре примера root воспроизвёл через полный `assess`, а не только вызов regex.
Каждый возвращает VIOLATION / REJECT с единственной указанной находкой.
Они сохранены с полными исходными policy, tools, history и response в JSON.

| Допустимый случай | Ложная находка | Причина |
|---|---|---|
| Запрещено открывать просроченный ticket **unless supervisor_override is true**; вызов имеет true | TEMPORAL_PROHIBITION | Парсер обрезает исключение после “in the past” |
| Политика: **“Do not require … any 2 out of …”**; инструмент пишет неуспешную попытку верификации | VERIFICATION_QUORUM_NOT_MET | Положительный regex не учитывает отрицание требования |
| Политика требует подтвердить DOB независимо от сохранённого значения; агент просит это сделать | REDUNDANT_INFO_REQUEST | Наличие значения ошибочно отменяет обязанность проверки |
| Политика разрешает один повтор после transient timeout; агент делает такой повтор | REPEATED_FAILED_CALL | Повтор объявлен нарушением без проверки политики и причины сбоя |

Ссылки в проверенном snapshot: `temporal.py:24`, `verification.py:17`, `prose.py:68`,
`invariants.py:77`. Проверки называют себя domain-agnostic, однако обобщённые имена
и отсутствие case IDs сами по себе не делают эти выводы следствиями политики.

Дополнительные воспроизведения субагента, не включённые в основной executable artifact:
чужая родительская сущность через альтернативный `id`; выбор конфликтующей даты по
порядку результатов; orphan tool result; числовой operand из произвольного поля;
разрешённая частичная замена `[A,B] → [C,B]` ошибочно считается noop. Эти результаты
не используются для нового агрегированного score.

## Что переносить и что исправить

1. **Сохранить** routing, audit receipts, проверку подписи/hash bundle, отказ от
   подмены аргументной синтаксической проверки подтверждением пользователя.
   Подпись удостоверяет целостность артефакта; семантическую полноту она не доказывает.
2. **Закрыть небезопасный prose consent fallback**. Для свободной речи использовать
   source-bound operation/actor/parent/parameter extraction; полный пользовательский
   ответ разбирать на scoped CONFIRM/MODIFY/REFUSE/CONDITIONAL/NEW_REQUEST.
   Непроверенная семантика остаётся SHADOW/UNKNOWN. Наличие всех значений не заменяет
   привязку этих значений к операции. Не исключать enum, boolean и длинные параметры
   без отдельного объявления их роли.
3. **Разделить сигнал детектора и разрешение выполнения**. Unresolved mandatory atom
   должен сохранять unknown prerequisite и влиять на STRICT enforcement.
   Не маркировать доказанным согласием отсутствие обнаруженного нарушения.
4. **Исправить nullable/schema и receipts**. Наблюдение должно иметь валидные actor,
   связанный call/result, целевую родительскую сущность и однозначность; нельзя
   собирать всё в общий corpus и выбирать последний подходящий словарь.
5. **Проверять polarity, guards и exceptions до DECISIVE**. При неполном разборе
   оставлять эвристику диагностической. Повтор, переспрос и частичный noop требуют
   собственной применимой политики/семантики инструмента.
6. После фикса заморозить реализацию и проверить новые контрасты и новый набор.
   Показать отдельно реальное consent coverage, неправильные TRUE/FALSE и новые TP/FP.
   Наши текущие контрпримеры после исправления будут regression/development тестами.
