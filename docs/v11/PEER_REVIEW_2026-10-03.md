## Оставшиеся дефекты: воспроизведены

### 1. Вопрос о факте по-прежнему принимается за описание действия

`witness.py:125`, внутренний `bound()` принимает любое `?` при совпадении ID.
Примеры перед `apply_a(record_id=X, amount=2)`:

- «Запись X уже закрыта?» → «Нет»: **FALSE**, хотя это отрицание факта,
  а не отказ от изменения. CONFIRMATION-атом выдаст ложную тревогу.
- «Запись X уже закрыта?» → сразу вызов: тоже **FALSE** без описания действия.
- «Это запись X, которую нужно посмотреть?» → «Да»: **TRUE**, хотя пользователь
  подтвердил объект просмотра, а не изменение.

Нужно различать ответ о факте и подтверждение конкретного действия. Простое
совпадение ID и вопросительного знака такой связи не доказывает.

### 2. Согласие не привязано к операции и существенным параметрам

«Подтверждаете применение суммы **2** к X?» → «Да» →
`apply_a(record_id=X, amount=999)` даёт **TRUE**. Даже новая фраза
«Сейчас применю **999** к X» считается допустимым повествованием после согласия.
В последнем контрасте старая версия давала FALSE, новая TRUE; оба результата
не доказаны. Без подтверждённой связи параметров нужен UNKNOWN.

Нужна запись согласия вида `(действие, сущность, параметры, ход пользователя)`.
Код должен проверять, что новое описание/вызов не меняет эту запись. Для
свободной прозы связь может предложить модель, но буквальные значения и
последовательность проверяются кодом; неполная связь остаётся UNKNOWN.

### 3. TARGET привязывает дочерний элемент, но теряет родительскую сущность

`evaluate.py:86`, ветка коллекций. Результат допустимого read `{}`:
`{"record_id":"Y","items":{"I":{"item_id":"I","enabled":false}}}`.
Цель — запись **X**, элемент I. TARGET по `$key == item_id` выбирает I из
чужой записи Y: необходимое `enabled == true` становится **FALSE**, finding=true.
Атом **проходит admission**; это не только прямой обход валидатора в тесте.

Исправление `observed_anchors()` затрагивает только скалярную ветку и этот
случай не закрывает. Нужны совместная проверка родительского ID и TARGET,
проверка происхождения результата и UNKNOWN при отсутствии однозначной связи.

### 4. Защита границ ID пока асимметрична

`witness.py:99`: правый `X-1` защищён, но **P.X** и **group/X** по-прежнему
совпадают с X. Оба контраста возвращают TRUE. Нужна одинаковая обработка
соединённых символов слева/справа; пунктуация после самостоятельного X
должна сохранять обычное совпадение.

## Главная проблема компиляции этими коммитами не решена

`compile.py` и `schema.py` между версиями **не изменились**. Повторно проверены
те же 34 сохранённых ответа старого пилота, без новых запросов:

| Модель | Валидные envelope | Принятые атомы | Общие атомы между моделями |
|---|---:|---:|---:|
| GPT-OSS120b high | 14/17 | 12 | 0 |
| Nemotron ultra | 14/17 | 1 | 0 |

Числа admission старой и новой версий одинаковы. Это неполный пилот двух
моделей: Gemma ещё не измерена. Сохранённые ответы не доказывают, что будущие
ответы третьей модели не помогут; но сейчас оснований обещать DECISIVE нет.

Конкретные причины:

- У GPT-OSS три ответа и их JSON-повторы закончились `finish_reason=length`
  с пустым `content`: output-limit 8192 занят генерацией/рассуждением. Это
  отличается от сознательного ответа `atoms: []`.
- Три GPT-OSS атома используют структурированный `prior_call:{tool,binding}`
  вместо строкового `prior_call` и отдельного `binding`; admission отклоняет.
  У Nemotron два невалидных атома, один также с неправильной modality.
- У Nemotron три TimeoutError. Их нельзя считать смысловой ошибкой модели.
- Mistral availability получил 429, поэтому его breaker открывается отдельно.

Следующий опыт должен отдельно проверить достаточный output budget для high
и однозначный wire-пример prior-call. Если переносить точный объектный wrapper,
это только явно описанный механический адаптер без исправления неверной
modality. Новый protocol/freeze и отдельные receipts обязательны; старые
неудачи остаются сохранёнными. Смысловую полноту такой адаптер не доказывает.

## Замер пока тоже имеет ограничения

- Frozen manifest содержит **4 положительных мутанта** (3 M1, 1 M3),
  **0 положительных M2**. Telecom/banking без положительных аннотированных
  проверок. Даже 4/4 недостаточно для широкого вывода о переносе.
- `measure_mutations({})` возвращает `positive_mutants:0`, хотя frozen
  manifest содержит 4. При отсутствии таблицы положительные примеры должны
  оставаться в знаменателе как пропуски; отдельно нужен счёт отсутствующих
  таблиц, а не исключение примеров.
- `mechanism()` считает совпадение одного lhs достаточным. Для условия
  `status == 'open'` он принимает `status == 'blocked'` как MECHANISM.
  Такой результат нужно показывать как связанную тревогу, отдельно от точного
  совпадения обязанности/оператора/значения/связи. Иначе possible right-label,
  wrong-reason воспроизводится уже внутри кодового scorer.

Основной замер **TP/FP/FN/TN на public46 для новой версии не проводился**.
Baseline остаётся 15/0/8/23, улучшение детектора не подтверждено.
