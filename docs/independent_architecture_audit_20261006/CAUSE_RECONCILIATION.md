## 2. Что именно означает wrong-cause внешний вывод

Внешняя таблица относится к **21 дополнительному winning обвинению** относительно A за три прогона: 7/6/8 новых TP. Она не является утверждением, что все V4 причины неверны. DF на этих внешних строках не запускался.

По исходному frozen judge новые SAME — 2/1/0. Проверка всех 21 по полным источникам даёт другую диагностическую категоризацию: 5 поддержанных cores, 1 поддержанный core с лишним условием, 14 ложных winning cores и 1 неопределённый. То есть поддержанный core, включая mixed, — 3/2/1. Это post-hoc source review, не замена frozen метрики и не новый результат holdout.

Например, one-call нарушение в `ext_tel_047` реально есть; PARTIAL на r2/r3 не опровергает его. Одновременно missing-confirmation обвинения в `ext_ret_019` противоречат h30 с деталями и h31 с явным Yes. Ошибка уже есть в raw AT и затем в raw verifier; JSON parsing её не создаёт.

Фраза «почти всегда находит нужные строки» количественно слишком сильна: на revised gold V4 находит 36/37/38 из 52 ERROR, **recall 69.2%/71.2%/73.1%**. Более точная формулировка: «V4 повышает бинарный recall относительно A; правильность дополнительных winning причин ограничена и частично искажена downstream обработкой и gold/judge».

## 3. На внешнем наборе тоже найдены downstream потери правильной работы

### ext_ret_022, r3: технический отказ после правильного кандидата

Ems уже даёт правильную причину на t1: после смены запроса на backpack/PayPal не получено явное yes на окончательные детали. Но verifier завершается `finish_reason=error`, `admission=INVALID_JSON`, `verdict=null`; `first_invalid` показывает тот же тип отказа на первой попытке. В raw reply начинается релевантный анализ, затем JSON остаётся незавершённым.

V4 выбирает surviving AT/t0 с ложным утверждением про изменение desk lamp, хотя current prose оставляет лампу без изменений, а call содержит только backpack. Это **correct candidate → technical rejection → false winning alternative**. Нельзя принимать незавершённый JSON как certificate, но нельзя и объяснять этот исход только отсутствием способности найти нарушение.

### ext_ret_025, r3: первый кандидат скрывает более релевантный

Все четыре AT target assessments имеют `admitted=true`. Код выбирает t0 и проверяет только его. Его обвинение в неподтверждённом возврате неверно: h23 перечисляет возвраты, h24 — Yes.

Raw t3 отдельно говорит о неподтверждённых cancellation details, включая reason. Source policy требует подтверждения order ID **и** reason (`no longer needed` / `ordered by mistake`). В полном prompt нет предложения/подтверждения этого reason; current call использует `no longer needed`. Поэтому у t3 есть поддержанное ядро причины, хотя формулировка также неаккуратно упоминает order ID, который присутствует в h23. Этот кандидат не выбирается и не получает verifier.

Это **выбор первого обвинения**, а не потеря target при inventory parsing. Повторная проверка t3 ещё не выполнена; нельзя считать его автоматически верифицированным или объявлять новый F1. Нужен отдельный candidate pool и source-grounded adjudication. Gold v2 помечает эту строку F1-only, так что полный список acceptable causes тоже требует дополнения в новой, отдельной фазе.

### ext_air_043, r1: narrow verifier теряет контрсвидетельство

Исходный reviewer packet содержит h51 и h53 с явным подтверждением downgrade всех пяти перечисленных reservations. Вход narrow verifier содержит только evidence `t0, h55, h57, h58, h59` — оба подтверждения исчезли при сужении до cited sources + последних четырёх events. Затем verifier поддерживает ложное missing-confirmation обвинение.

Raw AT уже ошибается на полном packet, но verifier не получает нужные данные для опровержения. Нужно сохранять применимую proposal/confirmation цепочку и маркировать неполноту поиска. Увеличение общей мощности модели само по себе не исправляет отсутствие контрсвидетельства во входе.

## 4. Дополнительная ошибка новой разметки

Для `ext_ret_041` gold S, помеченный checked, утверждает направление изменения адреса, противоположное видимому prompt: source tools и предложение показывают luggage W1092119 по 592 Elm, tablet W1603792 по 760 Elm; пользователь подтверждает перевод luggage на current/default 760 Elm. Gold S требует другого заказа и противоположного направления. Это проверяемое противоречие source и аннотации, возможно наследие hidden task expectation. Оно требует отдельной adjudication.

Бинарный ERROR этой строки сохраняет основание через prose+call F2. Неверный S не делает автоматически правильным ложное missing-confirmation обвинение, но дополнительно ограничивает выводы по совпадению причин.

## 5. Как следует формулировать решение о default

Рекомендуемая формулировка для исследовательской ветки:

> Исправления admission и части quote gates сохранили или восстановили конкретные правильные причины; DF4 и Ems имеют подтверждённые корректные случаи на development данных. На внешнем tau2 V4 даёт +7/+6/+8 бинарных TP без новых FP по пересмотренной gold v2. Дополнительные winning обвинения часто ложны, но часть правильных внутренних кандидатов теряется при verifier serialization, admission и выборе первого кандидата; narrow verification также может удалить контрсвидетельства. Gold v2 и cause judge не являются окончательным независимым контрактом. Default пока остаётся guard_adm2 до исправлений и нового сопоставимого blind эксперимента. Перенос DF и proof execution на этом внешнем наборе не измерен.

Это объясняет одновременно прежние победы и незавершённость V4. Следующие исправления следует измерять отдельно: serialization/error handling; exact addressed leaves; operation-specific binding/polarity; сохранение всех кандидатов; source closure для verifier; полные альтернативные причины в новом gold. Не принимать неподдержанные premises ради возврата прежнего TP и не объявлять гипотетический candidate recovery автоматическим улучшением.

Технические состояния ret022, admitted targets ret025 и удалённые narrow evidence air043 отдельно проверены исполняемыми assertions; [JSON receipts](cause_followup_receipts.json) сохраняет соответствующие поля и исходные подтверждения. Методологические формулировки дополнительно прошли peer review.
