## Предварительно обнаруженные причины ошибок

Смысловая проверка и проверка адреса различаются. В отдельном ручном аудите
всех 16 EFFECT-ответов A только 10 наборов action-span достигают содержательной
части описания. Остальные указывают на обрывки названий или разделитель:
например, `- update_reser`, `- cancel_reservat`, ` — Calculate`. Все 16
формально находятся внутри source range. Поэтому 16/16 admission не означает
16/16 правильно обоснованных эффектов.

У B 11/16 EFFECT-ответов проходят точную локализацию, 5 не проходят из-за
отсутствующей или неоднозначной цитаты. У принятого ответа всё равно может
быть неверный смысл: математическое вычисление модель относит к MODIFY;
для динамического вызова неизвестного инструмента тоже выводит MODIFY.
Это гипотезы модели, не свойства, доказанные цитатой.

В инвентаризациях встречаются `AND` без двух детей, `BEFORE` без двух событий,
а также требования из соседнего окна вместо запрошенного. Схема исходного
Pydantic-класса не переносит произвольный Python validator в JSON Schema:
проверку arity раньше выполнял только локальный код после ответа.

Независимый аудит обнаружил различие при использовании alias source ID:
A принимает абсолютный диапазон родительского источника внутри показанного
окна, B требует ID показанного фрагмента. Это ограничение первого сравнения.
Во всех 47 ответах B alias-адресов и обходов через числовые позиции не было.
Различие реализаций сохраняется как ограничение протокола.

## Следующий кандидат

Отдельная версия без исправления первого frozen прогона:

1. Код выпускает ID непустых исходных строк. Строки служат адресами, а не
   считаются независимыми правилами. Родительский и соседний контекст сохраняется.
2. Модель выбирает ID, не считает позиции и не переписывает цитаты.
3. Arity формулы включается в JSON Schema: ATOM/UNKNOWN — 0 детей,
   AND/OR — минимум 2, NOT — 1, BEFORE/AFTER — 2.
4. Source-span требования должен содержаться в запрошенном окне. Условия
   и действия по-прежнему могут ссылаться на соседний контекст.
5. Для native сравнения code-issued ID точных JSON-скаляров позволяет
   перепроверить числа кодом. Выбор связи числа с правилом остаётся гипотезой.
6. В prompt явно задано различие condition/guard, необходимого условия,
   условного запрета и обычного разрешения. Это изменение семантической
   инструкции, поэтому следующий опыт проверяет комбинацию улучшений.

Это разработка после открытия ошибок первого parser, а не независимый
held-out результат. Gold целевых решений не открывался.

## Поиск фактов

Существующий поиск ранжирует весь source, но показывает его начало. Поэтому
выбор правильного 63-тысячного наблюдения ещё не доставляет нужный фрагмент
из его конца. Кандидат ранжирует все окна полного native prefix и распределяет
лимит между источниками, сохраняя текущий вызов и последнюю пару реплик.

Используется BM25 с k1=1.5 и b=0.75; это стандартная формула с обычными
параметрами, не подбором по данным. См.
[описание в учебнике Information Retrieval](https://nlp.stanford.edu/IR-book/html/htmledition/okapi-bm25-a-non-binary-model-1.html).
В структурном тесте нужный фрагмент после 40 тысяч символов доставляется
в показанный контекст. Это проверка доставки текста, не точности модельного witness.

Для поиска применимых требований нужен полный обратный проход по найденным
правилам. Он не доказывает, что извлечение нашло все правила. Необработанные
окна, неопределённый scope, отсутствие witness и исчерпанный бюджет сохраняются
как конкретные причины UNKNOWN.

Выбор целевых вызовов для дальнейшего узкого сравнения выполнен только по
хешам system-текста и `(seed, case_id, target_id)`: два вызова на каждый из
четырёх различных system-текстов. Манифест
`outputs/searh_23/evidence_graph_search_probe_20261004/target_selection.json`.
Успех извлечения и метки не используются для отбора.

## Границы выводов

Мы оцениваем текущие native вызовы, не исторические вызовы и не текстовые
ответы. У public46 таких вызовов 37 в 23 строках; это другой знаменатель,
чем прежние 84 исторических и текущих вызова consent inventory.

Дословность, корректная схема, полный поиск и арифметика дают разные
проверяемые свойства. Они не подтверждают автоматически применимость политики,
истинность пересказа агента или полноту семантического разбора.
Все результаты этого опыта остаются SHADOW, `code_proof=false`.

Поддержка custom JSON Schema описана в
[официальной документации Mistral](https://docs.mistral.ai/studio/conversations/structured-output/custom).
Локальная проверка ответа обязательна и при использовании режима API.
