## Протокол

46 одинаковых реальных диалогов × direct/search. Общий structural layer;
11 входов обходятся без LLM в обоих рукавах. Direct получает полный контекст,
search — полный индекс и инструменты последовательного доступа. У каждого
неструктурного входа максимум 1 direct и 6 search вызовов. Промпты и hash
кода заморожены в `comparison_ids_v3/frozen.json` до вызовов API. Gold
открывает отдельный scorer после полного окончания, алгоритм в ходе прогона
не корректируется. Public46 многократно просмотрен: это development
регрессия, не независимая проверка переноса.

Сначала один paired вход проверяет формат и достаточность длины. При
технически пригодном формате остальные 45 продолжаются в том же journal,
готовая первая пара не пересчитывается. Семантическое несогласие не служит
основанием менять промпт в замороженном эксперименте.

## Проверено до API

44 теста и 92 механических прохода service dispatch. Эти результаты
проверяют сохранение исходников, вызов нужного интерфейса и доступность
источников; они не означают 92 правильных модельных решения.

## Результаты

V3 сохранил два UNKNOWN: direct дал законченный ответ, но у четырёх закрытых
проверок отсутствуют evidence IDs; search сделал пять чтений и ещё один
native tool call в FINAL вместо assessment. V4 попробовал API
`tool_choice=none` и явное сообщение об окончании запросов. Провайдер всё
равно вернул native call в FINAL. На повторе пять исходных запросов и direct
взяты из cache, новый HTTP был только один; это не семь новых вызовов.

V5 закрывает native разговор на FINAL: весь предыдущий transcript без
обрезки становится JSON-данными в одном user сообщении, tools не предлагаются.
Модель получает те же прочитанные исходники и результаты операций, но уже
не продолжает native tool conversation. Изменение механическое; gold этих
пилотов не открывался. V2–V4 остаются отдельными остановленными пилотами.
Замороженный полный протокол теперь `comparison_ids_v5/frozen.json`.

### Конкретные причины

1. **Формат закрытых проверок.** У direct 34/35 модельных оценок стали
   UNKNOWN из-за неполных checks; у search 26 таких случаев. В direct у
   30 ответов закрытая `exceptions` проверка не имеет evidence IDs, у 27 —
   `alternatives`, у 28 — `arithmetic`. Дописать ссылки недостаточно для
   доказательства смысла этих проверок.
2. **Смешение исследователя и проверяемого агента.** В banking_051 search
   обвинил проверяемого агента в нашем `read_source` после нашей команды
   окончить запросы. В banking_080 модель вообще предложила `KB_search_dense`
   из каталога проверяемого агента; транспорт правильно отклонил его и ничего
   не исполнил. Другой UNAVAILABLE — airline_10::t21: HTTP ответ с пустым
   content. Оба дали UNKNOWN; это не 402/429 и не отсутствие CUDA.
3. **Прочитал часть — объявил отсутствие.** Airline_7: числа находятся в
   reservation responses h19–h22, но search после других чтений заявлял,
   что этих чисел нет. Правильная положительная метка не делает эту причину
   верной. Аналогично retail_48 search заявлял, что пользователь не дал zip,
   хотя h4 и h7 содержат `80273`.
4. **Смысл цитат не проверен.** Единственный принятый LLM FP — banking_063::t8:
   заявлено отсутствие согласия на перевод, хотя scorer метит случай чистым.
   Все source IDs и пять checks прошли: это демонстрация предела проверки
   происхождения текста. При этом direct предлагает NO_ERROR на banking_003,
   не установив исчерпанность поиска, и на retail_29, не установив отсутствие
   другого допустимого заказа.

Последние сырые предложения без валидатора (только диагностический replay,
не новый детектор): direct 4 TP / 8 FN / 23 TN, search 8 TP / 4 FN / 11 FP /
10 TN / 2 без assessment. Здесь исключены 11 structural случаев, а часть
предложений имеет невалидные поля/причины. Простое снятие checks не является
исправлением: поиск одновременно находит больше положительных меток и
выдумывает значительно больше нарушений.

### Отдельная проверка target frame

До открытия gold полного V5 заморожен `target_frame_probe_v2`: шесть
исторических положительных регрессий × direct/search, 12 результатов.
Код повторяет проверяемый ответ и его t-IDs перед каждым model request,
явно отличает его от действий Guardian и напоминает формат evidence IDs.

12/12 закончены: direct 1 TP / 5 FN, все six checks формально закрыты;
search 1 TP / 5 UNKNOWN. 35 новых HTTP / 404 617 tokens. Поисковый TP
airline_7 получен с ложным объяснением «чисел нет в контексте», поэтому это
совпадение метки, не подтверждённое верное рассуждение. У direct retail_48
отмечено неподтверждённое разделение имени; этот известный пример не доказывает
перенос. В наборе нет отрицательных контролей: precision этим опытом не
измеряется.

V2 reminder содержал указание assessment-формата даже в SEARCH; это вызвало
пять преждевременных assessment. Исправление V3 делает reminder фазовым:
SEARCH просит только следующую операцию/ready_for_judge, JUDGE/FINAL — оценку.
DIRECT сообщения не меняются и используют cache. Это технический контроль,
не новая семантическая теория; результат будет записан отдельно.

Артефакты V5: `comparison_ids_v5/score.json`, `mechanism_audit.json`,
`predictions.jsonl`, `status.json`, `real46_artifacts.zip` (все 92 raw/index
references проверены по hash). ZIP содержит только реально использованные
источники, а не все механически сгенерированные снимки. Сохранён вне GPU.
`target_frame_probe_v2/probe_artifacts.zip` также сохранён вне GPU.

Конкурсный `scripts/predict.py` не меняется. Ни V5, ни target-frame V2 пока
не подходят для повышения в конкурсный слой.
