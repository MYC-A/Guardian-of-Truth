## Как ошибается даже независимая проверка

Оставшиеся два FP с графом:
`textile_certification::order::04` и `sports_equipment_rental::order::04`.
После неуспешной проверки агент снова вызывает `inspect_*`. Политика
требует успешную проверку перед **`commit_*`**, а целевой вызов ничего
не коммитит. Проверяющая модель точно цитирует правило и неудачный
результат, но переносит запрет на саму проверку. В одном объяснении она
даже утверждает, что policy «explicitly prohibits repeating a failed
inspection», хотя в источнике этого нет.

Это прежняя ошибка action-scope, сохранившаяся после второго судьи.
Цитата и повторное согласие двух моделей не являются доказательством
применимости. Новый слой помогает на части случаев, но не устранил эту
ошибку универсально. Правила под имена `inspect_*` не добавлялись.

## Что показал формальный перевод

Использованы исходные `guardian_truth.formal_translation` и
`formal_reasoning` с ограниченным signed-Horn выводом. Первый запуск
оказался ошибкой нашего адаптера: промпт ссылался на JSON schema, а
схема не передавалась. Его нулевой результат не относится к качеству
формальной архитектуры. После исправления: 63/80 структурно валидных
переводов; 27 из них явно UNSUPPORTED; 19 выводов решателя из 80:
18 FOLLOWS и 1 CONTRADICTS. Среди этих 19 есть FP и FN.

Схема допускает свободный текст атома. В одном ответе атомом запроса
стало «вызов запрошен», а не «вызов разрешён»: запрос подставлен как факт
из целевого ответа и доказывает сам себя. В другом отрицательная
политика превращена в отрицательный факт о мире. Решатель честно выводит
следствие ошибочного перевода. Дословная цитата этого не предотвращает.

Часть покрытия ограничена **самим backend**: нет общих переменных,
арифметики, временных операторов, case splitting и contraposition.
Сильнее переводящая модель может лучше соблюдать схему, но это не
расширяет логический фрагмент. Phi передаётся Gemma только с явным
статусом неподтверждённой интерпретации. Для self-sourced query
добавляется предупреждение, исходный перевод не исправляется.

Исправленный полный журнал `outputs/hybrid_phi_shadow/feb312d214f1d141f051/`.
Сравнение M00/M10/M01/M11 и H3 запущено отдельным фиксированным
протоколом; чисел качества до завершения всех прогнозов в отчёте нет.

## Сравнение моделей перевода

Зафиксировано `dataset/translation_models_v1/protocol.json`: те же
16 входов, schema, промпт, solver, temperature=0 и лимит 4,000 output
tokens для Codestral 2508, Kimi Code и Mistral Small 2603. Ministral
сравнивается по уже полученным ответам, без повторной генерации.
Выборка dev, а не sealed. Это замена frontend-модели, не новая архитектура.

Документация: [Codestral](https://docs.mistral.ai/models/codestral-25-08),
[Kimi Code в Ollama](https://registry.ollama.com/library/kimi-k2.7-code),
[форматы JSON Mistral](https://docs.mistral.ai/studio/conversations/structured-output).
Специализация на коде сама по себе не подтверждает точность NL→логика.

В клиенте найден ещё один собственный баг: для явного `provider/model`
API-ответ успевал попасть в кеш, а логирование затем искало provider по
уже укороченному model ID и теряло успешный ответ. Исправление проверено
регрессионным тестом. Ответы Codestral восстановлены из точного кеша,
без повторного API-прогона; первый ошибочный журнал сохранён. Ошибки
доступа к другим моделям отмечаются отдельно от невалидного перевода.

## Следующее основание для выбора

После полного dev-сравнения фиксируются кандидаты и проводится один
прогон на 160 входах других доменов. Даже хороший результат там будет
проверкой переноса **этих четырёх логических шаблонов**, а не полной
гарантией для конкурса. Для широкого вывода нужны другие логические
формы и независимо проверенная разметка. Обещать универсальность по
нынешнему синтетическому набору нельзя.
