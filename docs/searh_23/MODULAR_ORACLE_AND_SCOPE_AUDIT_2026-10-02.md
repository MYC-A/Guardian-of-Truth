## 1. Исправлена реальная ошибка связывания вызовов

В `v2_pipeline.as_row` ID строился из длины списка **ещё не спаренных**
вызовов. После ответа список уменьшался; очередная последовательная пара
получала тот же `h0`. Native verifier требовал единственный вызов с таким ID
и отвергал факты с `CALL_NOT_UNIQUELY_PRESENT`.

Теперь ID берётся из позиции события: `h{index}`. Если одновременно ждут
ответа несколько одноимённых вызовов, адаптер сохраняет
`AMBIGUOUS_CALL_RESULT` и оставляет ответ неспаренным. Ближайший вызов
по времени не объявляется правильной привязкой без транспортного основания.
Ошибки pairing видны в итоговом V2 trace.

Это поправляет оценку прежнего пилота: **его 0 фактов — смесь ошибок
автоматического контракта, API и адаптера**, а не чистый отрицательный
результат SystemV2. Старые четыре записи не заменены; холодного API-повтора
после исправления ещё не было.

### Ограничения Step3 тоже существенны

На 32 авторских фактических ответах правильные bindings и claim inventory
дали 8 ERROR, 8 NO_ERROR, 16 UNKNOWN:

- Для `active` у нужного ID с двумя наблюдениями native проверяет последний
  предшествующий факт: 16/16 определённых правильных результатов.
- В восьми implication-примерах факт `a=true` и политика
  `IF a → verified` не превращаются в `verified=true` внутри `check_claim`.
  Этот интерфейс сверяет состояние, а не запускает общий вывод по правилам.
- В восьми completion-примерах `status=success/pending` — исходное поле

Следовательно, улучшение NL→предикаты требуется вместе с проверяемыми
bindings **и** подходящим видом Step3: правило вывода для implication,
контракт эффекта для completion. Одной удачной модели-переводчика недостаточно.

## 3. Mistral/Code IR: ограниченная проверка чувствительности

Протокол `sensitivity_protocol.json` записан до offline-вычисления;
gold не читается. Исходный signed-Horn solver получает реальные сохранённые
переводы и не более семи вариантов каждого валидного FORMALIZED IR.
Ни цитаты, ни исходный текст не чинятся. INVALID/UNSUPPORTED/402/429
отдельно исключены из перебора, а не объявлены правильными ответами.

Всего шесть валидных FORMALIZED baselines, 36 ограниченных изменений:

| Изменение | n | Изменился формальный relation |
|---|---:|---:|
| Направление первого правила | 5 | 2 |
| Удаление первого правила | 5 | 1 |
| Удаление одного conjunct | 2 | 0 |
| Замена всех entity annotations неподтверждённым ID | 6 | 0 |
| Замена всех time annotations неподтверждённым будущим | 6 | 0 |
| Удаление первого факта | 6 | 2 |
| Изменение polarity первого факта | 6 | 3 |

Entity/time — **неинтерпретируемые аннотации** этого solver; это прямо
указано в его интерфейсе. Даже две правильные Codestral FOLLOWS сохраняются
после неподтверждённой замены ID/времени. Цитаты остаются дословными, но не
удостоверяют связь с изменённой аннотацией. Guard на источник фактов этого
также не исправляет: он проверяет наличие предшествующего наблюдения,
а не semantic binding каждого predicate.

Эти изменения — диагностические, **не альтернативные верные переводы**.
Неизменный verdict на ограниченном переборе не означает устойчивость.
У signed-Horn нет отдельного типа исключения/сравнения дат; их полнота
не притворяется измеренной через удаление правила.

Практический следующий эксперимент: Code/Instruct предлагает rule tree и
bindings, код проверяет каждый факт по исходному пути, ID, позиции и силе
эффекта; independent B проверяет применимость исходного правила. Общий
formal result сохраняется advisory до измерения source faithfulness.
