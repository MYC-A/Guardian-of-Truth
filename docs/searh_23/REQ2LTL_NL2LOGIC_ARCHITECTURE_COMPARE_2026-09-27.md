# Парное сравнение четырёх способов разбора policy

Дата: 2026-09-27. Ветка: `codex/fast-followup-20260924`.

## Что проверяется

Вопрос: повышает ли **автоматическую полноту разбора всего исходного policy**
именно рекурсивный разбор по Req2LTL/OnionL или NL2Logic относительно нашего
staged-подхода? Это проверка компиляции policy, а не качества конкурсных
вердиктов на траекториях. `scripts/predict.py` не менялся.

Исходные 12 входов и ручной gold записаны в коммит `4962cf4` **до
первого вызова API**. Первый форматный пилот V1 выявил дефект интерфейса:
в JSON mode сервер возвращал валидный JSON, но поле `left` оказывалось
вложенным объектом вместо строки, а `D_select` — массивом вместо объекта.
Рекурсивные рукава обрывались почти сразу; их пилотные нули нельзя трактовать
как проигрыш алгоритмов. Сырые ответы V1 оставлены в отдельной директории.

Основной протокол V2 с явными JSON Schema для **всех четырёх рукавов**
зафиксирован в `226778c` до первого успешного ответа V2. Перед этим
одна попытка была отклонена API с HTTP 422: сервер потребовал поле `schema`,
а опубликованный пример SDK использовал `schema_definition`. Это была
валидация HTTP-запроса, результат модели не появился. После корректировки
формата и отдельного коммита протокол не меняется.
SHA-256 канонического протокола: `7c047f7e198b28d42d93138d8b0a4cff554af910df109456922942c2f5f5f6ea`;
gold: `d5cf750d70f8abb15d7f4eb7d9016726f346d747726a120797cc062f5b27ff6c`.
`frozen.json` содержит только policy, catalog и prompts;
`gold.json` открывает лишь scorer. Все четыре рукава идут по тем же policy и
тем же `ministral-14b-latest` с temperature=0 через Mistral API. Восемь
policy ранее просматривались в наших экспериментах, четыре придуманы для
контраста OR, истинного исключения, двух связанных действий и множества
инструментов. Поэтому это парное сравнение архитектур на **знакомых и
авторских** случаях, не независимая оценка переноса на скрытый конкурс.

Эталон сохраняет `DESCRIPTIVE` для явного пояснения вроде «подача заявки не
равна публикации». В `gold_directives` эти узлы считаются вместе с
нормативными, хотя сами по себе не требуют действия. Это строгая проверка
сохранения исходного смысла, а не чистая метрика числа обязанностей. В
credit-пункте `GATE` и условный запрет могут быть логически эквивалентны;
exact IR всё равно требует заранее записанный `GATE`.

Файлы: `experiments/searh_23/policy_architecture_abcd_v1.py` (общий раннер),
`experiments/searh_23/policy_architecture_abcd_v2.py` (основной протокол),
`experiments/searh_23/policy_architecture_abcd_v2/{frozen,gold}.json`, ответы и
per-case score в `outputs/searh_23/policy_architecture_abcd_v2/`.

## Что на самом деле перенесено из работ

### C — Req2LTL / OnionL

[Статья Req2LTL](https://arxiv.org/html/2512.17334), в особенности разделы
IV–V и Algorithm 1, описывает: сначала общий временной или mode scope
(по умолчанию `Globally`); затем рекурсивное выделение унарного scope,
внешнего бинарного отношения и атомов; структурную проверку OnionL и
детерминированный перевод дерева в LTL. Публичный
[репозиторий](https://github.com/Meng-Nan-MZ/Req2LTL) на момент проверки
содержал README и медиа, но не доступную реализацию транслятора. Поэтому C —
минимальное *воспроизведение алгоритма*, не запуск авторского кода.

У нас первая модельная операция отделяет global/mode scope, затем каждый
узел отдельно выбирает внешнее отношение, после чего атомный парсер
привязывает лист к буквальной цитате и роли. Код проверяет тип/арность,
ограничивает рекурсию и детерминированно собирает Guardian IR. В конечной
формуле используются `GATE`, `ORDER`, `PERMIT`, `FORBID`, `EXCEPT`, `EVEN_IF`,
`AND`, `OR` вместо чистого LTL: проверка действия, каталога инструментов и
различия `LATEST`/`PRIOR_TRUE` не выражается одной готовой LTL-трансляцией
из статьи. Визуальная ручная коррекция и few-shot база авторов не включены.
Статья реализует Building-OnionL как prompt-guided алгоритм построения JSON;
здесь рекурсивные шаги вынесены в отдельные API-вызовы. Это позволяет видеть
ошибку каждого шага, но не является побайтовым воспроизведением их prompts
или полным OnionL2LTL-транслятором.

### D — NL2Logic

[Статья NL2Logic](https://aclanthology.org/2026.findings-eacl.317/) и
[публичный код](https://github.com/peng-gao-lab/nl2logic) задают другую
последовательность: при необходимости перефразировать кванторы, на **каждом**
узле выбрать `atomic / quantified / logical / negation`, вызвать
соответствующий узкий парсер только для внешнего оператора, рекурсивно
обработать дети и детерминированно сгенерировать выражение из AST. Код
проекта ориентирован на FOL, Z3 и backend OpenAI/vLLM/Ollama; его готовый
`Pipeline` нельзя напрямую использовать для `MISTRAL_MODEL` и Guardian IR.
Поэтому D воспроизводит порядок вызовов и рекурсию, а атомный парсер и
компилятор заменены адаптерами к policy/tool-каталогу. SaT-разделитель не
запускался: каждый вход уже один короткий policy-пункт, а не документ.
Двухпроходная генерация деклараций Z3 неприменима к нашему типизированному IR.
У D есть доменная адаптация `BEFORE` и temporal-полей: исходный FOL-AST
проекта не описывает `LATEST` против `PRIOR_TRUE` из Guardian.

### Контроли A и B

A получает весь policy и сразу пишет тот же конечный IR. B сначала перечисляет
самостоятельные директивы, затем по одной достраивает их поля. B сохраняет
маршрут прежнего staged-парсера, но расширен до общего IR для сравнения;
поэтому его цифра здесь **не является повтором** прежних `0/12`.

Все рукава получают одинаковый исходный policy и catalog. Число API-вызовов
различается по алгоритму и отдельно показывается: преимущество по точности
без стоимости нельзя считать бесплатным. В C/D один и тот же атомный парсер;
разница между ними — порядок и способ построения дерева.

## Заранее заданная оценка

Для каждого случая считаем отдельно:

- `directive_match`: правильный вид и **буквальный action span** каждой
  самостоятельной директивы. Избыточные директивы видны отдельно.
- `scope_match`: при такой директиве правильно выбраны все исполняющие
  инструменты и общий контекстный scope.
- `logic_match`: совпадает форма AND/OR/NOT, буквальные условия и семантика
  `EXCEPT` против `EVEN_IF`; временная модальность атомов считается ниже.
- `temporal_match`: совпадают `LATEST`/`PRIOR_TRUE` на условиях или пара
  `BEFORE` для двух действий.
- `span_hit`: доля эталонных буквальных action/condition/before/exception/scope
  цитат, реально попавших в **итоговый IR**. Лист дерева, который не удалось
  связать с директивой, балл не даёт. Повторить весь policy
  одной строкой здесь не даёт автоматического зачёта отдельных цитат.
- `exact_ir`: полное совпадение множества директив и всех их полей; очень
  строгая метрика, поэтому частичные совпадения обязательны к показу.

Буквальные цитаты полезны для аудита, но строгий exact может занизить число
семантически эквивалентных формулировок. По каждому policy ниже и в `score.json`
даны найденные и лишние узлы, пропущенные цитаты и ошибки исполнения.

## Результаты

Один полный прогон V2 окончен. После начала успешных ответов prompts,
схемы, алгоритмы, policy и gold **не менялись**. Scorer воспроизвёл тот же
результат локально из сохранённых ответов. Все 48 `arm × policy` лежат в
`score.json` вместе с точными недостающими/лишними узлами и ошибками.
До открытия агрегированного score была исправлена только диагностика
кратности одинаковых узлов в списках `missing/extra`; формулы основных
метрик и ответы не изменились.

`Вид + буквальное действие` требует совпадения **обоих** полей; `governed`
и логика считаются только для сопоставленной директивы. Поэтому числа не
можно читать как независимые accuracy по каждому полю. Source-span здесь
означает цитаты **итогового IR**. Суммы API-токенов взяты из `usage.total_tokens`
сохранённых 294 ответов; один B-ответ завершился ошибкой формата, остальные
достигли `finish_reason=stop`.

Чтобы отдельно видеть **сам факт распознавания** `AND/OR/NOT/EXCEPT/EVEN_IF`,
после основного score посчитали диагностическую *operator presence*: у A/B в
итоговом IR, у C/D также в промежуточном дереве. Это **не основная метрика**:
оператор может стоять у неверного действия. Эталон содержит семь случаев с
такими операторами.

| Рукав | Нужный оператор присутствует | Лишний оператор | Нужный пропущен |
| --- | ---: | ---: | ---: |
| A | 4 | 4 | 3 |
| B | 4 | 11 | 3 |
| C | 4 | 4 | 3 |
| D | 4 | 6 | 3 |

Например, C видит `OR` в новом dispatch-пункте и `EXCEPT` в draft-пункте,
но не привязывает их к корректному действию; D видит `EXCEPT`, но теряет
`OR` dispatch. В telecom ни C, ни D не сохранили `EVEN_IF` как уступку.

`diagnostics.json`; вычисление в

### Что сломалось у каждого рукава

**A.** Один запрос часто узнаёт направление и инструмент, но возвращает
лишние логически выведенные директивы вместо только независимых исходных.
В credit-модели верно нашлись `PERMIT preview` и `GATE issue`, но рядом
появились отдельные `FORBID` и `ORDER` для того же `issue`. Условие
`recorded approval` было помечено `LATEST`, тогда как frozen gold требует
предшествующее зафиксированное одобрение (`PRIOR_TRUE`). В hotel модель
верно выбрала операцию возврата, но процитировала `the refund` вместо
замороженного `the refund SECOND` и добавила порядок для самой отмены.
Это показывает, что exact IR строже одного правильного смыслового направления.

**B.** Отдельная инвентаризация повышает попадание отдельных исходных цитат
до 18/38, но сама инвентаризация или следующий шаг добавляет дубликаты:
32 узла на 19 эталонных. У `credit_preview_new` один head породил два
направления, а разрешение предварительного просмотра повторилось трижды.
В `records_dev` B сохранил три из четырёх исходных цитат, но не собрал полный
scope. Форматный сбой одного `B_detail` сохранён как сырой ответ, не исправлялся
повторным вызовом.

**C.** OnionL-подобная декомпозиция не собрала ни одной конечной директивы.
Это не означает отсутствия промежуточных правильных частей: на hotel она
нашла scope платной брони и `ORDER`, но переписала дочерние действия в
символические имена `cancel_reservation` и `process_refund`, не являющиеся
буквальными фрагментами policy; рекурсия остановилась по `no_progress`.
В `records_dev` дерево содержит оба условия, но одно превращено в
синтетический атом `check_owner_approval(document_id) = approved`, а action
leaf цитирует весь пункт. Только **5/38** gold-цитат присутствуют даже в
промежуточных листьях C (диагностический подсчёт после прогона). Здесь
семантическая атомизация разрывает привязку к исходному тексту.

**D.** Селектор и специализированные парсеры делают больше локальных шагов,
но неверно выбирают внешний оператор для правил допуска: `records_dev` и
`parcel_handover_transfer` превращаются в business `ORDER` между проверкой
и действием. На hotel D действительно построил `ORDER`, нашёл буквальную
цитату отмены и правильные инструменты, но лист возврата не дал буквальной
цитаты, поэтому итоговое отношение осталось несобранным. На baggage и
telecom дерево `NOT(PERMIT(...))` не даёт само по себе доказанного
`FORBID` без дополнительной семантики модальности. Единственная выданная
директива D — безусловный запрет `issue a credit`; он потерял условие
одобрения и разрешение preview. В промежуточных листьях D были **9/38**
эталонных цитат: больше, чем у C, но недостаточно для полной сборки.

## Ответ на исследовательский вопрос

В **этом замороженном сравнении** адаптации C и D не дали преимущества над
адаптированным staged B по автоматическому полному IR. Они потратили примерно
в 3–4 раза больше вызовов, а более глубокая рекурсия усугубила две старые
проблемы: выбор управляемого действия и привязку нормализованного атома к
буквальному source span. Синтаксически правильная структура сама по себе
не обеспечивает семантическую полноту.

Это **не опровержение Req2LTL или NL2Logic**. C не использует недоступный
авторский код, few-shot базу и ручную визуальную коррекцию; D адаптирует
FOL-парсер к временным и инструментальным правилам Guardian. Восемь policy
ранее просматривались, остальные четыре придуманы нами; набор мал и не
скрыт. Строгое буквальное совпадение штрафует даже близкую цитату вроде
`the refund` вместо `the refund SECOND`. А/B тоже расширены до общего IR,
поэтому их цифры нельзя механически сравнивать с историческим V3 `0/12`.

Практический вывод для Guardian: **не повышать C/D в конкурсный рукав**.
Если исследовать эту линию дальше, необходим отдельный контроль, который
сохраняет для каждого рекурсивного узла offset исходного текста и разрешает
нормализацию только рядом с ним. Новый тест должен быть на невиданных policy
и заранее оговорить допустимые эквивалентные цитаты и `GATE`/условный запрет.
Текущие ответы нельзя превращать в точный verifier без такого контроля.
