# Парное сравнение четырёх способов разбора policy

Дата: 2026-09-27. Ветка: `codex/fast-followup-20260924`.

## Что проверяется

Вопрос: повышает ли **автоматическую полноту разбора всего исходного policy**
именно рекурсивный разбор по Req2LTL/OnionL или NL2Logic относительно нашего
staged-подхода? Это проверка компиляции policy, а не качества конкурсных
вердиктов на траекториях. `scripts/predict.py` не менялся.

Исходные 12 входов и ручной gold записаны в коммит `4962cf4` **до
первого вызова API**. Первый форматный пилот V1 выявил дефект интерфейса:
в JSON mode сервер возвращал валидный JSON, но поле `left` оказывалось
вложенным объектом вместо строки, а `D_select` — массивом вместо объекта.
Рекурсивные рукава обрывались почти сразу; их пилотные нули нельзя трактовать
как проигрыш алгоритмов. Сырые ответы V1 оставлены в отдельной директории.

Основной протокол V2 с явными JSON Schema для **всех четырёх рукавов**
зафиксирован в `226778c` до первого успешного ответа V2. Перед этим
одна попытка была отклонена API с HTTP 422: сервер потребовал поле `schema`,
а опубликованный пример SDK использовал `schema_definition`. Это была
валидация HTTP-запроса, результат модели не появился. После корректировки
формата и отдельного коммита протокол не меняется.
`frozen.json` содержит только policy, catalog и prompts;
`gold.json` открывает лишь scorer. Все четыре рукава идут по тем же policy и
тем же `ministral-14b-latest` с temperature=0 через Mistral API. Восемь
policy ранее просматривались в наших экспериментах, четыре придуманы для
контраста OR, истинного исключения, двух связанных действий и множества
инструментов. Поэтому это парное сравнение архитектур на **знакомых и
авторских** случаях, не независимая оценка переноса на скрытый конкурс.

Файлы: `experiments/searh_23/policy_architecture_abcd_v1.py` (общий раннер),
`experiments/searh_23/policy_architecture_abcd_v2.py` (основной протокол),
`experiments/searh_23/policy_architecture_abcd_v2/{frozen,gold}.json`, ответы и
per-case score в `outputs/searh_23/policy_architecture_abcd_v2/`.

## Что на самом деле перенесено из работ

### C — Req2LTL / OnionL

[Статья Req2LTL](https://arxiv.org/html/2512.17334), в особенности разделы
IV–V и Algorithm 1, описывает: сначала общий временной или mode scope
(по умолчанию `Globally`); затем рекурсивное выделение унарного scope,
внешнего бинарного отношения и атомов; структурную проверку OnionL и
детерминированный перевод дерева в LTL. Публичный
[репозиторий](https://github.com/Meng-Nan-MZ/Req2LTL) на момент проверки
содержал README и медиа, но не доступную реализацию транслятора. Поэтому C —
минимальное *воспроизведение алгоритма*, не запуск авторского кода.

У нас первая модельная операция отделяет global/mode scope, затем каждый
узел отдельно выбирает внешнее отношение, после чего атомный парсер
привязывает лист к буквальной цитате и роли. Код проверяет тип/арность,
ограничивает рекурсию и детерминированно собирает Guardian IR. В конечной
формуле используются `GATE`, `ORDER`, `PERMIT`, `FORBID`, `EXCEPT`, `EVEN_IF`,
`AND`, `OR` вместо чистого LTL: проверка действия, каталога инструментов и
различия `LATEST`/`PRIOR_TRUE` не выражается одной готовой LTL-трансляцией
из статьи. Визуальная ручная коррекция и few-shot база авторов не включены.
Статья реализует Building-OnionL как prompt-guided алгоритм построения JSON;
здесь рекурсивные шаги вынесены в отдельные API-вызовы. Это позволяет видеть
ошибку каждого шага, но не является побайтовым воспроизведением их prompts
или полным OnionL2LTL-транслятором.

### D — NL2Logic

[Статья NL2Logic](https://aclanthology.org/2026.findings-eacl.317/) и
[публичный код](https://github.com/peng-gao-lab/nl2logic) задают другую
последовательность: при необходимости перефразировать кванторы, на **каждом**
узле выбрать `atomic / quantified / logical / negation`, вызвать
соответствующий узкий парсер только для внешнего оператора, рекурсивно
обработать дети и детерминированно сгенерировать выражение из AST. Код
проекта ориентирован на FOL, Z3 и backend OpenAI/vLLM/Ollama; его готовый
`Pipeline` нельзя напрямую использовать для `MISTRAL_MODEL` и Guardian IR.
Поэтому D воспроизводит порядок вызовов и рекурсию, а атомный парсер и
компилятор заменены адаптерами к policy/tool-каталогу. SaT-разделитель не
запускался: каждый вход уже один короткий policy-пункт, а не документ.
Двухпроходная генерация деклараций Z3 неприменима к нашему типизированному IR.
У D есть доменная адаптация `BEFORE` и temporal-полей: исходный FOL-AST
проекта не описывает `LATEST` против `PRIOR_TRUE` из Guardian.

### Контроли A и B

A получает весь policy и сразу пишет тот же конечный IR. B сначала перечисляет
самостоятельные директивы, затем по одной достраивает их поля. B сохраняет
маршрут прежнего staged-парсера, но расширен до общего IR для сравнения;
поэтому его цифра здесь **не является повтором** прежних `0/12`.

Все рукава получают одинаковый исходный policy и catalog. Число API-вызовов
различается по алгоритму и отдельно показывается: преимущество по точности
без стоимости нельзя считать бесплатным. В C/D один и тот же атомный парсер;
разница между ними — порядок и способ построения дерева.

## Заранее заданная оценка

Для каждого случая считаем отдельно:

- `directive_match`: правильный вид и **буквальный action span** каждой
  самостоятельной директивы. Избыточные директивы видны отдельно.
- `scope_match`: при такой директиве правильно выбраны все исполняющие
  инструменты и общий контекстный scope.
- `logic_match`: совпадает форма AND/OR/NOT, буквальные условия и семантика
  `EXCEPT` против `EVEN_IF`; временная модальность атомов считается ниже.
- `temporal_match`: совпадают `LATEST`/`PRIOR_TRUE` на условиях или пара
  `BEFORE` для двух действий.
- `span_hit`: доля эталонных буквальных action/condition/before/exception/scope
  цитат, реально попавших в **итоговый IR**. Лист дерева, который не удалось
  связать с директивой, балл не даёт. Повторить весь policy
  одной строкой здесь не даёт автоматического зачёта отдельных цитат.
- `exact_ir`: полное совпадение множества директив и всех их полей; очень
  строгая метрика, поэтому частичные совпадения обязательны к показу.

Буквальные цитаты полезны для аудита, но строгий exact может занизить число
семантически эквивалентных формулировок. По каждому policy ниже и в `score.json`
даны найденные и лишние узлы, пропущенные цитаты и ошибки исполнения.

## Результаты

Заполнить после одного замороженного прогона, без изменения prompts или gold.
