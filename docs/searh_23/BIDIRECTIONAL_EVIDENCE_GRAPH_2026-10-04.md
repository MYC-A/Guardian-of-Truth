# Двунаправленный граф исходных свидетельств

Дата: 2026-10-04. Ветка: `research/bidirectional-evidence-graph-20261004`.
Основа: `64f48c5a`. Работа выполнена в отдельном worktree.

## Что реализовано

Новый пакет `src/guardian_truth/evidence_graph`:

1. Код определяет настоящие вызовы в текущем ответе, их исполнителя и аргументы.
2. Весь системный текст разбит на точные окна с контекстом соседей. Это окна
   показа, а не утверждение о границах самостоятельных правил. Сохранены все
   символы, включая текст после `[AVAILABLE TOOLS]`.
3. Модельные задачи разделены: инвентаризация одного окна; эффект и объект одного
   инструмента; применимость одного требования к одному действию; свидетельство
   для одного атомарного условия. Объект описывается свободным текстом по исходной
   декларации. Словарей под названия инструментов, домены и конкурсные ID нет.
4. Прямой поиск задаёт порядок проверки. Обратный проход проверяет все извлечённые
   требования, включая окна с нулевым лексическим совпадением. Полнота этого
   прохода не доказывает, что извлекатель нашёл все требования.
5. Сохраняются открытые вопросы, неподдержанные узлы формулы и незакрытая
   применимость. Известная неопределённость не исчезает через `DOES_NOT_APPLY`.
6. Используются исходная топология, зарегистрированные факты и точное совпадение
   типизированных значений как связи поиска. Обход BFS/DFS возвращает исходные
   источники. Эти связи не означают владение, успешное действие или согласие.
7. Проверка условия видит реестр всего префикса истории; может запросить точный
   более ранний фрагмент. Число запросов чтения и повторных раундов ограничено;
   исчерпание возвращает `READ_BUDGET_EXHAUSTED`. Нет ограничения последней парой
   сообщений. Свидетельства после проверяемого вызова отклоняются.
8. AND/OR/NOT, before/after, guard и исключения считаются трёхзначной логикой.
   Неизвестный guard или необходимое исключение оставляют `UNKNOWN`.
   Исключения сохраняются при своём правиле. Неуспех разрешающего условия сам
   по себе не превращается в запрет.
9. Числовые/типизированные сравнения по native JSON может пересчитать код.
   Проверяются уникальная связь вызов–результат, явные joins, родительская сущность,
   выбранная запись и актуальность наблюдения для связанной сущности. Цитаты
   констант должны принадлежать конкретному атомарному условию. Полный JSON,
   прочитанный кодом, отдельно записывается в `code_source_reads` с исходными
   позициями; короткая цитата не выдаётся за прочтение всей записи моделью.

`scripts/predict.py` и прежние замороженные рукава не изменялись. В пакете и
offline runner нет клиента HTTP и режима запуска сетевых запросов.

## Что взято из исследований

- [GraphReader](https://aclanthology.org/2024.findings-emnlp.746/): поиск через граф,
  возврат к исходному фрагменту, соседнему контексту и дополнительное чтение.
  Это перенос механизма навигации, а не воспроизведение его QA-агента/результатов.
- [GraphRAG](https://microsoft.github.io/graphrag/index/default_dataflow/): локальное
  извлечение со ссылками на текст и объединённый индекс. Здесь не применяется
  объединение разрешений или операций по одному названию сущности.
- RAPTOR, эмбеддинги и LangExtract не подключались. Для текущего структурного
  опыта дополнительных зависимостей сверх уже установленного Pydantic не нужно.

## Проверенные результаты — только механика

- 41 новая проверка структуры, источников, логики и offline runner проходит.
- Вместе с 32 проверками V5 и 19 проверками SourceStore: **92 passed**.
- Все 46 исходных входов public46 обработаны без модельных вызовов.
- **359 окон** покрывают все символы системных событий: 100% покрытия исходного
  текста по конструкции. Это не полнота смыслового разбора.
- Первый этап: **383 логических задания, 47 разных запросов**: 31 инвентаризация
  окна и 16 извлечений эффекта. Одинаковые запросы переиспользуются только при
  точном совпадении сообщений и схемы, внутри того же замороженного протокола.
- LINK/WITNESS создаются после получения ответов предыдущих этапов. Число 47
  относится только к первому этапу, а не к стоимости всего опыта.
- Новых HTTP-попыток: **0**. Новые токены моделей: **0**.

Контроли включают чужую родительскую сущность, свидетельство из соседней записи,
неоднозначное спаривание, более новый невалидный результат, более новый результат
другой сущности, константу другого условия, malformed call, строгие bool/number
различия, будущий результат, незакрытое исключение, позднее перечитывание,
подмену источника и неподходящий кэш. Для этих тестов интерпретации заданы вручную;
они не доказывают качество автоматического извлечения или понимание согласия.

## Точный знаменатель

Новый слой проверяет **37 native calls в текущих ответах**, расположенных в
**23 из 46 строк**. Остальные 23 строки не получают решения о текстовом ответе.

Предыдущие 84 цели consent probe имели другой состав: 59 исторических + 25
текущих вызовов. Там исключались объявленные READ и необъявленные инструменты.
Новый инвентарь содержит все прежние 25 текущих вызовов, ещё 3 READ и 9
необъявленных. Исторические вызовы здесь доступны как свидетельства, но не
считаются дополнительными проверенными целями.

В replay без модельных ответов все 37 текущих вызовов остаются UNKNOWN вследствие
неполученных инвентаризаций/эффектов. Это ожидаемое отсутствие вывода; переносить
его в метрику ложных отрицаний или точности нельзя.

## Ограничения, которые сохранены явно

- Точные позиции подтверждают происхождение текста, но не смысл отношения.
  `candidate_decision` имеет режим `SHADOW_MODEL_SEMANTICS`, `code_proof:false`.
  Даже пересчитанный native факт не доказывает правильность его привязки к policy.
- Модель может полностью пропустить директиву внутри просмотренного окна.
  `units_reviewed` — учёт обработки; `semantic_completeness_proven` всегда false.
- Истинность prose-согласия, полнота его параметров и интерпретация `NEW_REQUEST`
  ещё не проверены новой модельной серией. Здесь нет нового доказательства TRUE
  на 19 consent-целях и нет улучшенной конкурсной TP/FP/FN-метрики.
- Формальная граница последней декларации инструмента может включать последующую
  policy-прозу. Её семантическая граница не доказана; это отражено в EFFECT
  packet, отчётах и протоколе. Domain regex для её угадывания не добавлялся.
- Успешная попытка вызова и успешный эффект различаются. Native receipt и время
  появления результата подтверждают событие, но сами по себе не успех.
- Полный автоматический разбор сложных ссылок/общих условий не завершён.
  Неразобранная часть остаётся в ledger; inventory пока не имеет отдельного
  модельного этапа пересборки после дополнительных чтений.
- JSON Schema экспортируется. Её соблюдение генератором требует поддержки
  backend; обычная проверка ответа не заменяет constrained decoding.

## Воспроизведение

```powershell
$env:PYTHONPATH = (Join-Path (Get-Location) 'src')
python -m pytest tests/test_evidence_graph.py tests/test_policy_table_v11_consent_pair_v5.py experiments/searh_23/source_search_20261002/test_source_search.py -q
python experiments/searh_23/evidence_graph_v1/offline.py replay --arm bidirectional
python experiments/searh_23/evidence_graph_v1/offline.py replay --arm forward
```

Готовые запросы/протокол: `outputs/searh_23/evidence_graph_v1_sealed/`.
У prepare есть `--strategy BFS|DFS`, `--chunk-chars`, `--model` и `--out`.
Чтобы зафиксировать модель, нужно создать новый каталог протокола с её именем
до получения ответов. Текущий протокол имеет модель
`NOT_SELECTED_NO_API_AUTHORIZATION`.

Файл ответа для offline replay должен содержать ровно:

```json
{
  "protocol_sha256": "hash from protocol.json",
  "request_sha256": "hash from the exported request",
  "model_id": "same as protocol",
  "reply": {}
}
```

Replay принимает `--cache PATH`, проверяет протокол, исходники, входы и имя модели,
сохраняет ошибки и экспортирует следующий набор запросов. Несовместимые прежние
consent-ответы не используются. После подготовки исходники не корректируются в
том же протоколе; исправления требуют нового протокола и каталога.

Хэши Python-исходников нормализуют CRLF к Git-каноническому LF; сами входные
строки и их позиции не нормализуются. Артефакты пишутся с LF, версия Pydantic
закреплена в протоколе. Это предотвращает ложный сбой переноса Windows → Linux
и незаметную замену генератора JSON Schema.

Следующий опыт: одна выбранная модель, одинаковые источники/извлечённые требования,
forward top-4 против полного reverse sweep; отдельно варианты BFS/DFS. Это
абляция навигации и связности, а не сравнение с текущим конкурсным детектором.
Считать отдельно пропущенные директивы, ошибочную применимость, AND/OR/exception,
temporal, неправильные entity joins, открытые вопросы и итоговые TP/FP/FN после
независимой разметки. Для проверки текстовых ответов понадобится отдельный этап
выбора утверждений. Новые API-прогоны не запускались: действует указание
«Пока только исправления без новых API».
