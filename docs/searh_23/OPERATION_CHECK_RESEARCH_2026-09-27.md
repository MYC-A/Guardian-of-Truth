# OPERATION_CHECK_RESEARCH_2026-09-27 — semantic role of policy events

Ветка: `codex/fast-followup-20260924`. Дата: 2026-09-27.
Код и артефакты: `experiments/searh_23/operation_check/` (код, frozen),
`outputs/searh_23/operation_check_v1/` (raw outputs, score, analysis).

## 1. Проверяемая проблема

Предыдущие линии (one-shot A, staged B, рекурсивные C/D, source-first E,
Req2LTL/OnionL, NL2Logic) сошлись в одном месте: парсер находит фрагменты,
но не может надёжно определить, какой фрагмент является регулируемым
бизнес-действием, какой — проверкой/предусловием, какой — наблюдением
состояния, и к какому действию привязано условие. Source offsets решили
provenance, но не semantic role. Это исследование проверяет, помогают ли
НЕ-LLM-методы (dependency parsing, AMR, SRL) и grounding по каталогу
инструментов (embedding / cross-encoder / NLI / узкий LLM-вопрос), и
проверяет гибридную архитектуру: структура → кандидаты-события →
grounding по описаниям инструментов → роль → только потом привязка.

## 2. Замороженный протокол (до инференса)

- **20 новых авторских политик**, 20 доменов без повторов прошлых сьютов
  (ветклиника, водоочистка, библиотека, кран, авиация, ДЦ, телеком,
  железная дорога, кухня, электросеть, архив, таможня, аптека, payroll,
  биотех, шахта, мусоровоз, страхование, карантин, элеватор).
  16 конструкций: check-before, only-if, after-then, requires-and/or,
  observe-then, confirmation-before, A-before-B, may-but-forbidden,
  unless, even-if, multiple-ops, multi-checks-one-op, shared-check,
  descriptive-noop, communication-obligation.
- **Каталоги инструментов** с description + input/output schema; в каждом
  каталоге — негативные пары §12: операция vs аудит-лог, мутация vs
  чтение того же объекта, request-created vs completed, misleading имя
  (`execute_blast_sequence` = инструмент только ЧИТАЕТ план), observation-only.
- **Gold (75 событий, 33 ребра)**: `candidate_events` {source_span, role,
  governed_tools} + `condition_edges` {condition_span, operation_span,
  relation}. Роль = природа события; contrast-предложения дают внутренний
  акт без рёбер; «X before Y» → GATE, если X — проверка/наблюдение/подтверждение,
  ORDER_BEFORE, если X — операция.
- **Renamed-сьют**: tool_xNN + непрозрачные коды сущностей, описания/schema
  не меняются, gold пересчитан программно. Гарантия устойчивости к
  переименованию — часть оценки.
- Коммиты заморозки ДО инференса: `77bad90a` (протокол+gold),
  `f5bb480a` (уточнение конвенций до инференса), `63cdd017` (раннеры),
  `10413529` (mini-сет для §15-валидации пост-хок фиксов, 10 новых
  доменов, 36 событий, 18 рёбер — тоже до прогона).
- Раннеры не читают gold; компонентные входы — отдельный файл только со
  спанами; relation-диагностика — oracle-endpoint по дизайну (§10).

## 3. Окружение и библиотеки

main venv (python 3.12, RTX 3090): torch 2.10.0+cu128, transformers 5.16.1,
sentence-transformers 6.0.1, stanza 1.14.0 (GPU). amr_env (3.12, CPU):
amrlib 0.8.1 + model_parse_xfm_bart_large (83.7 SMATCH) + RBW aligner,
transformers 4.46.3, torch 2.14.0+cpu. srl_env (3.10, CPU): allennlp
2.10.1 + allennlp-models, structured-prediction-srl-bert.2020.12.15,
torch 1.12.1+cpu, numpy 1.23.5, spaCy 3.3.3. Модели grounding:
BAAI/bge-base-en-v1.5, BAAI/bge-reranker-base, cross-encoder/nli-deberta-v3-base
(лицензии MIT/Apache-2.0; веса AMR — LDC-derived, исследовательское
использование). API: Mistral (ключ в env, не выводится), Ministral-14b и
Codestral-latest; **все модели класса medium/small/magistral на этом
тарифе отвечают 429 (code 1300) даже на одиночный запрос после паузы** —
это ограничение тарифа, задокументировано; keyless-канал blockrun
(nvidia/nemotron-3-super-120b) волатилен и для полноценного прогона
непригоден (проверено). Сильным контролем назначен codestral-latest —
самая сильная стабильно доступная модель.

## 4. Arms

A — Mistral-14b one-shot на компонентной задаче (события+роли+инструменты+рёбра).
B — stanza UD: клаузальные кандидаты + NP-аргументы, closed-class
подчинители, гипотеза роли из структуры. C — AMR (amrlib BART-large) +
RBW-выравнивание. D — PropBank SRL (allennlp BERT). E — bge-base
embedding grounding (name-blind by design). F — bge-reranker cross-encoder
(name-blind). G — NLI (nli-deberta): pair-labels «инструмент реализует/
проверяет/наблюдает/коммуницирует спан» + probe типа инструмента. A2 —
Mistral narrow pair-классификация (gold-спан × инструмент). I/I2 — то же
на codestral-latest. relation / relation_strong — §10 oracle-endpoint
диагностика связи. H — замороженный гибрид: B-кандидаты → NLI-роль →
привязка по UD-маркам и аргументной структуре. H+ — тот же H с LLM-
резолвером UNKNOWN. **H2 (пост-хок)** — B-кандидаты → top-3 инструмента
по reranker → один узкий LLM-вопрос на кандидата; валидирован ТОЛЬКО на
новом mini-сете.

## 5. Результаты: основной замороженный набор

### 5.1 Обнаружение и классификация событий (75 gold)

| Arm | span-совпадения | роль верна | check→OP (ложные повышения) | recall ролей: OP / CHECK / OBS / COMM |
|---|---:|---:|---:|---|
| B dependency | 61/75 (81.3%) | 32 (42.7%) | 10 | .68 / **.00** / .15 / .00 |
| C AMR (IoU) | 4/75 (5.3%) | 4 | 0 | .09 / .00 / .00 / .00 |
| D SRL | 63/75 (84.0%) | 28 (37.3%) | 15 | .64 / **.00** / .00 / .00 |
| A Mistral e2e | 66/75 (88.0%) | **53 (70.7%)** | 2 | .77 / .50 / .85 / .40 |
| I codestral e2e | 65/75 (86.7%) | 46 (61.3%) | 2 | .68 / .50 / .46 / .60 |
| H гибрид (NLI) | 61/75 (81.3%) | 10 (13.3%) | 0 | .14 / .11 / .15 / .00 |

Ключевой структурный факт: **у B и D recall проверок = 0**. Синтаксис
(UD-дерево, PropBank-аргументы) не отличает «проверь температуру» от
«отправь результат» — оба выглядят как действия с ARG0/ARG1. Различие
живёт не в дереве, а в семантике инструмента.

### 5.2 AMR-компоненты (§8, containment-метрики)

Операция присутствует в AMR: **95.5%**, проверка: **100%**, наблюдение:
76.9%, коммуникация: 100% — AMR находит события на уровне концептов.
Но: relation preserved **15.2%** (AMR :condition/:time не переводятся в
policy-связи), выравнивание — токен-анкеры (78.1% узлов), фразовые спаны
AMR не даёт (IoU-совпадения 4/75). Деонтику (obligate-01/possible-01)
AMR в меру сохраняет, но GATE/ORDER из неё не извлекается.

### 5.3 Grounding событий по каталогу (gold-спаны, 75)

| Arm | top-1 верный | top-3 | check-событие → мут. инструмент | неверный инструмент операции |
|---|---:|---:|---:|---:|
| E bge-base | **68/75 (90.7%)** | 72/75 | **0/23** | 4/44 |
| F bge-reranker | 66/75 (88.0%) | 72/75 | **0/23** | 6/44 |
| G NLI | 46/75 (61.3%) | 68/75 | 5/23 | 18/44 |
| A2 Mistral pairs | pair-acc 68.0% (поз. 70.8%, UNREL 67.4%) | — | FP 96/294 | — |
| I2 codestral pairs | pair-acc 53.0% (поз. 55.6%, UNREL 52.4%) | — | FP 140/294 | — |

NLI-probe типа инструмента по описанию: **24.7%** (mutate 9/44,
read 7/41) — NLI не восстанавливает «мутация vs чтение» из текста
описания. Зато E и F **ни разу** не заземлили проверочное событие на
мутирующий инструмент (0/23) — семантическая близость НЕ повышает CHECK
до OPERATION при grounding по описанию. У LLM-arms на совпавших
событиях инструменты тоже всегда корректны (A 35/39, I 33/36,
check→mutate 0).

## 9. Отрицательные находки (не сработало)

1. **NLI-роли**: pair-labels путают CHECKS/OBSERVES и чувствительны к
   формулировкам («before dispensing…» → ungrounded); H = 13.3% ролей.
2. **NLI-тип инструмента по описанию**: 24.7% — «мутация vs чтение»
   текстом описания NLI не извлекается.
3. **Relation-only 15/16 не воспроизводится** (52-58%), NONE-пары почти
   не распознаются (16-25%).
4. **LLM pair-классификаторы избыточно позитивны**: 96 (ministral) и
   140 (codestral) ложных связей на 294 нерелевантных парах.
5. **Codestral хуже ministral** на узкой pair-задаче (53% vs 68%) и
   чувствительнее к переименованию.
6. **AMR-отношения не переводятся** в policy-связи (15.2%),
   выравнивание токенное.
7. **Правило H «ungrounded→OTHER»** погубило 20 реальных операций
   (span с маркером «before …» не заземляется).
8. **Средний класс моделей Mistral недоступен** тарифу (429/1300 на
   любой запрос) — сильный контроль ограничен codestral.
9. **Синтаксическая роль**: check-recall B/D = 0 — tree/аргументы не
   кодируют «проверка vs операция».
10. **Пере-привязка LLM-e2e**: 22 лишних ребра у A (условия лепятся к
    контрастным/запрещённым действиям).

## 10. Ответы на вопросы

**Q1. Помогают ли dependency/AMR/SRL обнаруживать operation/check лучше LLM?**
По ОБНАРУЖЕНИЮ спанов — сопоставимо или лучше (B 81%, D 84% против A 88%;
AMR по containment находит 95.5% операций). По КЛАССИФИКАЦИИ роли — нет:
check-recall B и D = 0%, AMR тоже не различает. Синтаксис даёт отличных
кандидатов и excellent mark-based рёбра (B: 19/33 всего с 3 лишними), но
роль из дерева не извлекается. Вывод: парсеры — источник кандидатов и
связей, не ролей.

**Q2. Насколько tool descriptions/schema помогают выбрать бизнес-операцию?**
Это самый сильный сигнал во всём исследовании: top-1 grounding 90.7%
(embedding), 88% (cross-encoder) на основном наборе и 97.2% на mini;
ни один description-based arm ни разу не заземлил проверку на
мутирующий инструмент (0/23 и 0/12). Прежний oracle-факт (20/22 при
gold action) обобщается: понимание каталога — надёжная способность.

**Q3. Что лучше для event↔tool grounding: embedding, cross-encoder, NLI или узкий LLM?**
Embedding (bge-base) > cross-encoder (bge-reranker) >> NLI (61%) и
узкий LLM (68% ministral; 53% codestral). При этом узкий LLM даёт
метку роли, а ранжирование — только инструмент; NLI не даёт ни того,
ни другого надёжно. Практический выбор: reranker/embedding для выбора
инструмента + один узкий LLM-вопрос для роли (схема H2).

**Q4. Устойчивость к переименованию инструментов?**
Структурные и name-blind grounding-армы — полностью стабильны.
Ministral-e2e — стабильна (53→53): не опирается на имена. Codestral —
деградирует (46→39 ролей): частично использует имена. Результат,
исчезающий после rename, в этом исследовании — только у codestral.

**Q5. Решает ли сильная LLM узкую задачу значительно лучше Ministral?**
Проверить «существенно более сильную» модель не удалось: тариф Mistral
блокирует весь medium-класс (429/1304), keyless 120B-канал нестабилен.
Codestral-latest (максимум тарифа) лучше по ПРИВЯЗКЕ (30/33 vs 23/33
рёбер, меньше лишних), но хуже по узкой pair-классификации (53% vs 68%)
и теряет точность при переименовании. Обе модели одинаково проваливают
relation-only и NONE-пары — часть проблемы глубже уровня модели.

**Q6. Остаётся ли relation-only простым этапом после правильного grounding?**
Нет. 15/16 не воспроизводится: 51.5% (ministral) / 57.6% (codestral) на
gold-парах, 16-25% на NONE. Ошибки сосредоточены в GATE vs ORDER_BEFORE
vs ORDER_AFTER — ровно та гранулярность, которой не было в старом
16-кейсовом опыте. Relation-typing — самостоятельная нерешённая задача.

**Q7. Есть ли комбинация, готовая к интеграции?**
Для РОЛИ — да, с оговоркой: H2 (структурные кандидаты + reranker top-3 +
узкий LLM-вопрос) на новом mini-сете даёт 66.7% ролей, 0 ложных
повышений CHECK→OP и 100% верных инструментов — лучше замороженного
A (63.9%, 2 повышения) при лучшем CHECK-recall (.375 vs .125). Для
ПРИВЯЗКИ условий — нет: структурная привязка консервативна (6/18),
LLM-привязка пере-генеративна (11 лишних). Честный интеграционный вывод:
использовать гибрид для ролей и инструментов с UNKNOWN-гейтом на
привязке; не повышать в конкурсный детектор без отдельного
end-to-end-доказательства.

## 11. Ограничения

Авторский набор (n=20 + 10) небольшой и один; метрика спанов строгая
(L1/IoU≥0.5); gold-конвенции (роль=природа, contrast-предложения без
рёбер, направление «before») зафиксированы, но являются выбором
разметчика; «сильная модель» — codestral (33B MoE, код-ориентированная),
не medium-класс; I2_pairs на renamed-сьюте завершён частично (195/366
вызовов на момент отчёта — числа по нему предварительные для
переименованных пар); cost-by-price не приводится точно (цены
меняются), приведены токены и вызовы. `scripts/predict.py` не менялся;
конкурсный детектор не затронут.
