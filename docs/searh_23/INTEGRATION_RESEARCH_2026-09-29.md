### 1. Совпадение действия не означает совпадение объекта

`compatible_nodes` v10 принимает все четыре ошибочные пары:

- `Load wagon 12` / `Load wagon 13`;
- `Inspect panel A` / `Inspect panel B`;
- `Scan parcel ZX-41` / `Scan parcel ZX-42`;
- `Drain tank 3 on Monday` / `Drain tank 3 on Tuesday`.

Причина: общий глагол и хотя бы одно общее содержательное слово считаются
совместимостью; противоречащие идентификаторы и модификаторы не блокируют
совпадение. Эту же функцию используют для подавления пар и объединения рёбер.
Внутренняя consolidation имеет ещё один путь с таким же критерием.

Добавлен отрицательный scope gate, включая проверку **всех** членов перед
объединением кластеров. Он не является доказательством положительной
кореференции. Контроли совместимости: **4/8 → 8/8**. Перестроение узлов на
30 старых F/F2/F3/F4 не изменило ни одного состава узлов; это регрессия
инвентаря, не новый результат всего downstream.

Опция `W1_SCOPE_GUARD=1` требует отдельного `W1_RUN_OUTPUTS`, чтобы не
переписывать замороженный v10. Без опции старый путь сохранён.

### 2. Реальное значение результата не доказывает его произвольное название

Legacy Step 2 проверяет путь, значение и ID, но затем копирует из предложения
модели `predicate`, `strength` и `is_observation`. В контролях прошли:

- `$.status="completed"` → `unit.replaced` без контракта о замене;
- тот же self-report → `CONFIRMED` без независимого подтверждения;
- `is_observation=True` → авторитет `READ_OBSERVATION` без подтверждённого типа инструмента;
- ответ другого инструмента с тем же `call_id`;
- `contract_bound=True` → обход отсутствующего ID в результате.

В старом witness приняты **5/7 опасных предложений**; ещё один контроль —
корректное копирование поля. Это реальные исполняемые контрпримеры, а не
претензия к формулировке отчёта.

Оценщик `_match_fact` принимает **predicate OR provenance path**, а ошибки
strength учитывает отдельно от precision. Поэтому `P=1.0` показывает
воспроизводимость полей источника, но не полноту семантического доказательства.

Пересчёт сохранённого test без inference и изменения gold:

| рукав | совместно точные predicate/entity/value/strength/provenance | precision | recall |
|---|---:|---:|---:|
| F structural | 7/16 | .4375 | 7/19 = .3684 |
| H witnessed LLM | 9/17 | .5294 | 9/19 = .4737 |
| I oracle contracts | 11/11 | 1.000 | 11/19 = .5789 |

Это **строгая точность полей**, не оценка «доли фактически ложных утверждений»:
часть различий predicate может быть соглашением о названии. Старые scores
сохранены. Gold не содержит `observed_at` для каждого факта; новый оценщик
явно сообщает этот недостаток и не утверждает, что проверил неразмеченное
время. Максимальное взаимно однозначное сопоставление не даёт дубликатам
дополнительного зачёта.

## Новый интерфейс композиции

```text
Step 1: policy → proposed events / scoped endpoint certificates
                       ↓ semantic rule binding is still a separate gate
Transport: unique call/result pair + producer version + exact JSON path
                       ↓
ResultObservation: источник действительно сообщил это значение
                       ↓ separately supplied ReviewedBinding
WorldFact: названное условие, типизированный объект, гарантированная сила
                       ↓ Step 2 append-only ledger
ReviewedRule + target call → full scope join → latest BEFORE target
                       ↓
CONDITION_SATISFIED / VIOLATION / UNKNOWN / NOT_APPLICABLE
```

`step2/trusted.py` разделяет сырое наблюдение и семантический факт. Ни один
модельный флаг не назначает авторитет и не отменяет проверку ID. Проверяются
членство событий в траектории, уникальность пары, одинаковый инструмент,
роль, порядок, полный путь, типизированное значение и равенство объектов.
Источник ограничен позицией инструмента в каталоге и hash его описания,
схемы/версии. Rename имени сохраняет scope; изменение контракта — нет.
Одинаковые описания у разных производителей не объединяют их.

`integration/runtime.py` использует настоящий ledger Step 2. Сначала
соединяет **все** измерения scope (например, объект и сумму), затем выбирает
последнее подходящее наблюдение. Новое одобрение для суммы 70 не затирает
одобрение для суммы 50. Более новое наблюдение с неизвестной суммой приводит
к UNKNOWN. Результаты после действия не могут оправдать это действие.

Контракты `ReviewedBinding` и `ReviewedRule` предоставляет доверенный
вызывающий код; строка `MODEL_CONFIDENT` отклоняется. Это граница доверия,
а не автоматическая проверка истинности произвольного контрактного текста.
Тестовые контракты ENV_TESTED относятся к авторским fixtures и не
переносятся автоматически на реальные инструменты.

**Граница вывода:** J — четыре новые авторские пары с одним и тем же видом

Старые 30 случаев не изменились по инвентарю узлов; downstream на них не
пересчитывался. Положительный результат J не покрывает политику с исключением,
общим условием у двух действий или неявным объектом.

Текущий `RuntimeProofLayer` работает, когда доверенный контракт и правило уже
заданы. Он не доказывает отсутствие обязательного события по неполной истории:
если подходящего свидетельства нет, возвращается `UNKNOWN`. Следующий узкий
эксперимент должен отдельно проверить автоматическое получение полных
rule/contract bindings и полноту траектории. Только затем можно сравнивать
конкурсный детектор с базой на независимых случаях.
