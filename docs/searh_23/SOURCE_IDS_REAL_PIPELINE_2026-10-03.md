# Возвращаем исследование к реальным длинным входам

Ветка `research/source-search-20261002`, отдельный worktree. Аудит
`A:\GIS_Загрузки\Guardian_System_Audit_2026-10-02.md` требует сначала устранить
потери в основной цепочке и пройти реальные случаи, затем исследовать модели
и формализацию. Предыдущий ответ о доступности Horde не изменял систему;
этот шаг продолжает незавершённую основную задачу.

## Исправленные дефекты цикла

1. Ключ продолжения страницы включал `limit`, а ключ окна — `end/expand`.
   Следующее корректное чтение с большим окном не закрывало старый remainder.
   Эти параметры теперь относятся к окну выдачи, а не к смыслу запроса;
   фильтры, source ID, тип сущности и значение сохраняются в ключе.
2. `get_open_questions` возвращал весь исходный список после частичной оценки.
   Теперь вопросы обновляются по проверкам с валидированной provenance;
   OPEN возвращается в очередь. Это модельная отметка проверки, не доказательство
   истинности условия. Дополнительно возвращается копия списка: сохранённая
   трасса больше не меняется при последующих закрытиях вопросов.

## Новый отдельный интерфейс оценки

`id_contract.py` использует **тот же** цикл read-only поиска, графа и вычислений.
Модель выбирает event/quote IDs; код формирует дословные цитаты. Находка обязана
указывать реальный latest event, а не прежний вызов. Все пять проверок имеют
явные статусы в объекте с фиксированными ключами. UNKNOWN и материальные пробелы
сохраняются; поле CHECKED не доказывает смысловую правильность.

Первоначально выдаются:

- полный распознанный SYSTEM для поискового рукава;
- полный target и фактический инвентарь native calls из парсера;
- реестр event IDs с ролью и исходными offsets;
- краткий граф, который не ограничивает полный индекс.

Прямой рукав получает полный исходный контекст и тот же source-ID контракт.
Поисковый рукав раскрывает источники последовательно и может продолжить поиск
после запроса судьи. BFS/DFS и Decimal/date вычисления — те же реальные
операции полного индекса; инструменты оцениваемого диалога не исполняются.

Новый opt-in профиль `source-search-ids-v2` подключён к service runtime.
Старые работающие процессы и `scripts/predict.py` не изменены. Исследовательский
source-ID reviewer не подключён: на просмотренных случаях он подтверждал
ложные обвинения. Свободный DAG-компилятор также не включён.

## Приёмка на полном реальном наборе без модели

`comparison_ids_v2/mechanical_acceptance.json`: **92/92 прохода** — 46 входов
через direct/search service dispatch. HTTP-вызовов 0: после структурного слоя
инъецирован явно отключённый model stub. Все исходные строки сохранились;
каждый неструктурный случай дошёл до stub, минуя прежний ранний budget reject.
Максимальный первоначальный payload **417 040 UTF-8 bytes**. Новое ограничение
800 000 bytes пропускает этот payload, но не является гарантией окна провайдера.
При отказе провайдера case и причина сохраняются, новый большой контекст не
обрезается тайно.

Отдельный **механический**, а не новый семантический TP, контроль на настоящем
retail__48::t4 сохраняет заданную ERROR-гипотезу через code-generated source IDs.
Это не replay старого правильного LLM-ответа и не оценка качества retail__48.

44 регрессии (19 source, 18 typed scope, 7 новых integration) проходят локально.
Новые тесты воспроизводят оба дефекта, проверяют историю/target, сохранение
source ID, обязательные OPEN-проверки и фактический target call inventory.

## Замороженное сравнение

`comparison_ids_v2/frozen.json`, `inputs.jsonl`; 46 одинаковых реальных входов,
92 результата. Сначала шесть **исторических регрессий**, затем оставшиеся 40.
Приоритетные имена используются только для расписания, в runtime правил по ID нет.
Один GPT-OSS:120b через Ollama, одни checks, один structural layer, один ledger.
На неструктурный случай: максимум 1 direct + 6 search HTTP; на structural — 0.
Верхняя граница полного протокола **322 попытки** до учёта structural bypass.
Алгоритм замораживается до API; публичный gold открывает отдельный scorer.
Public46 многократно просмотрен: это регрессия, не независимый перенос.

Сначала допускается один короткий paired контроль в остатке уже разрешённых
1 200 000 / 350. На момент подготовки в ledger 1 144 171 / 1 200 000 и
251 попытка. Остаток **55 829** не покрывает полный набор: один самый длинный
direct payload резервирует больше этого значения. Для полного сравнения
необходимо отдельное увеличение общего предела; прежние counters не сбрасываются.

предохранителем первого 402/429, без polling/retries. Это потолок, не обещание
израсходовать его полностью.

## Что ещё не доказано

- Реальный LLM выбрал релевантную текущую дату/рейс и правильные операнды.
- Сам последовательно нашёл второй заказ и проверил его допустимость.
- Верно связал поисковые обязанности banking с latest transfer.
- Все 46 дали валидную модельную оценку, а не UNKNOWN/ошибку провайдера.
- Качество/стоимость улучшились относительно direct; есть перенос на
  новых длинных сценариях с независимо проверенными метками.

Прежние source-index механизмы подтверждены отдельной real-input приёмкой:
оба заказа доступны, banking text results индексируются, 75% вычисляется из
исходных сумм, airline dates доступны literal extractor. Это доступность и
работа вычислителя; критерии выше требуют полноценной модельной трассы.
