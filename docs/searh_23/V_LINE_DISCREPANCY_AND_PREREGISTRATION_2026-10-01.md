## 1. Почему V3 ≡ V1: равенство было предопределено ВЗВЕШИВАНИЕМ, а не качеством второго семейства

V3 = structural-shortcut ∨ majority(2×gemma seeded + 1×mistral greedy):

* семейство gemma получало **2 из 3 голосов**;
* измеренное внутри-семейное согласие seed101 vs seed102 = **38/38 = 1.000**
  (все валидные пары) — повторные вызовы одной модели НЕ являются
  независимыми свидетельствами;
* следовательно пара gemma всегда образовывала большинство, и решение V3
  на каждом кейсе с валидными голосами gemma совпадало с решением
  одиночного gemma-судьи (V1);
* структурный shortcut (5 подтверждённых structural-кейсов, label=1 без
  голосования) и кворум-fallback (одни и те же 3 кейса невалидных голосов)
  были идентичны в V1 и V3.

Равенство V3=V1 (TP17 FP0 FN6 TN23, F1 .8500 у обоих) — свойство
КОНСТРУКЦИИ голосования, а не экспериментальный результат о бесполезности
mistral-канала. Кроме того, важная поправка к интерпретации «V1 — точный
канал TP17/FP0»: **официальный V1 = structural_confirmed ∨ gemma-голос**;
чистый gemma-канал (только валидные голоса) — это TP12 FP0 при покрытии
38/46 (5 кейсов закрыты структурным shortcut, 3 — невалидные голоса).

Никакой победитель не объявляется: OR-объединение двух LLM-семейств с
структурным каналом на сожжённом наборе численно совпадает с
историческим контрольным OR (TP20), но с +1 FP; профиль «OR всех
семейств» — обмен точности на полноту. Диагностика зафиксирована только
как мотивация пре-регистрации правила комбинирования.

Границы правила «двое судей + третий проверяльщик при расхождении»
(на 28 кейсах общего покрытия; 23 согласия, 5 расхождений):
* идеальный третий проверяльщик: P 1.000 / R 1.000 / F1 1.000
  (верхняя граница на покрытии);
* третий всегда-0: P 1.000 / R .778 / F1 .875;
* третий всегда-невпопад (adversarial): P .700 / R .778 / F1 .737.
Реальная ценность дизайна определяется тем, попадает ли фактический
третий проверяльщик в верхнюю часть этого диапазона на свежих данных —
что и проверит holdout (протокол §6).

### V0.1 (пре-регистрирован ДО инференса на holdout)

Три механических правила с дословным основанием:
* **R1** `policy_one_call_violation`: ≥2 tool call в целевом ходе ПРИ
  наличии в политике этого кейса дословной клаузы «one tool call at a
  time» (клауза цитируется в basis; домены без неё не помечаются);
* **R2** `policy_text_and_call_violation`: проза + tool call в одном ходе
  при той же клаузе;
* **R3** `schema_missing_required_subfield`: обязательные подполя
  массивов/объектов аргументов по каталогу (дословная схема).

Диагностический эффект на сожжённом public46: **TP11 FP0, P 1.000,
R .478, F1 .647** (было TP5/.357; исторический baseline TP12/.686).
Восстановлены 6 из 7 потерянных попаданий, 0 новых FP. Финальная
валидация — holdout. Реализация: `common.py` (`ONE_CALL_CLAUSE`,
`_check_schema` R3, `_structural_channel` R1/R2); диагностический прогон:
`outputs/public46_v01/` (исторический `outputs/public46_v0/` не тронут).

## 8. Пре-регистрация правила комбинирования (ДО инференса на holdout)

См. `experiments/searh_23/three_architectures/PREREGISTERED_PROTOCOL.md`
(заморожен вместе с этим коммитом, до какого-либо инференса на
`dataset/dev_input.csv` / `dataset/sealed_input.csv`). Суть:

* **Одно семейство = один голос.** Повторы/сиды одной модели никогда не
  голосуют (внутрисемейное согласие 1.000 измерено). vireonix `auto` —
  никогда не независимое семейство.
* **V6**: structural-shortcut (V0.1) ∨ [J1=gemma greedy, J2=mistral
  greedy; при согласии — согласованный лейбл; при расхождении или
  невалидном голосе — третий проверяльщик T=gpt-oss:20b greedy; невалидный
  T → 0 + degraded-строка (никогда молчаливый уверенный 0)].
  Невалидный голос **маршрутизируется к третьему проверяльщику**, а не
  становится нулём — устраняет класс citation-fallback FN (2 из 6
  пропусков V1).
* Роли J1/J2/T назначены по diagnostic public46 (сожжённый набор) —
  зафиксированы честно как выбор инфраструктуры; после появления
  предсказаний holdout переназначение запрещено; в V6 нет числовых
  порогов для подстройки.
* Критерии фальсификации: эскалация >50% → дизайн неэкономичен;
  FP(V6) >> FP(одиночного судьи) на sealed → цена дизайна — точность;
  расхождение rename-близнецов внутри семьи → leakage.

**Честный негатив (смоук 2026-10-01):** granite-guardian-4.1-8b
пробовали как третьего проверяльщика в JSON-режиме — отклонён: это
guardian-классификатор, выдающий `<score> yes/no </score >` независимо от
judge-контракта (строгий JSON с verbatim-цитатами недостижим). Модель
остаётся для V5-диагностики в нативном режиме (groundedness-критерий,
исторический standalone F1 .8095). Третьим проверяльщиком пре-егистрирован
**gpt-oss:20b** (семейство gpt-oss, валидный JSON-смоук: верный вердикт
на контрольном кейсе, 17с).

## 9. Негативные результаты (без ретуши)

1. V3≡V1 — артефакт взвешивания (2/3 голосов у gemma), а не доказательство
   бесполезности второго семейства; вывод TA-2 «k=3 кросс-семейное
   голосование не даёт НИЧЕГО» отозван как поспешный.
2. «TP17 FP0 у V1» содержит 5 структурных shortcut-хитов; чистый
   gemma-канал — TP12; у обоих LLM-каналов есть невалидные голоса
   (3 у gemma, 12 у mistral) — покрытие цитирования — реальный bottleneck.
3. mistral-канал на общем покрытии приносит 3 настоящих семантических FP
   (пере-строгая интерпретация вежливости, выдуманное требование
   подтверждения, неверное прочтение заказа) — «бесплатного» recall от
   второго семейства нет.
4. 3 из 6 FN V1 не восстановимы ни одним текущим каналом (общие слепые
   зоны: banking_051::t15, retail_29::t13, retail_48::t4).
5. granite-guardian как JSON-судья — не работает (см. §8).
6. У старого structural baseline 4 из 7 «лишних» TP — случайно-верные
   причины (правило срабатывало на тех же ходах, где была другая,
   семантическая ошибка) — урок: структурные TP нельзя интерпретировать
   как «понятые» ошибки без per-case разбора.
