# RELATION_GRAPH_v1 — построение рёбер между source-backed events

**Дата:** 2026-09-28 · **Ветка:** `codex/relation-research-20260928` · **Код/данные:** `experiments/searh_23/relation_edges_v1/`

## 1. Резюме

Предыдущее исследование (OPERATION_CHECK, 2026-09-27) показало: события из
policy находятся хорошо, tool-description grounding почти решён (top-1
90.7%), роли гибридно-классифицируются, но **привязка condition→operation
остаётся слабым местом**, а старый relation-only результат 15/16 не
воспроизводится (51.5–57.6%). Данное исследование проверяет архитектурную
гипотезу: не один большой LLM-вопрос «построй граф», а декомпозиция

```
events → PAIR RETRIEVER → RELATION DETECTOR (existence) → DIRECTION →
RELATION CLASSIFIER (type) → GROUP LOGIC (AND/OR) → typed policy graph
```

**Главный результат.** Декомпозиция резко выигрывает у одного вызова LLM:

| архитектика | рёбра верно | лишние | precision | recall | тип верно |
|---|---|---|---|---|---|
| e2e один вызов mistral | 5/36 | 109 | 0.04 | 0.14 | — |
| e2e один вызов codestral | 7/36 | 40 | 0.15 | 0.19 | — |
| LLM-детектор + LLM-классификатор | 36/36 | 120 | 0.23 | 1.00 | 32/36 |
| **ce-детектор ∧ LLM + DIR + CLS (post-hoc)** | **30/36** | **9** | **0.77** | **0.86** | **26/30** |
| то же, renamed-сьют | 30/36 | 8 | 0.79 | 0.86 | 27/30 |
| то же, **mini-валидация (новые кейсы)** | 13/15 | 4 | 0.76 | 0.93 | 13/13 |

Узкое место сместилось: **retrieval не проблема** (recall@3 = 100% у всех
четырёх вариантов ранжирования), проблема — **precision детекции ложных
рёбер**, и она решается связкой «cross-encoder × узкий LLM», а не capacity
модели. Направление ребра — отдельная узкая задача (1 ошибка из 30 после
DIR-руки против 29–36 без неё).

## 2. Вопрос и декомпозиция

Даны source-backed events (A=check identity, B=send result, C=archive, D=
approval exists). Нужно построить A→B, D→C и НЕ построить A→C, D→B, B→A.
Две задачи разделены (и это подтверждено литературой, см. §3):

1. **RELATION DETECTION** — есть ли вообще смысловая связь (симметричная
   задача на неупорядоченной паре);
2. **RELATION CLASSIFICATION** — какой тип и направление.

Метрики этих задач считаются раздельно; классификация — только на парах с
правильными endpoint'ами, независимо от ошибок retrieval/detection.

## 3. Литературная база (что перенесено)

- **CausalSense** (LREC 2026, ANR-kFLOW/CausalSense, Apache-2.0): декомпозиция
  EE → RD (бинарно) → RC (cause/enable/prevent/intend). Их выводы: RD лёгкая
  (F1 до 0.98), RC тяжёлая (0.77; enable/prevent путаются с cause). Наше
  перенесение: RD-before-RC подтверждено; наши «тяжёлые» классы —
  ORDER vs PRECONDITION и RESPONSE vs ORDER.
- **PET** (AAAI 2022, HF patriziobellan/PET, MIT): схема Activity/Gateway/
  ConditionSpecification/Flow изоморфна нашей задаче — рёбра
  условие→операция там first-class citizens; XOR/AND-гейты ≈ наши группы
  условий. Подтверждает отдельный GROUP LOGIC-компонент.
- **Declare-извлечение** (Reijers et al., CAiSE 2019): Precedence/Response/
  Succession + негации; распознавание направления («какая активность a,
  какая b») названо ключевой проблемой бинарных констрейнтов — ровно наша
  MP2-проблема. Их модальный критерий can-vs-must объясняет системные
  путаницы → мы сохраняем допустимые альтернативы в `acceptable`, а не
  заставляем угадывать.
- **EventRelBench/EventRelInst** (Findings EMNLP 2025): LLM слабы на event
  relations (иногда ниже random) → аргумент против одного большого вопроса.
- **SpERT** (span-pair cross-encoder): дизайн pair-энкодера
  [локальный контекст + маркеры спанов + «описания типов»] — наши
  tool-описания играют роль type-описаний. OpenNRE проверен и НЕ принят:
  entity-centric Wiki-типы, переноса на policy-спаны нет.

  содержала только op/comm на стороне target — два nested-ребра оказались
  недостижимы. Расширена до всех non-OTHER событий ДО вскрытия LLM-результатов;

## 5. Руки

| рука | что делает |
|---|---|
| R1/R2/R3/R4 | retriever: bge-base эмбеддинги / bge-reranker / stanza-структурная близость / гибрид (веса a priori) |
| DET-ce | bge-reranker pair-score, пороги 0.50/0.35 (заморожены) |
| DET-nli | nli-deberta-v3, гипотеза «A must happen before B or enables/triggers B», пороги 0.50/0.35 |
| DET-mistral / DET-codestral | узкий LLM-вопрос на каждую пару (name-blind: описания инструментов, без имён) |
| CLS-mistral / CLS-codestral | узкий вопрос типа на каждую пару, вывод `possible_relations` (неоднозначность сохраняется) |
| GRP | AND/OR/XOR по набору родителей цели |
| DIR (post-hoc) | «какое событие должно произойти первым» на каждой обнаруженной паре |
| E2E | полный граф одним вызовом (базлайн) |
| комбо | consensus 2-of-3; пост-хок «ce-полоса ∧ mistral» |

Все LLM-промпты name-blind; роли событий даны (они предсказываются
frontend'ом в реальном пайплайне, oracle-трек использует замороженные).

## 6. Семантика метрик

- **Detection** — на неупорядоченных парах: позитив, если gold-ребро есть в
  любом направлении («есть ли вообще связь»). Направление — не задача
  детекции. Плюс диагностика direction-blindness.
- **Classification** — только на gold-положительных парах с правильными
  endpoint'ами: exact / acceptable (`acceptable`-множество gold) /
  set_any (любой из возможных отношений попал в acceptable).
- **Pipeline** — собранный граф: correct / extra / missing / direction /
  type; граф с одним направленным ребром на пару (dirfix-вариант).

## 8. Failure analysis (главные паттерны ошибок)

1. **Пере-связывание смежных шагов процесса** (LLM-детектор): «Bottling→Cap→
   Store», «Etch→anneal→pack» — всё в одном policy связывается в цепочки.
   Тематическая близость ≠ регуляторная связь. 66–76 FP у mistral.
2. **Кросс-связывание со-условий**: ticket↔photo-ID (члены AND-группы),
   sign-waiver↔approve-plan (члены OR-группы) связываются между собой.
3. **Проверка привязывается ко всему downstream**: gravity-stable → Cap,
   Store (а не только Bottling).
4. **MP1-ловушка не проходит** у LLM-детектора: bindA и bindB симметрично
   дают RELATED и для verify→rent, и для register→rent — привязка по
   правдоподобию, а не по тексту политики. (MP2/MP4/MP6 — проходят.)
5. **NLI-гипотеза не работает**: deontic-семантика («must happen before»)
   почти не энтайлится (R=0.08) — NLI-модели не переносят обязательность.
6. **Направление в парном вопросе иллюзорно**: классификатор прав на
   gold-направлении и одновременно «связывает» обращённую пару (36/36).
   Решение — отдельный DIR-вопрос.
7. **Вложенные цепочки**: op→check-пары редки, но DIR-fallback по ролям
   ошибается на них (проверка считается «всегда антецедент»).

## 9. Ответы на 10 вопросов задания

1. **Можно ли надёжно найти правильный parent?** Да: recall@3 = 100% (все
   4 руки), top-1 73–79% (R4-гибрид 79%, mini 100%). Правильный родитель
   всегда в top-3.
2. **Помогает ли retriever убрать лишние рёбра?** Сам по себе — почти нет
   (top-3 гейтинг: 120→117 FP у LLM-стека). Пользу даёт композиция
   retriever→precision-детектор, а не гейтинг LLM.
3. **Что лучше для detection?** Cross-encoder pair-score (P 0.79, F1 0.81);
   лучший ансамбль — «ce-полоса ∧ узкий LLM» (F1 0.82–0.85, валидирован на
   mini). NLI-гипотеза непригодна (R 0.08). Голый LLM — P 0.32–0.41.
4. **Что лучше для classification?** Узкий LLM на правильных endpoints:
   ministral-14b exact 80.6% / acceptable 88.9% (mini 93.3% / 100%).
   Codestral хуже (63.9%). Направление — отдельной DIR-рукой (1 ошибка/30).
   (Ограничение: per-type NLI/cross-encoder пробы для классификации не
   прогонялись — после провала NLI-детекции приоритет был отдан DIR.)
5. **Что дали PET/EventRel/Declare?** Архитектура (RD-before-RC от
   CausalSense; first-class condition-рёбра и XOR/AND-гейты от PET;
   направление-как-проблема и модальные путаницы от Declare; span-pair
   дизайн от SpERT). OpenNRE проверен и отклонён (entity-centric).
6. **Помогает ли сильная LLM?** Частично и не там, где ждали: codestral
   точнее в detection (P 0.41 vs 0.32) и в e2e-событиях (precision 0.96),
   но ХУЖЕ ministral в парной классификации (63.9 vs 80.6) и не решает
   пере-связывание. Преимущество даёт декомпозиция, а не capacity.
7. **Сохраняется ли качество после rename?** Да: DET-ce идентичен
   (name-blind по построению), mistral ±3пп, пост-хок пайплайн
   0.769→0.790. Entity-code переименования на relation-слой не влияют.
8. **Нужен ли fine-tune?** Сейчас — нет: zero-shot композиция уже
   P 0.77–0.79 / R 0.86–0.93 / typed 87–100%; ошибки (5 missing, 9 extra)
   — паттерны промптов/порогов, а не capacity. Fine-tune оправдан только
   при требовании P ≥ 0.9 (обучающие данные: PET + EventRelInst +
   synthetic minimal pairs, с Guardian-style held-out — по §11).
9. **Какие классы принципиально неоднозначны?** ORDER_BEFORE vs PRECONDITION
   (op-антецедент), RESPONSE vs ORDER_BEFORE (обязанность vs порядок),
   STATE_GATE vs PRECONDITION (наблюдение состояния vs исполнение проверки);
   для них необходимы `possible_relations`-множества (наш классификатор
   выдаёт их, скоринг set_any 91.7–100%). Если различие verdict-значимо —
   UNKNOWN, а не угадывание.
10. **Достаточная ли precision для Guardian?** Для «убедительного» порога —
    да: лучший пайплайн P 0.77–0.79 при R 0.86–0.93 и типе 87–100%, с
    1 ошибкой направления на 30 рёбер и решёнными AND/OR-группами; все
    компоненты дешёвые (локальные модели + ~1.3 узких LLM-вопроса на ребро).
    Для verdict-критичного применения (P ≥ 0.95) — ещё нет: нужны
    второй голос/UNKNOWN-гейт на 9 оставшихся FP.

## 10. Negative findings (честно)

- Узкий LLM-вопрос НЕ делает детекцию точной: на 36 рёбер 66–80 ложных —
  «узость» вопроса не компенсирует склонность модели считать тематически
  близкое «связанным».
- NLI как прямой детектор регуляторных связей провалился (R 0.08);
  обобщать «NLI-гипотезы» на deontic-тексты нельзя.
- Retriever-gейтинг не фильтрует FP LLM (117/120 остаются).
- E2E одним вызовом даёт «hairball» (109–130 лишних рёбер у mistral).
- GROUP parent_set_exact = 0: наборы родителей загрязнены пере-связыванием
  (сами AND/OR при этом классифицируются верно).
- MP1 (привязка условия к A vs B) не проходится LLM-детектором вообще —
  это главный оставшийся риск false-binding в проде.

## 13. Интеграция и следующие шаги

- **Не интегрировать в `scripts/predict.py`** (красная линия задачи):
  хотя mini-валидация пост-хок композиции состоялась (P 0.76 / R 0.93 /
  typed 13/13 на НОВЫХ кейсах), это один раунд; нужно (а) frontend-трек
  (события из H2-frontend вместо gold-событий — шум upstream), (б) новая
  генерация frozen-кейсов (MP1-ловушки и вложенные цепочки в большем
  объёме), (в) UNKNOWN-гейт/второй голос для P ≥ 0.9.
- Лучший кандидат композиции: `R4-retriever → (DET-ce ∧ DET-llm) → DIR →
  CLS → GRP` — всё name-blind, ~1.3 LLM-вопроса на ребро-кандидат.
- Сырые артефакты: `outputs/{R_retriever,DET_local,det_*,cls_*,grp_*,
  e2e_*,dir_*}{,_renamed,_mini}/`, скоринги `outputs/score_*.json`,
  промпты в `rel_run_llm.py`, датасет `frozen/` с SHA-манифестом.
