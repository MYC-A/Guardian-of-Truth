## Ответы
1. **Смена модели при том же методе** помогает частично: large-4 исправил 3 из 6 известных пропусков (2 суммы, 1 сущность),
   убрал FP базы (dev D2 округление, frozen Q5 даты), но пропустил Q12 (неуказанный выбор из двух заказов). Не решение само по себе.
2. **Слепой проход даёт эффект сверх дополнительного вызова** — это главный положительный результат. На ministral при равном
   числе вызовов: C 6/6 против E1 (тот же проход, но с видимым ходом) 4/6 на dev и 6/6 против 2/6 на devT; FP не выросли.
   Разница целиком в сущностях (P09): видя ход, модель подстраивает анализ под выбранный ID; не видя — сама выводит правильную
   запись и затем сравнивает. На frozen эффект мал (потолок): C +1 TP (Q12), но 1 FP (Q7, неверно прочитанное исключение
   «свои счета»), такой же FP у E1. Причины на devT слабее (3 из 6 частичные: «не тот ID», без «принадлежит другому»).
3. **Python сверх дополнительного прохода — нет.** Py_L = PyCtl_L = D = 6/6 на dev: на large-4 любой структурированный
   пред-проход закрывает те же строки, исполнение кода ничего не добавляет. Программы запускались 8/8 OK, но выбирали данные с
   ошибками (2 раза разбирали `'lena_k.'` / e-mail с точкой → «аккаунт не найден»); ревьюер не был сбит, но и не опирался на
   код сильнее, чем на догадку контроля. Плюс 2/10 обрезаний из-за длины кода.
4. **Что остаётся:** неверно прочитанные исключения (Q7: FP у C и E1), неуказанный выбор (Q12 ловит только C), даты у малой
   модели (Q5 FP у A), формулировка причины при переименованных ID. Для large+blind и Python frozen не проверен.
5. **Минимальный вариант:** C — ministral + один слепой проход перед `review` (≈2.6 вызова/строку, ≈5.5k токенов против 2.3k).
   Подтверждён на dev и devT, на frozen нейтрален по F1 (0.933 против 0.857 у A), FP не уменьшает. Как новый дефолт не
   предлагается: нужен прогон на реальных наборах (holdout2 / lockbox) с контролем E1.
