# Judge v3.1: профили вопросов, A/B подсказок, диагностика (14.10.2026)

База: b987dfd. Production не меняет способ принятия решения: ключ `overall@on`, `aggregate=primary`,
`positive_rate=0.30`. Новое включается только профилем и только после независимой размеченной оценки.

## Изменения

- Ключи `<вопрос>@<on|off>`: `questions` (overall, values, actions, tool_use, policy, refusal) x `hint_modes`.
  Первый ключ = первичная оценка, его промпт строится именно для него. Все варианты строки берутся из
  одного построенного промпта (тот же обрезанный транскрипт, cap и ответ) и отличаются только блоком
  подсказок и финальным вопросом. Подсказки остаются эвристиками, а не доказательствами.
- Приоритет первичного прохода: записи порции пишутся и fsync до любых дополнительных вызовов.
  `extras_schedule=after_primary` (default): extras только после первичной оценки всех строк.
  `per_chunk` (офлайн A/B, тёплый prefix cache): extras после порции, только если остаток
  первичного прохода ещё укладывается, иначе откладывается. Перед каждой порцией extras проверка
  времени по ИЗМЕРЕННОЙ стоимости (до первого замера пессимистично, как полный prefill), опционально
  `extras_max_seconds`. Сбой extras логируется и завершает только extras. `question_overhead` убран.
- Точность оценок по каждому результату: при `require_exact_scores` неточная первичная оценка пишется как
  `score=null`, `bounded_score`, `INEXACT_SCORE`; неточные extras в `bounded` и не смешиваются с точными.
- Диагностика в `done` и финальном логе отдельно для primary и extras: prompts, prompt/generated/cached/
  uncached tokens, wall seconds; если движок не сообщает cached tokens: `unavailable`, не 0. Также формы id,
  квантили первичных оценок, счётчики подсказок, `hints_shown`.
- Супервизор: профиль проверяется до старта, неверный -> `CONFIG_INVALID` и production-профиль.
  Файл перезаписывается при любом изменении файла оценок (в том числе после extras). Не-primary агрегат
  применяется только когда у ВСЕХ оценённых строк есть все входные ключи, иначе primary для всех
  (`primary(aggregate_incomplete)`). Жёсткие находки никогда не отключаются по доле: высокая доля
  только логируется (`HARD_RATE_HIGH`, по видам правил и неполноте каталога).
- Числа: пары для сумм/разностей берутся из 150 ПОСЛЕДНИХ упоминаний, а не самых маленьких чисел.
  При 150 и меньше числах поведение не изменилось. Суммы 3-4 слагаемых сознательно НЕ включены:
  без адресов операндов и принадлежности к одной сущности они дали бы ложное «подтверждение».
- `scripts/judge_analysis.py` (офлайн, не в ZIP): проверка SHA256 и позиций строк каждого прогона, конечность и
  схема оценок, сравнение только на общем пересечении оценённых строк, групповой бутстреп AUC,
  покрытие и время, on/off на строках с показанными подсказками. Меньше 300 строк = smoke only.

## Профили

| Файл | Ключи | Назначение |
|---|---|---|
| `submission/JUDGE_CONFIG.json` | overall@on | production |
| `submission/JUDGE_AB_HINTS.json` | overall@on, overall@off | офлайн A/B подсказок |
| `submission/JUDGE_AB_QUESTIONS.json` | 6 вопросов @on | офлайн A/B вопросов по типам |

A/B (GPU, независимый размеченный набор с колонками id,prompt,response,label):
```
python scripts/eval_judge_valid.py --input dev.parquet --model models/qwen36-a3b-awq --config submission/JUDGE_AB_HINTS.json \
    --python /runtime/python/run_python.sh --seconds 20000 --out runs/ab_hints
python scripts/judge_analysis.py --input dev.parquet --run runs/ab_hints --out runs/ab_hints/analysis.json
```
Правило: вариант заменяет overall@on только если нижняя граница группового 95% CI разницы AUC > 0.
valid46 только smoke (исполнение, 7 hard / 0 FP), без выбора порога, модели или агрегатора.
