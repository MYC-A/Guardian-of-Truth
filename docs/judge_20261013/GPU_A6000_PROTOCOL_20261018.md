## Ресурсный профиль

Исходник — `submission/JUDGE_OPEN_REVIEW40.json`, изменения только в отдельной
копии A6000: max_num_seqs=4, max_num_batched_tokens=4096, chunk=4,
engine_overrides.enforce_eager=true. Это объявленные изменения размещения/исполнения
на меньшем GPU, не tuning качества. max_model_len=49152, gpu_memory_utilization=.90,
legacy, prefix caching и chunked prefill сохраняются. Если этот профиль не запускается,
причина и следующая ресурсная конфигурация фиксируются до качественного сравнения;
исходные тексты не сокращаются из-за меньшей VRAM.

Тот же overall@on → open answer_audit → exact final. Промпты и валидаторы не меняются.
Scoring: T=1, one token, оба класса и finite exact log-odds обязательны.
Generation: T=0, top_p=1, seed=0, max_tokens=384. Один offline LLM на прогон.
Данные и gold читаются раздельно; ни gold, ни baseline score в новые model inputs
не добавляются. Overall durable до review; фактический source финала сохранён.

## Этапы и техническое правило

1. Pilot32: ровно подготовленные 32 строки, включая восемь длинных исторических.
   Измерить cold startup, stage/role wall, input/output/cached counters при наличии,
   exactness, notes statuses/delivery, trimming и sampled peak VRAM.
2. Если доля TRUNCATED среди выполненных prepass >15%, допускается единственный
   переход 384→768 до quality-run. Он определяется только finish/status, без отбора
   по gold/F1. Повторить тот же пилот и зафиксировать итоговый generation budget.
   Пустая/INVALID/TRUNCATED справка не считается успешной blind/open delivery.
3. После пилота оценить стоимость полного dev/regression/eval по фактическим tokens
   и wall; не переносить скорость коротких Compli строк на длинные Guardian строки.
   При техническом дефекте сначала исправить/зафиксировать его, сохранить неудачный
   receipt; не маскировать отказ положительными quality claims.
4. Первый quality-набор — весь dev520; Guardian regression397 отдельно. Eval1893
   запускается после заморозки кандидата и оценки затрат. Целевые три независимых
   offline-повтора каждого выполненного quality-набора, без result cache. Если полные
   три повтора/полный eval не выполнены, это явно NOT_EXECUTED, не ACCEPT.

Quality deadline пилота 7200 с (внешний ограничитель 7500); quality deadline больших
наборов выбирается явно по пилоту и фиксируется перед стартом, без утверждения о
конкурсной скорости. Настоящий predict/supervisor с 1380/1530/1680/1800 с проверяется
отдельно; эти production значения не меняются.

## Одни оценки, фиксированные способы решения

Из каждого сохранённого массива вычисляются без новых модельных вызовов:

- overall;
- MAX доступных конечных exact overall/final (нынешнее поведение);
- final-only, с технически отсутствующим score, помеченным как missing.

Для всех — неизменный `decision.decide`, hard override и квоты .30/.40.
Основная пара: **final .40 против MAX .40**. .30 и overall — диагностика;
пороги, веса и новые arms по результатам не подбираются.

Для final-only all-row бинарный результат при отсутствующем score использует
действующий mechanical-only/no-score fallback этой строки. Он не называется
модельным NO. Сырые overall/final шкалы через построчную подстановку не смешиваются;
глобального сброса всех final к overall нет. При неполном coverage отдельно
показываются all-row с fallback и одинаковый exact-intersection. AUC всех строк
без exact score не выдумывается; AUC subset помечается и не сравнивается как all-row.

F1/P/R/confusion, AUC/AP, score correlation, исправления/поломки и добавочные
положительные решения считаются на одинаковых строках. Paired grouped bootstrap
95% CI ΔF1: 2000 ресэмплов семейств с возвращением, seed=20261018, **фиксированные
предсказания** исходного quota-решения; это conditional CI, квота внутри bootstrap
повторно не ранжируется. Повторы модели не считаются новыми группами.

Compli основной внешний срез airlines+healthcare; insurance с известным upstream
model-based отбором показывается отдельно и в общей таблице. Это prefix/policy
адаптация, не метрика закрытого Guardian. Старые Guardian данные SEEN, не новый
holdout. PolicyGuard с trajectory gold в основной run не входит.

Вердикт о продвижении требует независимых подходящих данных, положительной нижней
границы grouped CI ΔF1, ΔAUC>0, достаточной реальной notes delivery, не худшего
exact/model coverage и полного target-runtime. Один пилот или внешний benchmark
этого не доказывает. При неполных/просмотренных данных — INSUFFICIENT_EVIDENCE.
