## A. Правило решения (только сохранённые scores, без GPU)
Протокол: docs/judge_20261013/V3_A_DECISION_RULE_PROTOCOL.md
1. Найти в коде сабмита и scripts/predict.py точное текущее правило (квота,
   max(overall,final), hard positives, равные score). Записать файлы и строки.
2. Кандидаты (список закрыт):
   R0 квота .40 + hard positives (текущее).
   R1 log-odds > 0 + hard positives.
   R2 log-odds > t, t подбирается 5-fold CV по conversation groups, цель:
      средний F1 по сетке долей из п.3.
   R3 калибровка Платта (в той же CV), на каждом наборе без меток оценка доли
      нарушений EM-методом Saerens 2002, обвинение при скорректированной
      вероятности > tau (tau в CV).
3. Оценка на seen397 и real191 отдельно, valid46 только как регрессионная строка.
   Доли нарушений p: 0.12, 0.15, 0.20, 0.25, 0.35, 0.50 и исходная. Перевзвешивание
   ресэмплингом с весами w+ = p/pi, w- = (1-p)/(1-pi). Квотные правила применять
   к перевзвешенному набору. Метрики: F1, precision, доля ложных обвинений, recall.
   Bootstrap 1000 по группам, 95% интервалы разности с R0.
4. Шум score: взять разброс log-odds из сохранённых повторных прогонов (replay);
   если их нет, записать это и добавить гауссов шум sd = макс. наблюдённый разброс.
   Считать долю решений, меняющихся от шума.
5. Принять кандидата, если: (a) при p=0.12 и 0.20 F1 выше R0 на >=0.03 и нижняя
   граница интервала > 0 на обоих наборах; (b) при p=0.50 и исходной доле F1 не ниже
   R0 больше чем на 0.01; (c) от шума меняется <=3% решений. Из прошедших брать
   самый простой: R1 < R2 < R3. Никто не прошёл: оставить R0.
6. Скрипт scripts/v3_decision_rule.py (без GPU, фиксированный seed) + pytest:
   R0 на исходной доле совпадает с опубликованным (seen397 current-max .751244 при .40);
   EM на синтетике с известной долей ошибается < 0.02.
   То же правило потом применяется к scores LoRA в части E.

### B2. Единая схема (JSONL, одна строка = один целевой ход)
id, source, source_revision, domain, family, scenario_id, group_id (диалог),
pair_id (общий у нарушения и его корректного близнеца, иначе null),
policy (полный текст), tools (спецификации), history (все сообщения до целевого
хода, включая tool calls и tool results), target_turn, label (1 = материальное
нарушение, 0 = корректно), violation_type (rule_scope | eligibility | consent |
authorization | tool_args | unsupported_fact | completion_without_result |
wrong_transfer | none), governing_rule (цитата правила), evidence_msg_ids,
label_origin (simulator | perturbation | upstream | human), is_hard_negative,
n_tokens (токенизатором Qwen3-4B), license.

### B3. Как получать примеры
a) tau2, естественные ошибки. Через vLLM на сервере запустить симуляции несколькими
   агентами разного качества (минимум 3, например Qwen3-4B, Qwen3-8B, Qwen3.6-35B),
   несколько seed, все задачи доменов. Ход = нарушение, если: write-вызов с
   аргументами, не совпадающими с ожидаемыми действиями задачи, и он меняет БД
   против итогового эталонного состояния; или агент сообщает факт/результат,
   противоречащий результатам инструментов или БД. Ход = корректный, если он
   совпадает с ожидаемыми действиями или является read/уточнением без ошибки.
   Если автоматически нельзя однозначно отнести ход: исключить и посчитать.
   Метку ставить только первому ошибочному ходу диалога; ходы после него не брать.
b) tau2, «сломать и дописать». Из успешных траекторий выбрать целевой ход и
   внести ровно одно изменение из типологии violation_type: аргумент из другой
   записи; факт, которого нет в результатах; «выполнено» без вызова; пропуск
   согласия; нарушение eligibility; ненужная передача оператору; правило не той
   фазы. Исходный ход сохранить как корректного близнеца (тот же pair_id).
c) Трудные корректные (is_hard_negative=1), не меньше 30% всех label=0:
   ход выглядит рискованным, но разрешён: возврат при выполненных условиях,
   передача оператору по явной просьбе или по правилу, согласие получено раньше
   в истории, ограничение снято более ранним изменением правила, повтор
   неудачного вызова по разрешённой причине, краткое корректное резюме при передаче.
d) CompliBench: сгенерировать новые диалоги их пайплайном во всех доступных доменах,
   метки ходов из их аннотации. Взять до 6k ходов.
e) ToolRM: rejected -> label 1 (tool_args), chosen -> label 0, тот же pair_id.
   Подвыборка до 3k, стратифицировать по типу ошибки, оставить и случаи
   «вызов не нужен».
f) RAGTruth/HaluBench: контекст -> результат инструмента, ответ -> сообщение агента,
   label по их разметке (unsupported_fact). Подвыборка до 2k.
Цель: 15-25k ходов. Доля label=1 30-40%. Ни один источник не больше 40% train.

### B4. Нормализация
1. Рендерить ВСЕ примеры тем же кодом, который строит вход судьи в production
   (найти рендерер в репо). Формат обучения должен совпадать с форматом сабмита.
   Отдельный тест: production-рендер и train-рендер одного примера дают
   побайтно одинаковый текст.
2. В 30% примеров заменить имена инструментов и параметров на нейтральные
   (consistent внутри примера), в 30% перефразировать политику (сильной моделью,
   с проверкой, что смысл правил не изменился, выборка 100 вручную).
3. Дедупликация: точная + near-duplicate (MinHash по истории+ходу). Пары
   с одинаковым входом и разными метками: удалить обе и записать.
4. Длина: не обрезать молча. Записать распределение n_tokens. Не меньше 20% train
   длиннее 16k токенов. Всё, что выше потолка обучения из C, исключить с подсчётом.

### B5. Чистота и разметка
1. Деконтаминация против всех eval-наборов из B1.6: точный текст, near-dup,
   совпадение user ID и resource ID. Совпало: исключить.
2. Аудит меток: прогон 35B current-max только по входам (без меток). Все расхождения
   35B с меткой + случайные 5% просмотреть по полному правилу и истории, лучше двумя
   людьми. Ошибку метки исправлять только по правилу, а не по мнению модели;
   вести журнал исправлений. Если на выборке >10% меток неверны, остановиться
   и чинить генератор, а не обучать.
3. Сплиты по group_id и scenario_id, никаких общих диалогов между сплитами:
   - DEV-домен: telecom целиком (кроме части для holdout).
   - HOLDOUT: ~300 ходов из всех доменов, новые сценарии, проверены человеком
     полностью. Заморозить (SHA256) до начала обучения, открыть один раз в E.
   - TRAIN: остальное.

### B6. Обоснования (для варианта L2)
Для каждого train-примера 35B пишет обоснование, ЗНАЯ правильную метку, в формате:
"Правило: <цитата>. Условия: <проверка по истории и результатам>. Вердикт: YES|NO".
Отбросить обоснования, где вердикт не совпал с меткой или процитировано правило,
которого нет в политике.

## C. Обучение LoRA
Протокол: docs/judge_20261013/V3_C_TRAIN_PROTOCOL.md
- База Qwen/Qwen3-4B-Instruct-2507, revision cdbee75f17c01a7cc42f958dc650907174af0554.
  Начинать с базы, не с v1/v2b. Тот же стек, что в scripts/train_lora_tooltruth_20261018.py.
- LoRA rank 16, alpha 32, dropout 0.05, all-linear; BF16, SDPA, gradient checkpointing,
  micro-batch 1, эффективный batch 16, AdamW lr 1e-4, weight_decay 0.01, warmup 3%,
  clip 1.0, 2 эпохи, seed фиксирован.
- Потолок длины: сначала проверить по памяти A6000 32768 токенов на 10 самых
  длинных примерах. Не влезает: 24576, записать, сколько примеров исключено.
- Два варианта, одинаковые данные:
  L1 текущий объектив: BCE по разности logsumexp групп YES/NO (как v2b).
  L2 SFT на обоснование + вердикт; score = log-odds YES/NO на токене вердикта.
  Для L2 отдельно измерить время на ход: если весь тест не влезает в лимит
  сабмита, L2 не годится для production, даже если качество выше.
- Checkpoint в конце каждой эпохи. Выбор только по DEV (telecom + dev split) по
  AUROC. HOLDOUT, valid46, 397, real191 при выборе не смотреть.
