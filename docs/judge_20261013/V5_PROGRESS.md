# V5: отдельный адаптер 35B, техническая подготовка — 19.10.2026

Экспериментальный ZIP V4 завершён; его состав и SHA не меняются.
Поручение пользователя — после него начать отдельную LoRA для текущей 35B.
Адаптер 4B не переносится на 35B.

## Текущее состояние

Технический пилот `guardian-lab-v5-35b-pilot8-torch-v1` завершён успешно:
BF16, последние восемь слоёв, attention/shared-expert проекции, 3 833 856
обучаемых параметров. Все три длинных TRAIN-входа прошли forward/backward:
loss и gradients конечны, LoRA B gradients ненулевые, base gradients отсутствуют.
Пик allocated 31 088 686 080 байт, reserved 31 937 527 808 байт; около 30 ГиБ.
Скорость 173,92 токена/с, оценка полной эпохи с запасом 56 192 с (15,6 часа).
Технически профиль помещается в память, полная эпоха в лимит четырёх часов не входит.
Временная оценка получена на трёх длинных примерах и не гарантирует скорость всех строк.

Optimizer updates = 0; native gate пока не пройден. Текущий probe
`guardian-lab-v5-35b-native8-v4` проверяет последовательные синхронные запросы
без APC. Перед ним обнаружены следующие технические проблемы:

- Первый native запуск падал на попытке LoRA-wrap квантованных routed experts.
  Ограничение `lora_target_modules` на attention/shared-expert suffixes позволяет
  загрузить двигатель, routed experts не оборачиваются.
- Второй запуск обнаружил zero/base delta0.5000 log-odds.
- Третий, уже без APC, показал zero/base delta0.8750, но и base/base repeat
  delta0.6250, zero/zero repeat delta0.5000. Поэтому разница не доказана как
  эффект адаптера; даже неизменная база пока не воспроизводится. Неизмеренный
  перенос или точность подключения не объявляются, gate не ослаблялся.
- Четвёртый запуск отключает async scheduling и оценивает входы по одному,
  с повторными контролями. Ненулевой технический B увеличен с std.01 до std.1,
  чтобы его действие можно было отделить от обнаруженного численного шума.

До первого optimizer update пользователь предложил окно около12часов.
В протокол внесена поправка: до9часов optimizer wall-time, до2часов native
оценки, остаток на подготовку/анализ/сохранение. Даже при допуске этот прогон
может быть частичной эпохой; фактические rows/steps/epoch_fraction сохраняются.
После успешного native gate предусмотрен повтор пилота актуальным trainer,
затем свежий адаптер, немедленный checkpoint после первого optimizer step
и почасовые health receipts. Проверка самой моделью/обучением не заменяет человека.

База: `cyankiwi/Qwen3.6-35B-A3B-AWQ-4bit`, revision
`00fcea2d3bcf5389b518d4fc082e5590e0ba4844`. Все файлы сверяются с манифестом
готового ZIP. Замороженный TRAIN1458, 8 498 123 токена, максимум 9655,
обрезанных TRAIN-входов нет. Метки и происхождение примера в текст не входят.
Данные DEV152/HOLD336 не используются для optimizer updates или выбора профиля.

Обучающее окружение отдельное: torch2.10.0+cu128, Transformers5.14.0,
PEFT0.21.2, GPTQModel7.6.0, Optimum2.1.0. Рабочий vLLM/V4 venv не обновлялся.
Список версий и installation receipts сохранены в `v5_evidence/`.

## Проверки и отказы до обновления весов

1. Первый пилот получил ноль подходящих `nn.Linear`: прямой GPTQModel loader
   не перенёс `modules_to_not_convert` из HF-конфига в свои dynamic skip rules.
   Добавлен ограниченный преобразователь настроек в памяти процесса. Исходные
   config и веса не меняются; CPU-проверка сохраняет AWQ geometry и routed experts.
   Второй пилот подтвердил все 250 исходных float-проекций (`MODEL_MODULES`).
2. Второй пилот остановился при подключении PEFT: отсутствовал требуемый Optimum.
   В отдельный venv установлен pinned Optimum2.1.0 без обновления зависимостей;
   проверка `is_gptqmodel_available()` прошла. Третий пилот успешно подключил PEFT.
3. В BF16 Torch-пилотах всех 40 слоёв найден резервный Torch GDN path без FLA.
   В отдельный venv добавлены `flash-linear-attention==0.5.2` и `fla-core==0.5.2`.
   Повтор подтвердил kernel `fla.ops.gated_delta_rule.chunk.chunk_gated_delta_rule`,
   загрузку 250 адаптеров (19 169 280 параметров) и zero/disabled parity внутри HF,
   но остался медленным. Оба процесса остановлены как технические, с receipts;
   полного forward/backward benchmark у них нет, tokens/sec не заявляется.
4. Проверен поддерживающий training `AWQ_GEMM_TRITON` в FP16 со статическим
   loss scaling128. Пилот остановился на `ZERO_ADAPTER_HF_PARITY_FAILED` до
   backward/optimizer. Причина расхождения (нефинитность или численная разница)
   этим receipt не разделена; backend отклонён, порог не ослаблялся.
5. Поэтому проверяется предусмотренный протоколом BF16-вариант последних
   восьми слоёв. Это выбор по техническим ограничениям, без DEV/HOLDOUT quality.

Отказы и технические остановки сохранены, optimizer updates отсутствуют. Причина относится
к новому training loader/окружению; ошибка готового vLLM ZIP этим не установлена.

## Дальше

1. Finite forward/backward и замер. Если память/время неприемлемы, предусмотрены
   последние восемь слоёв; выбор только технический, до просмотра качества.
2. Zero-adapter parity и заведомо ненулевой TRAIN-only адаптер в исходном vLLM.
   Проверяется фактическое влияние адаптера, exact coverage и освобождение GPU.
3. Зафиксировать профиль и SHA обоих receipts. Только затем свежая инициализация
   и optimizer updates: r16/alpha32/dropout.05, lr2e-5, accumulation16, одна эпоха
   с обновлённым ограничением optimizer wall-time девять часов. Неполная эпоха явно отмечается.
   Медленный профиль не означает, что полная эпоха уложится в этот лимит.
4. Парная classifier-only оценка base/adapter на одинаковых token IDs: новые
   DEV/HOLDOUT и старые 397/520, отдельно valid46/real191. Фиксированный input cap,
   механические fixes и квота .40, дополнительные .30/.50 только диагностика.
   Это отдельно от полного production overall→open-review→MAX; его превосходство
   одной classifier-only проверкой не устанавливается.

Человеческой проверки нет: статус EXPLORATORY_ONLY_HUMAN_UNVERIFIED.
Польза нового адаптера и прирост на закрытом тесте пока не измерены.
Для обучения и последующей оценки подготовлены конечные Supervisor jobs и
локальный сборщик артефактов с проверкой SHA. До прохождения gate они не запускаются.
Обещание времени полной эпохи до результата пилота не даётся.
