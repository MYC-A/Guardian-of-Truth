# V4: новые данные, исправленный формат и fresh-base LoRA — 19.10.2026

Зафиксировано до заморозки V4 и до первого нового optimizer step. Это исследовательская
серия по поручению пользователя; результаты v3/E2 и прежние ограничения сохраняются.

## Гипотеза и сравнения

Точнее различать применимое нарушение и корректный похожий ход: согласие в истории,
согласие на другой объект/цену, допустимость операции и статус, basic economy,
компенсация, факт из последнего инструмента, неподходящий API. Сама строка `yes`
не используется как универсальный семантический классификатор.

Отдельно сравниваются: прежний 35B R0; base 4B; предыдущая LoRA v3; новая LoRA v4;
фиксированная смесь percentile ranks 35B/v4 50:50. Квоты .30/.40/.50 — заранее
заданные диагностические точки, без выбора по valid46/real191/закрытым ответам.
Кандидат bounded_turn_shape измеряется отдельно от LoRA, с правилом S_quota;
S_OR остаётся отдельной ранее объявленной диагностикой. Production config и ZIP
не меняются автоматически. Новые hard-метки могут превысить квоту, как штатный override.

## Данные до обучения

Смесь и ограничения — V4_DATA_PREPARATION_PROTOCOL.md. Ориентировочные объёмы не
добираются шумом. Если caps, лицензии и исключение пересечений не позволяют получить
1800/500–800/800 строк, фиксируется фактический недобор и его причина.

Native DB constructed contrasts явно отделены от настоящих слабых траекторий.
Эталонные вызовы replay не объявляются автоматически корректными диалогами.
Для корректных близнецов обязательны native execution, policy/source и schema checks.
Natural: только текущий доказуемый конфликт; reward и несовпадение с reference не
являются меткой; неизвестные ходы исключаются; после первого доказанного нарушения
траектория не даёт новых обучающих целей. Проверенный read может быть допустимым
текущим ходом при не полностью проверенном префиксе; это явно отмечено в metadata.

В V4 текущий response имеет явный заголовок ассистента. В v3 constructed inputs
этого заголовка не было: структурный парсер возвращал RESPONSE_WITHOUT_HEADER.
Старые файлы и измерения не переписываются. Парные base/v4 оценки используют один
и тот же исправленный renderer; реальные benchmark inputs остаются исходными.

До alias и split: exact/near/explicit entity проверки против 2810 benchmark inputs
и старых DEV/HOLDOUT/STRESS; затем общие scenario/pair/entity/near components.
Компоненты со старым TRAIN закреплены за TRAIN. Новый контроль формируется только
из остальных компонентов; target HOLDOUT300/DEV150, реальный объём в FROZEN.json.
Alias по hash примерно30%, одинаковый для пары, без изменения entity IDs; inverse map
и исходные native receipts сохраняются. Это не новые примеры или templates.
В сумме внешние источники <=15%; template cap60; учёт legacy включён в оба ограничения.

Проверка: parse/source/schema/native proof; отдельная стратифицированная проверка
спорных новых семейств. Модельный аудит не заменяет человеческий. Human review
недоступен; весь запуск HUMAN_UNVERIFIED, исходный acceptance-gate остаётся false.
Доля длинных входов и class balance публикуются как фактические, без искусственного
удлинения и удаления одной половины пары для красивого счётчика.

## Обучение и время

Fresh Qwen3-4B-Instruct-2507 cdbee75f17c01a7cc42f958dc650907174af0554,
без загрузки v3 adapter. BF16, SDPA, gradient checkpointing, LoRA r16/alpha32/dropout.05,
all-linear, AdamW lr1e-4, weight decay.01, gradient clip1, accumulation16, seed20261019.
Objective прежний: BCE для точных logsumexp(YES)-logsumexp(NO). Один проход, без
выбора checkpoint по holdout. Максимум32768 токенов, без silent truncation.

Сначала технический forward/backward на10 самых длинных выбранных TRAIN-входах,
без optimizer update. После него оценка длительности по реальным tokens/sec.
Финальный бюджет optimizer части <=5400 секунд; по истечении сохраняется неполная
эпоха с явной epoch_fraction, она не выдаётся за полную. Ошибки/OOM сохраняются,
автоматического перебора конфигураций по качеству нет. Свои model servers остановить
перед обучением. Checkpoints каждые20 updates, offbox хеши и полная история процесса.

## Оценка и решение

В том же процессе после обучения — base и adapter, одинаковые input/token receipts.
Новый DEV/HOLDOUT и исходный seen397, включая real191/valid46; отдельно dev520.
Контрольные метки не подаются модели и не используются для подбора данных/checkpoint.
Прежние наборы просмотрены и пересекаются: это regression/EXPLORATORY.

Публиковать AUROC, confusion/F1/precision/recall, exact coverage, сопоставление TP/FP,
paired grouped CI и FP при matched recall. Низкую долю нарушений12%/20% анализировать
отдельно: native holdout с иным prior не доказывает перенос на конкурс.
Проверить, даёт ли v4 выигрыш после одинакового shape-gate у обеих моделей.
При отсутствии надёжного переноса сохранить отрицательный результат; не собирать
ZIP и не обещать F1 на закрытом тесте. Исходные quality/human/time acceptance gates
не считаются пройденными только из-за завершившегося optimizer.
