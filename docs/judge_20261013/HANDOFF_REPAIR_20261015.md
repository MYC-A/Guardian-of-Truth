# Исправление кодировки handoff и уточнение аудита

## Подтвержденная ошибка документов

В de5651d859f918104e012d763b3236d0a42d9dc8:

| Файл в git | Bytes | Кириллица | Символы ASCII ? |
|---|---:|---:|---:|
| AGENT_HANDOFF_20261015.md | 16 279 | 0 | 9 716 |
| MODEL_CANDIDATES_20261015.md | 14 466 | 0 | 7 702 |

Соседний RESULTS_20261015.md содержал кириллицу. Проверка прочитала blobs через
git show и декодировала bytes как UTF-8, без участия вывода терминала.
Поэтому это потеря символов при записи, не проблема отображения GitHub.

Причина: многострочный русский текст передавался из Windows PowerShell в stdin Python
через pipe. PYTHONUTF8=1 и правильное декодирование готового файла не восстанавливают буквы,
уже замененные вопросами при передаче. Проверка только отсутствия U+FFFD была недостаточна.

Документы восстановлены через Unicode-aware apply_patch без этого pipe.
Проверяются: строгий UTF-8, реальное наличие кириллицы, точные русские контрольные фразы,
отсутствие длинных серий ?, tracked blob и bytes после получения с удаленного Git.
Правка касается задания и отчета, не production-кода, модели или ZIP.

## Что из ответа агента воспроизведено

D1: stage_input — JSONL с ensure_ascii=False; judge_stage читает splitlines.
В коде оцененной версии это scripts/judge_stage.py:225 и запись в judge_submission.py:297.
Для U+2028, U+2029 и U+0085 внутри поля JSON отдельное воспроизведение подтвердило:

- json.dumps(..., ensure_ascii=False) сохраняет этот символ внутри строки.
- splitlines режет одну JSON-запись, json.loads падает.
- split по LF сохраняет одну запись.

Воспроизведение было без GPU и без правки inference-кода. Чтобы считать исправление готовым,
агент должен добавить regression реальной записи/чтения stage_input, включая CRLF.
Наличие проблемы в коде не доказывает, что такой символ был в закрытом тесте.

## Что не следует принимать за доказанный production-сбой

- D2/D4: изоляция исключений строк и проверка token cap — обоснованные точки проверки кода.
  Нужны воспроизведение и тесты каждой ветви, не только чтение диффа.
- D3: доля positives от scored rows — текущий сознательный контракт. Для данного изменения
  он сохраняется. Неполное покрытие отражать в диагностике, не исправлять случайными единицами.
- D5: dependency closure упаковщика обязательна при подключении U2. Проверять обе формы import.
- D6: tests.test_evidence_packer нужно включить в CI интегрированного пути. До интеграции
  его отсутствие в judge workflow не является доказательством ошибки текущего judge.
- D7: фактическая проверка веса/revision и durability output требуют отдельной оценки;
  manifest field не доказывает сверку с pinned provider hashes.
- P1: error/error(s) в теле receipt не всегда означает сбой. Проверять null/пустые списки,
  сведения об исторической ошибке и обычные данные, иначе появятся ложные находки.
- P2: неоднозначная привязка не отменяет факт вызова и не доказывает неизвестный инструмент.
  Сохранить исходные события и отдельно UNKNOWN статуса/связи.
- P3–P7: нужны production-format regressions и измерение встречаемости. Точный отступ может
  быть частью формата, но не является универсальным решением для всех вариантов.
- «Ровно семь ключей stage_input» — наблюдение о текущей схеме, не запрет на явно протестированное
  совместимое расширение. Не строить архитектуру вокруг магического числа.
