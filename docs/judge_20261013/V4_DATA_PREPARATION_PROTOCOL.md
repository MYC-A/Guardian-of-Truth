До генерации новых примеров/меток и до любого нового обучения. Это отдельная

## Новая целевая смесь и границы

Ориентиры пользователя: около1800 парных source-backed tau2 строк,500–800
source-supported естественных ходов4B/8B, около800 старых TRAIN frozen-v2;
ToolRM+ToolACE+RAGTruth Data2txt В СУММЕ <=15% всей смеси, включая старые строки.
Это новая tau2-heavy смесь по явному указанию пользователя, а не соблюдение
прежнего source<=40% v3. Прежний объём15–25k тоже не объявляется выполненным.
При конфликте ориентиров соблюдать качество и caps, уменьшать число строк
с отчётом причин, не добирать повторами. Максимум60 строк на domain/family/
template_id. Перефразы и переименования не создают новые template_id или сценарии.
В30% примеров, выбранных hash до метрик, последовательно переименовать tools и
parameters в policy/schema/history/target/proof; исходник и отображение сохранить,
группы не разрывать. Не менять IDs/данные для обхода деконтаминации.

Исключены HaluBench/APIGen NC, RAGTruth QA/Summary, новые объёмы ToolRM,
полностью сочинённые35B диалоги. Источники/лицензии/revisions унаследовать только
после проверки локальных receipts. Human review отсутствует; source checks
не называются человеческой проверкой или доказательством неизвестного теста.

## Эталонные действия через среду

Пин tau2:96a3ef92329baf908ffe9dfe188cea34e8701d2a, исходные task/state/policy/tools.
Проверить, что эталонные действия выполняются в native initial state с task setup.
Сохранить реальные результаты инструментов и diff DB до/после каждого write.
Эталон обычно задаёт конечные действия, а не полный корректный диалог: нельзя
назвать автоматически правильным ход с отсутствующей аутентификацией/согласием.
Добавленный read/consent каркас явно помечать constructed, не natural.
Каждая пара: один изменённый target ИЛИ одно проверяемое условие истории,
корректный близнец остаётся, полный source lineage и проверка нативных tools.

Семейства: retail запрещённое удаление/смена продукта; scoped turn shape;
согласие ранее, отказ, согласие на другой объект/цену; статус; airline flight
change basic economy (не путать с разрешённой сменой cabin), основания отмены,
компенсации с полным набором условий; платежи/возвраты; telecom limits/contract;
факты последнего успешного результата; success без write; transfer по правилам.
Для всех нельзя считать одно выполненное условие доказательством полной
допустимости. Включать пары consent-present + independently-ineligible.
Не объявлять причиной нарушения отсутствие буквального слова yes: явная просьба
выполнить однозначное предложение тоже может устанавливать согласие.

## Естественные траектории

Сначала инвентаризировать уже сохранённые4B/8B trajectories. Затем ограниченные
новые task/model/seed pilots, localhost-only, cache/review off, сохранение failures.
Не экстраполировать18 коротких пилотов линейно на длинные задачи и500–800 меток.
Расхождение аргументов с эталоном НЕ является достаточной меткой1: возможны
альтернативный корректный путь, read, иная последовательность или разрешённое
действие. Требовать доказуемый source-policy/state конфликт для текущего хода.
Task reward — не turn label. Предыдущие ходы получают0 лишь при подтверждённой
корректности, не автоматически. До первого доказанного нарушения; после него
ходы исключать; неясный префикс не превращать в verified-correct историю.
Все модель/seed варианты одного task и общих entity/near компонентов — один split.

## Длина, чистота, заморозка

Полный текущий production renderer. Считать реальные token lengths, не добавлять
padding/дубли для длины. Сохранить долю>16k; если её нет, original long-input gate
остаётся false. Exact/near/entity decontamination против всех protected input-only
наборов и старых DEV/HOLDOUT перед split; frozen-v2 DEV/HOLDOUT/STRESS в TRAIN
не включать. При переиспользовании старого TRAIN сохранять split lineage.
Старый открытый holdout не называть новым: подготовить новые source components,
заморозить входы/метки до оптимизации и маркировать HUMAN_UNVERIFIED.
Качество выше счётчика: rejected/ambiguous/error cases и причины сохранить.
Новый training protocol и readiness отчёт требуются до оптимизации.
