# Полная схема + замороженный верификатор: dev520, 20.10.2026

После исправления V8 выполнен полный base 35B overall → open answer_audit → exact final
→ MAX при квоте .40. Затем к одним и тем же решениям применены замороженные V8
base/new verdicts как понижающий фильтр: threshold=0, hard защищены, без добора квоты.
Новая LoRA обучена ранее; нового обучения в V8–V10 не было.

**Это локальный exploratory результат, не F1 закрытого конкурса.** Данные просмотрены
ранее, human review отсутствует. В сравнении с defaults лучшего ZIP использован
batch64 вместо16, eager synchronous LoRA-capable runtime без активного адаптера
для основной схемы. Компиляторный кеш переиспользован; prediction cache отсутствует.
Конечные оценки верификатора пересчитаны V8; его reviews сохранены от V7. V10 не
генерировал верификатор повторно внутри полной схемы.

## Результат при .40

| Решение на dev520 | TP | FP | FN | Precision | Recall | F1 |
|---|---:|---:|---:|---:|---:|---:|
| Тот же текущий overall без open/MAX | 106 | 102 | 39 | .509615 | .731034 | .600567 |
| Полная схема open/MAX | 110 | 98 | 35 | .528846 | .758621 | .623229 |
| Полная схема + base verifier | 109 | 85 | 36 | .561856 | .751724 | .643068 |
| Полная схема + новая LoRA verifier | 110 | 88 | 35 | .555556 | .758621 | .641399 |

Новая LoRA снимает **10/98 FP, не теряя ни одного из 110 исходных TP**.
Снятые FP распределены по трём доменам: airlines2, healthcare2, insurance6.
Base verifier снимает13 FP, но теряет1 TP в airlines. Его F1 чуть выше; преимущество
дообученной модели над base по общему F1 не установлено. Практический сигнал новой
LoRA здесь — более консервативное снятие обвинений, а не доказанное превосходство модели.

Вне исходного pool40 новая LoRA ошибается и теряет TP; это не универсальный безопасный
верификатор. В частности, на valid46 при pool70 она снимает3 FP ценой3 TP и ухудшает F1.
При historical pool40 valid46 остаётся18TP/0FP. Вывод относится к конкретной схеме .40.

## Неопределённость и полнота

Offbox пересчитаны решения из исходных overall/final scores, проверено совпадение
с predictions и onbox метриками. Все **520 overall и 520 final exact**, MAX глобально
не откатывался к overall. Чтение gold выполнялось после inference.

Bootstrap: 65 conversation groups,1000 общих resamples, seed20261020. В каждом draw
заново пересчитывались ранжирование и квота .40; модельные outputs фиксированы.

Bootstrap оценивает неопределённость на имеющихся просмотренных данных и фиксированных
outputs; он не подтверждает перенос на private test или устойчивость новой генерации.

## V11: зафиксированная следующая проверка fresh generation

После результата V10 запущены три полных повтора свежего verifier только на208
положительных решениях полной схемы. Candidate IDs фиксируются predictions V10,
без gold. Входы — прежние исходные V7 prefix+policy, без предварительного accusation
текста или результата baseline. Код проверяет208 строк и отсутствие gold fields.

Модель — тот же обученный35B adapter,100 source modules; chunk64, max_tokens192,
temperature0/seed0; V8 source-quote admission и exact YES−NO score. UNKNOWN или
невалидная цитата сохраняют обвинение, hard защищены, квота не добирается.
Все reviews и scores в каждом повторе считаются заново; APC/compiler cache допускаются.
Повторы не считаются независимыми задачами. Никакого изменения порогов по результатам.

Это проверка того, сохраняется ли выигрыш при фактическом применении на candidate pool,
а не только при переиспользовании reviews, сгенерированных ранее на всех строках.
Измеряются TP/FP каждого повтора, изменения решений и время каждого прохода отдельно.
Это ещё не packaged end-to-end submission run и не cold-start проверка.

GPU предоставлен пользователем в распоряжение агента. Прежний срок15:15 МСК был
рабочим ограничением агента; после V10 агент выделил на V11 ещё до20 минут,
с абсолютным deadline15:35 МСК (12:35 UTC). Это не дословно заданный пользователем
новый срок. Job конечный, без автоматических quality retries.
