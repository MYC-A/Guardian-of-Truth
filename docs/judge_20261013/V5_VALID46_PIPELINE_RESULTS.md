# Полная ветка лучшего open-review40 ZIP с LoRA 35B — 20.10.2026

Проверена основа `guardian-judge-qwen36-awq-open-review40-max-34fb1c75-20261018.zip`
с текущими parser/mechanical fixes и bounded turn-shape, без ветки 4B. Конфиг
непосредственно сверен с JUDGE_CONFIG.json внутри указанного ZIP. Профиль:
overall с hints → open answer audit → exact final → MAX → квота .40 и hard.
Во второй версии окончательная LoRA 35B применяется ко всем трём модельным этапам.

## Найденная ошибка native runtime

В vLLM 0.19.1 shared expert регистрировался дважды: через `mlp.shared_expert` и
`mlp.experts._shared_experts`. Эти регистрации используют одни и те же GPU storage.
При активации canonical weights загружались, затем alias без своих весов сбрасывал
те же буферы. В результате 24 из 50 исходных обученных модулей не работали корректно.
Это обнаружено прямым worker-аудитом, а не предположением из F1.

Исправление в изолированном worker удаляет только 16 дублирующих регистраций для
обученных shared expert слоёв 32–39. Исходные веса, base model и target filter
не изменяются. После реактивации: все 50/50 исходных модулей покрыты, 38 packed
модулей подключены, 62 пары A/B с учётом разделения GDN точно равны GPU-буферам.
Сохраняются BEFORE, repair и AFTER receipts. До этой проверки quality-строки
не оцениваются; технический probe после исправления повторяется.

Отдельные warnings о q/k/v и gate/up относятся к исходным именам до упаковки и
сами по себе были вводящими в заблуждение: attention-матрицы совпадали уже до
исправления. Они не были доказательством потери attention weights. Первоначальное
сообщение о доказанной ошибке target filter исправлено в протоколе.

Предыдущие classifier-only результаты V5 измеряли неполное runtime-подключение
LoRA; их нельзя использовать как результат полной LoRA. Обучение 1458/1458 и
файлы адаптера исправны, повторного обучения для этого исправления не требовалось.
Лучший ZIP с 35B без LoRA этот механизм адаптера не использовал.

## Границы сравнения и время

В обоих arms включён LoRA-capable engine, eager и synchronous scheduling;
остальные параметры лучшего ZIP, включая batch/context/APC/deadlines, сохранены.
Это host-venv эксперимент алгоритма полной ветки, не побитовое воспроизведение
исходного runtime ZIP. Оригинальный ZIP не менялся, promotion не выполнялся.

Контроль переиспользован из первой полностью завершённой попытки после сверки
конфига, input и exact coverage. Технические попытки остановлены до получения
полного quality-результата LoRA: сначала изучение warnings, затем ограничение
сериализации RPC, затем выявление несовпадения GPU-буферов. Gold для выбора
исправления не использовался. Исправление основано на идентичности storage и
покрытии матриц. Нет выбора checkpoint, квоты или лучшего quality-повтора.

Вызовы overall/prepass/final заняли 254.2 с у контроля и 335.7 с с LoRA
(около +32%). Stage wall: 545.0 и 468.0 с соответственно; меньшее второе время
объясняется повторным использованием compilation cache и не является ускорением
инференса. Сумма model-call времени не доказывает прохождение закрытого теста.

valid46 уже исследован, здесь только один парный прогон; ранее наблюдался runtime
шум решений. Наблюдаемое ухудшение не устанавливает универсальный вред LoRA.
Улучшение конкурса не измерено. На основании этого результата добавлять новую
LoRA в лучший ZIP не обосновано. Оценка полной LoRA на dev520 после исправления
runtime в рамках этой проверки valid46 не выполнялась.
