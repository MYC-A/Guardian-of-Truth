## 1. Что именно мы проверяем

Проверяемый ответ — это не просто текст. Он состоит из обязательств, которые агент берёт на себя.

Примеры обязательств:

- «Цена равна 708» — числовое утверждение.
- `resume_line(C1001, L1002)` — попытка изменить состояние.
- «Я уже сбросил настройки» — утверждение о совершённом действии.
- «Эту задачу нельзя решить доступными средствами» — утверждение об отсутствии допустимого плана.
- «Сообщите дату рождения» — утверждение, что необходимого значения ещё нет в контексте.

Ответ считается ошибочным, если найдено хотя бы одно существенное обязательство, которое опровергнуто контекстом, не имеет допустимого основания или нарушает правило.

## 2. Почему одного графа фактов недостаточно

Обычный граф может хранить:

```text
L1002 --дата окончания договора--> 2025-01-31
```

Но для проверки действия нужны ещё:

```text
resume_line --требует--> договор действует
2025-01-31 --раньше--> текущее время
договор закончился --противоречит--> договор действует
```

Для проверки отказа нужен поиск в обратную сторону:

```text
цель пользователя
  → возможные действия
  → условия действий
  → доступные инструменты
```

Поэтому внутри системы находится не только граф сведений, а четыре связанные структуры:

1. Реестр правил.
2. Журнал изменяющегося состояния.
3. Граф доказательств и выводов.
4. Набор обязательств проверяемого ответа.

## 3. Какие данные хранятся

### 3.1. Запись о сведении

Условное представление:

```json
{
  "id": "fact_104",
  "subject": "line:L1002",
  "relation": "contract_end_date",
  "value": "2025-01-31",
  "value_type": "date",
  "source_kind": "tool_response",
  "source_ref": "turn_4:get_details_by_id",
  "valid_from_turn": 4,
  "valid_to_turn": null,
  "status": "current",
  "extraction_confidence": 1.0
}
```

В этом раннем примере `extraction_confidence=1.0` обозначает механическое чтение поля, а не вероятность истинности даты. В реализации пока нет измеренных вероятностей: используется `null`.

Если языковая модель извлекла из свободного текста пользователя его намерение, уверенность может быть ниже:

```json
{
  "subject": "user",
  "relation": "wants_human_transfer",
  "value": true,
  "source_kind": "user_message",
  "source_ref": "turn_12",
  "extraction_confidence": 0.93
}
```

Число `0.93` здесь иллюстративное. Так его можно будет интерпретировать только после отдельной проверки соответствия оценок реальной частоте ошибок; сейчас такого измерения нет.

### 3.2. Запись о правиле

```json
{
  "id": "rule_resume_03",
  "action": "resume_line",
  "condition": "contract_end_date >= current_time",
  "effect_if_false": "forbidden",
  "source_ref": "policy:telecom:resume_line",
  "translation_status": "verified"
}
```

Для правила важнее не вероятностный вес, а состояние проверки перевода:

- `exact` — правило получено из формального описания или схемы;
- `verified` — правило извлечено из текста и подтверждено второй проверкой;
- `uncertain` — смысл правила ещё неоднозначен.

Неоднозначное правило нельзя использовать как безусловное основание для строгого нарушения.

### 3.3. Запись о выводе

```json
{
  "id": "derivation_77",
  "inputs": ["fact_104", "fact_current_time"],
  "operation": "date_less_than",
  "result": "contract_expired",
  "method": "deterministic",
  "confidence": 1.0
}
```

Если вывод сделан через смысловое сопоставление текста, метод будет `semantic`, а уверенность — оценённой на контрольных примерах.

### 3.4. Запись об обязательстве ответа

```json
{
  "id": "obligation_12",
  "response_span": "resume_line: {customer_id: C1001, line_id: L1002}",
  "kind": "action",
  "checks": [
    "tool_exists",
    "schema_valid",
    "arguments_grounded",
    "preconditions_satisfied",
    "action_order_valid"
  ],
  "status": "invalid_action",
  "witness": "derivation_77"
}
```

## 4. Где находятся веса

У системы есть три разных вида чисел. Их нельзя смешивать.

### 4.1. Уверенность извлечения

Показывает, насколько надёжно текст был преобразован в структурированную запись.

Хранится рядом с узлом сведения или обязательства.

Примеры:

- точное чтение поля из JSON: `1.0`;
- извлечение явной даты из текста: около `0.98` после калибровки;
- распознавание неявного намерения: может быть `0.75–0.95`;
- сложное смысловое толкование правила: может быть заметно ниже.

Эти значения нельзя задавать вручную навсегда. Они измеряются на размеченных примерах отдельно для каждого вида извлечения.

### 4.2. Уверенность сопоставления

Показывает, насколько уверенно система связала два объекта.

Например:

```text
«моя линия» ↔ L1002
«эта карта» ↔ credit_card_123
«да, меняйте» ↔ подтверждение конкретной операции
```

Она хранится на связи между узлами, а не внутри самого факта.

### 4.3. Коэффициенты окончательного оценщика

Они нужны только тогда, когда строгие проверки не дали ответа.

Например, окончательный оценщик может учитывать:

- осталось ли неподтверждённое обязательство;
- насколько полно разобран ответ;
- есть ли противоречащие сведения;
- насколько надёжен найденный путь доказательства;
- согласны ли независимые смысловые проверяющие модули.

Эти коэффициенты хранятся отдельно от графа: в файле настроек или в небольшой обученной модели. Они не изменяют факты и правила.

## 5. Почему нельзя просто усреднить веса

Пусть система нашла:

```text
явный запрет действия: 1.0
три косвенных довода в пользу действия: 0.8, 0.7, 0.7
```

Среднее могло бы сделать действие допустимым. Это неправильно: явный запрет имеет другой логический уровень.

Поэтому решение иерархическое:

```text
если найдено строгое нарушение       → label=1
иначе если есть доказанное противоречие → label=1
иначе если всё подтверждено и покрыто   → label=0
иначе                                    → вероятностная оценка
```

## 6. Как вычислять уверенность ответа

В ранней концепции предлагалась эвристика:

```text
уверенность ответа = минимальная уверенность
                     среди необходимых путей доказательства
```

Это показатель слабого звена, но не вероятность правильности всей цепочки и не гарантированная нижняя граница. Совместная корректность нескольких звеньев может быть ниже каждого отдельного значения. В первой реализации эту эвристику не используем.

Аналогично, максимум можно было бы использовать как показатель ранжирования, но не как готовую вероятность ошибки:

```text
уверенность ошибки = максимум по свидетельствам нарушения
```

Не следует сразу перемножать вероятности: разные проверки часто используют один источник и потому зависимы.

Позже окончательные значения можно откалибровать на отдельных данных так, чтобы, например, среди решений с уверенностью около `0.8` примерно 80% действительно были правильными.

## 7. Сквозной пример

Ответ:

```text
resume_line(customer_id="C1001", line_id="L1002")
```

Ход проверки:

1. Разборщик создаёт обязательство действия `resume_line`.
2. По описанию инструмента проверяется имя и форма аргументов.
3. Из результата инструмента находится связь `L1002 belongs_to C1001`.
4. Из результата инструмента извлекается дата окончания `2025-01-31`.
5. Из системного блока извлекается текущее время `2025-02-25`.
6. Точное сравнение дат выводит `contract_expired=true`.
7. Правило `resume_line` требует, чтобы договор не закончился.
8. Условие действия опровергнуто.
9. Создаётся минимальное свидетельство из двух дат и одного правила.
10. Итоговая метка — `1` без участия вероятностного оценщика.

## 8. Пример, где нужна вероятность

Ответ:

```text
Пользователь явно отказывается от предложенного способа решения.
```

Если пользователь сказал «ну это мне, наверное, не подходит», смысл не совершенно однозначен.

Здесь языковая модель выделяет намерение с некоторой уверенностью. Для надёжности можно:

1. Получить два независимых разбора.
2. Попросить каждый указать точный фрагмент текста.
3. Проверить, одинаково ли они определили объект отказа.
4. Передать расхождение окончательному оценщику.

Именно для таких мест нужны значения уверенности. Для проверки существования инструмента или сравнения дат они не нужны.

## 9. Что остаётся общим, а что относится к предметной области

Общая часть:

- источники и их полномочия;
- журнал состояния;
- происхождение значений;
- схемы инструментов;
- обязательства ответа;
- проверка покрытия;
- прямое доказательство;
- обратный поиск допустимого пути;
- иерархическое решение.

Предметный модуль добавляет:

- названия сущностей;
- возможные состояния сущностей;
- последствия действий;
- специальные предварительные условия;
- способы разложения целей пользователя.

Например, общая система знает понятия «состояние», «действие», «условие» и «переход». Модуль розницы сообщает ей, что `return_delivered_order_items` переводит заказ из `delivered` в `return_requested`.

## 10. Главный принцип

Граф хранит не мнение системы о правде, а проверяемую историю происхождения каждого вывода.

Вероятности применяются только там, где пришлось понимать неоднозначный естественный язык. Они не имеют права отменять точную схему, арифметику, дату, явный запрет или доказанное противоречие.
