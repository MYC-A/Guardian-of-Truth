## Ключевые выводы

1. **LLM-канал.** Валидный Mistral API (ministral-14b-latest, ключ
   пользователя) работает с сервера. LangExtract через API: 89% span-validity
   (5258 извлечений, 46 кейсов, 0 ошибок) против 31% у локального
   mistral-7b — канал сильнее подтверждён эмпирически, локальный канал
   заморожен (6 записей, отдельный namespace).

2. **P: почему старый P терял TP — установлен точно.** Extraction НЕ был
   проблемой (карты извлекались и заземлялись: FN-диагностика pjudge:
   judge_missed_with_grounded_cards). Проблема была в суждении без
   механического evidence: добавление graph digest даёт recall 1.0
   (FN 11→0 относительно старого P; FN 0 на public46). Обратная сторона —
   precision .62: карта-центричный судья over-triggers. G+P — лучший рукав
   P-семейства; +LangExtract и +Clingo поверх G+P монотонно ухудшают.

3. **NuExtract3 (I.C).** Как ИСТОЧНИК структурных карточек — работает
   (46/46 кейсов, 376 правил, верифицированные span-цитаты; рабочий путь:
   AutoModelForImageTextToText+AutoProcessor по имени, W4A16 через
   transformers, vLLM 0.15.1 arch Qwen3_5 не поддерживает). Как ЗАМЕНА
   контекста судьи — честный негатив (F1 .23–.38): выжимание policy в
   карточки теряет нюансы, нужные судье. Ценность N — покрытие и вход для
   P/Q/роутера, не контекст судьи.

4. **Clingo/RuleIR (I.D, S8).** 64 заземлённые карты, 28 детерминистически
   связанных, 0 нарушений: формальный слой консервативен (premise
   observability — главный блокер). Контроль не изменён. Честный негатив:
   формальная проверка не добавила пользы на этом датасете; включение её
   вердиктов в судью (pglcljudge) ухудшает метрики.

5. **Q (I.E).** 3332 механически найденных расхождения двух независимых
   каналов (NuExtract3 локально vs Mistral API; общих весов/провайдера/кода
   нет). 12 глубоких различающих вопросов (бюджет), 5 верифицированы
   механически (deciding words найдены в policy дословно), 1 downstream
   flip. Задокументирован предел: 1 кейс, где оба канала пусты (gold=1) — Q
   не срабатывает.

6. **Gate.** granite-guardian-4.1-8b существует (rev ab01ccca..., Apache 2.0,
   16G, установлен в superz_models/). На общем протоколе (тот же бюджет
   4800/7200, greedy, no-think, pre-baked groundedness) 4.1 лучше 3.3
   standalone: F1 .8095 vs .7805 (+1 TP, FP те же, 43/46 согласий).
   Протокольное отличие задокументировано: 4.1 не имеет guardian_config;
   BYOC-блок финальным user-сообщением. Baseline OR granite (F1 .8889) не
   превзойдён — обновление модели даёт скромный, но реальный прирост
   standalone-канала.

7. **Router v1 (Stage II).** Детерминированная маршрутизация (R1 tool_claim
   23/46, R2 entity_mixing 2/46, R3 rule_premise 38/46, R4 refusal 7/46,
   R5 interp_divergence 45/46): routing recall 1.0 — ни один gold-положительный

   были control=1). Ценность — трассировка и учёт покрытия, не прирост F1.

8. **Agent v1 (Stage III).** Минимальный адаптивный агент (оркестратор
   Mistral API ≤4 шага/кейс, 5 детерминированных инструментов, независимый
   evidence-controller, фиксированный агрегатор): 167 вызовов инструментов,
   23 NL-вопроса, 1 невалидный evidence отброшен. FP 2→1 (верифицированное

   там, где контроль стоял в 0 — consistent с P: для этого нужен
   граф-evidence в суждении, не только вопросный поиск).
