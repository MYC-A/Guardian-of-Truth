# EXPERIMENT_PROTOCOL.md — hybrid-service line (2026-10-01)

Branch: `research/hybrid-service-20261001` (from `research/three-architectures-24gb-20260930` @ 4df13b97).
Directive: «Guardian как сервис, с проверкой графовых, смысловых и формальных гибридов» (2026-10-01).
Этот документ фиксирует конфигурационную матрицу, гипотезы, критерии выбора,
бюджет и сплиты ДО массового инференса. Всё, что обнаружено ПОСЛЕ вскрытия
sealed-результатов, принадлежит новой версии протокола и новому эксперименту.

## 0. Главный вопрос исследования

Какое сочетание существующих графов (GE/GP), прямых судей (J),
специализированных проверяющих моделей (B) и формального ядра (Φ) даёт
лучший результат на новых данных при реальных ограничениях ресурсов
(24 ГБ GPU / 31 ГБ RAM / диск ~32 ГБ)?

Пять обязательных контрольных клеток (финальный ответ):
**граф без Φ / Φ без графа / граф + Φ / граф + новый checker / полный гибрид.**

## 1. Три представления (фиксация терминов)

| Слой | Что содержит | Реализация-кандидат |
|---|---|---|
| **GE** — граф свидетельств | сущности/ID, аргументы, события, время, наблюдения, состояния, источники, попытка/успех/провал | `guardian_truth.parsing` + `guardian_truth.provenance` (live, ядро с 421f9616); digest `g_graph.graph_digest` |
| **GP** — смысловой граф политики | цитаты правил, действия, условия, исключения, модальность, связи | карточки P-line (`p_precond_api` extract) + `micrograph_certificate_v1` (bounded) |
| **Φ** — формальная программа | типизированные предикаты, операторы, численные/временные ограничения | `semantic_pipeline_v1.rule_ir` + proof-engine gate-trees + Clingo |

Правило честности: в GE не записывать предположения LLM как факты; в GP
сохранять исходные предложения и помечать интерпретацию как интерпретацию;
в Φ сохранять исходную цитату и все смысловые допущения; во всех
представлениях указывать, что не извлеклось.

## 2. Единый harness

* Вход: `policy + полный каталог + история до хода + target response +
  metadata`; gold никогда не передаётся pipeline/кешу/моделям.
* Все arms — через одну схему конфигурации (JSON, `service/configs/`)
  и один скорер (`check`-семантика §13 + TP/FP/FN/TN).
* Неизменные оси при сравнениях: данные, исходный текст, основная модель,
  prompt scaffold, контекст, structural-модуль (v0.2), обработка
  невалидного ответа (1 технический re-ask → invalid/UNKNOWN).
* Для LLM с цитатами: валидация verbatim + source_refs; для
  MiniCheck/FactCG/Granite — их НАТИВНЫЙ формат (см. smoke), затем общий
  adapter; не принуждать все модели к одному JSON-контракту.
* Хранение: сырые ответы, нормализованный результат, цитаты и spans,
  причины отбрасывания, повторы, model revision, prompt hash, input hash,
  время, токены, стоимость. Кеш только идентичных вычислений.
* Исправленный structural-модуль v0.2 одинаков для всех новых основных
  arms; чистые модельные каналы без shortcut считаются отдельно;
  замороженный V0.1/V6 остаётся историческим baseline.

## 4. Конфигурационная матрица (§8 директивы, полный план)

Одинаковая основная модель J и одинаковый скорер во всех arms; кандидаты
(Σ-банк) одинаковы для S2–S7 (объединение подозрений finder-каналов +
независимые контрольные гипотезы).

### 4.1 Контекст и граф (одна модель, разные представления)
G0 (текст→J) / G1 (+GE digest) / G2 (+GP карточки) / G3 (+GE+GP) /
G4 (только GE+GP без текста — диагностический). В G1: старый digest vs
новый подграф с ID/временем/источниками. Контроль: сопоставимая по объёму
текстовая сводка (plain summary) — отделяет пользу структуры от повторения.

### 4.2 Центральный квадрат (главная проверка)
M00=G0 / M10=G3 (GE+GP, без Φ) / M01 (Φ+статус+основания, без графа в
контексте судьи) / M11 (GE+GP+Φ). Первый paired-проход: одна и та же
извлечённая Φ в M01 и M11 — проверяется именно помощь графа судье.
Дополнительно L0 (текст+L→J) и L1 (текст+GE+L→J): привязка/суммы/даты
кодом, сложный смысл — моделью.

### 4.3 Поиск → проверка
S0 (A→B) / S1 (A+GE/GP → B+GE/GP) / S2 (банк→MiniCheck-Flan-T5) /
S3 (банк→Bespoke-7B при свопе диска) / S4 (банк→FactCG) /
S5 (банк→Granite BYOC native, прежний критерий и custom-policy отдельно) /
S6 (банк→PRT-Qwen при свопе) / S7 (лучший checker + B на спорных).
Три задачи отдельно (не смешивать метрики): (1) подтверждение
факта/действия историей; (2) подтверждение интерпретации цитатой политики;
(3) подтверждение наличия нового нарушения кейсом.

### 4.4 Перевод (одинаковый backend)
T0 (существующий one-shot) / T1 (+подключённый syntax repair в оцениваемом
runtime) / T2 (выбор из явных вариантов/шаблонов) / T3 (LogicLLaMA — если
воспроизводим; иначе честный NOT_RUN) / T4 (контролируемый LE/LPS-подобный
ввод — при исполнимом инструменте).

### 4.5 Симбиозы (после dev)
H0=S1 / H1 (GE+L+B, исключения по GP) / H2 (GE/GP+лучший Φ-frontend+Φ+B) /
H3 (GE/GP+лучший checker+B, без Φ) / H4 (=H3+Φ) / H5 (лучшая комбинация +
прямой независимый судья / V6-routing). Ablation лучшего сложного варианта:
убрать GE / GP / Φ / checker / B по очереди.

## 5. Данные и независимость

* public46 = сожжённый исторический регрессионный набор (только
  воспроизведение и локализация регрессий; НЕ выбор default).
* **Dev**: ~80–120 кейсов, 8–12 свежих policy-семейств (fresh по
  USED_DOMAINS-аудиту всей истории, включая calib/Level E/zai/прошлые
  sealed/dev); пары ERROR/NO_ERROR близкой формы; обязательные феномены
  §10 директивы (исключения, границы сумм/дат, похожие ID, версии
  состояний, attempted/failed/succeeded, инструкции в данных, RU+EN).
* **Sealed**: 160–240 кейсов, ≥16 других семейств; gold замораживается до
  инференса (manifest + sha256); создание gold ≠ единственный источник —
  каждая метка с обоснованием из текста политики/наблюдений.
* Family-специфика: rename-близнецы внутри семей (leakage-контроль),
  counterfactual-minimal-pairs, «no candidates ≠ exhaustive».
* Источники: контролируемые мутации + новые домены с проверенными
  исходами; внешние наборы (AgentHallu/τ-bench) — только после
  лицензионной и label-семантической проверки (reward траектории ≠ gold
  хода).

## 6. Метрики и критерий выбора (заморожены до sealed)

* Основные: TP/FP/FN/TN, P/R/F1 (macro по семействам + общий); отдельно
  ошибки с вызовом и текстовые; доля валидных ответов, citation failures,
  UNKNOWN/fallback; покрытие finder; recall verifier на истинных
  кандидатах; стоимость (вызовы/токены/латентность p50/p95, peak VRAM).
* End-to-end считаются С учётом невалидностей и fallback (FN не
  удаляются из знаменателя).
* Выбор service default: среди конфигураций, укладывающихся в измеренные
  память/латентность, — лучшая по согласованной метрике (macro-F1) с
  контролем FP; при отсутствии статистически убедительного победителя —
  Pareto-варианты «быстрее/дешевле» и «полнее». Малая разница на
  нескольких кейсах ≠ превосходство (paired-сравнения, группировка по
  семействам).
* Гипотезы-предсказания (фальсифицируемые):
  H-G: GE digest помогает верификатору (flash-G1 .6667 vs .6207), но НЕ
  первому судье (S5 .6032) — ждём того же знака на свежих данных;
  H-Φ: формальный результат помогает судье ТОЛЬКО при подтверждённом
  переводе (S8: 60 unknown — премис-обсервабельность);
  H-CK: MiniCheck силён на фактах, слаб на нормах (smoke: 0.867 с
  промахами ровно на policy-исключении) — специализированное место, не
  универсальный судья;
  H-GR: Granite BYOC custom-policy — сильный нативный policy-checker
  (smoke 1.0) — кандидат S5/native и третьего проверяльщика в V-ветке.

## 7. Порядок прогонов и бюджет

* Этап A (готов): восстановление, HISTORY_AUDIT ч.2, регрессии §5.1–5.3,
  минимальный сервис (7/7 + HTTP), native smoke (таблица выше).
* Этап B: G/M/L/S/T-контроли на dev + новые checker-модели; банк
  кандидатов единый; каждый пропуск объясняется (unavailable/memory/
  license/runtime), BLOCKED ≠ качество 0.
* Этап C: H0–H5, поддерживаемые результатами B; ablation.
* Этап D: пре-регистрация 6–8 финальных конфигураций (обязательно:
  текущий baseline V6, лучший без Φ, лучший с Φ, лучший специализированный
  гибрид) → sealed прогон.
* Этап E: сервис на выбранном default + operational limits; выбор после
  sealed = использование test для выбора; новое независимое утверждение —
  только на новом holdout.
* Бюджет API: лимит этапа записывается перед прогоном (вызовы/токены);
  при исчерпании — прозрачное сокращение shortlist с сохранением
  центрального квадрата и checker-тестов.
